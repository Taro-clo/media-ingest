## 原理类

### 1. 为什么不复制文件，非要建硬链接？

**一句话答案**：因为硬链接让同一份数据在硬盘上**只存一份**、同时出现在两个目录里；复制会让空间翻倍，还会破坏"这两份永远是同一份数据"这个前提。

对比一下：

| | 硬链接（本项目采用） | 复制 |
|---|---|---|
| 硬盘占用 | **一份**（多的是目录里的名字，不是数据） | **两份** |
| 建链速度 | 元数据操作，瞬间完成（几 GB 的剧集也是毫秒级） | 要真的搬几十 GB |
| 删掉下载原文件后 | 媒体库那份**照常播放**，数据还在（直到最后一个名字被删） | 媒体库那份是独立副本，也能播 |
| 能否知道"这俩是同一个文件" | 能，`ls -i` inode 号完全相同 | 不能 |
| 修改内容的相互影响 | **改一个等于改两个**（同一份数据） | 互不影响 |

本项目是给 NAS 用的，媒体库里动辄几十 TB。复制会让你的存储需求**直接翻倍**，这就是为什么硬链接是唯一合理的选择。

反过来，**静默复制**是本项目明令禁止的行为：一旦偷偷改成复制，用户以为没占空间、实际占了两份，而且"删了原文件媒体库仍是同一份数据"这个前提悄悄失效了。所以遇到硬链接建不了的情况，本应用**宁可让任务失败并报错，也绝不回退为复制**（详见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 A9）。

### 2. 硬链接会占双倍空间吗？

**一句话答案**：不会。整个文件系统里那份数据只存**一份**。

硬链接是在目录里加一个**新名字**指向**同一个 inode**（同一个数据块）。所以：

- `ls -i 下载文件` 和 `ls -i 媒体库文件` 的 **inode 号完全一样**；
- `stat` 的**硬链接数**（`%h`）是 2 或更多；
- 磁盘总用量**没有增加**。

**【NAS 宿主】自己验证**：

```bash
du -sh /vol1/1000/Download/qbittorrent/Bangumi/"Show A"
du -sh /vol1/1000/Library/Bangumi/"Show A"
df -h /vol1/1000
```

两条 `du` 数字几乎一样大，但 `df` 的已用空间在建立硬链接前后**没有明显变化** —— 因为 `du` 统计的是"这个文件夹的内容有多大"，不是"盘上多占了多少"。

> ⚠️ **一个必须知道的反面**：既然是同一份数据，**原地修改内容会同时影响两边**。你在媒体库里用编辑器"保存"某个视频文件的内容，下载目录里那份的内容也变了（因为它们是同一份数据）。
> 所以：**只重命名、只删除，没问题；不要原地编辑内容。**
> （换个说法：`mv`/`rm` 动的是"名字"，安全；原地写入动的是"数据"，两边同时变。）

### 3. 能不能跨硬盘（跨文件系统）建硬链接？

**一句话答案**：不能 —— 而且比"跨文件系统"更严：**必须同一个挂载**。这是 Linux 内核的限制，`os.link` 会报 `Invalid cross-device link`（EXDEV），**没有任何办法绕过**（除了复制，而本项目不做复制）。

**为什么**：inode 号只在**单个文件系统内部**唯一（跨了文件系统，`inode 12345` 可能是完全另一个文件）；而内核 `linkat(2)` 在真正建链接之前，还会先比较源与目标的**挂载身份** —— 不在同一个挂载上就**一律 EXDEV**，跟 `st_dev`、btrfs 子卷都没有关系。所以"同一个文件系统"还不够，必须是"**同一个挂载**"。

**你会看到什么**

应用里（任务详情 / 日志 / 预检）：

```
跨挂载：源 /vol1/1000/Download/qbittorrent/Bangumi 与目标根 /vol1/1000/Library/Bangumi 不在同一个挂载，
os.link 会返回 EXDEV。本应用不会回退为复制文件。
请把下载目录与媒体库目录放进同一个 bind 挂载（见 docker-compose.yml 的 MEDIA_ROOT）。
```

> 📌 这条判定在**运行前只警告、不硬拦**（不会阻止你启动任务）；真跑起来后由**逐文件源完整性核对**给出最终结论 —— 失败就是 `link_failed`，**不会**悄悄复制一份冒充硬链接。

手动命令：

**【NAS 宿主】**

```bash
ln /vol1/1000/Download/qbittorrent/test.mkv /vol1/1000/Library/test.mkv
# ln: failed to create hard link '/vol1/1000/Library/test.mkv' => '...': Invalid cross-device link
```

**怎么判断自己的路径是不是在同一个挂载上**

**【NAS 宿主】**

```bash
findmnt -T /vol1/1000/Download/qbittorrent -o TARGET
findmnt -T /vol1/1000/Library -o TARGET
```

两条 `TARGET`（挂载点）**相同**才行。

> ⚠️ **别用 `stat -c '%d'` 当依据**：`st_dev` 相同**不能**说明能建硬链接（两条独立 bind 就曾 `st_dev` 相同却分属两个挂载，这正是只凭 `st_dev` 判断"假绿"的根因）。要确认就用 WebUI 媒体库页的「验证（含实证探针）」，`same_filesystem` 是 `true` / `false` / `null` 三态（第 36 问）。

**怎么办**

把下载根与媒体库根放进**同一条 bind**（就是 `docker-compose.yml` 里的 `MEDIA_ROOT` 共同父挂载）：

```yaml
volumes:
  - ${MEDIA_ROOT:-/vol1/1000}:${MEDIA_ROOT:-/vol1/1000}
  - ./data:/data
```

**不要**拆成 `…/qbittorrent:…` 与 `…/Library:…` 两条（两条独立 bind 必然失败 —— 第 34、35 问）。

> 实在需要跨盘，只有"复制"这一条路，本应用刻意不做。你可以自己用 `rsync` 之类的工具另做一份副本 —— 但要清楚那已经不是硬链接方案了（空间翻倍、删源后两份互不相干）。

### 4. 会不会动我的下载文件？

**一句话答案**：不会。但**请诚实理解**："源目录挂 `:ro`、内核层面写不进去"那种**结构性保证**与本方案的**单一共同父挂载**（内核让"源单独 `:ro` 挂载"与"跨路径硬链接"互斥）**做不到**，它被替换成下面这套**可验证的保证** —— **这是降级，不是等价替代**。

三层保证：

1. **代码层保证**：应用**没有任何代码路径**会写源目录；回归测试 `tests/test_no_source_mutation.py` 守住这一点。（源目录不单独以 `:ro` 挂载，原因见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §2.1（b）与 §3.5。）
2. **执行体行为**：建链阶段对源目录只做 `os.listdir` / `os.walk` / 读文件大小 / `os.link(源 → 目标)`。`os.link` **不修改源文件**，只是在目标目录加一个名字。
3. **重命名只发生在目标**：重命名阶段的目标根（`ROOT_DIR`，现行由规则引擎 `app/processors/engine.py` 执行）被指向你的**媒体库**路径，它原地改名的是媒体库里那一份的名字，不动下载目录里的名字。

**另外还有"可验证"这一步**：任务**开始前**对源目录做逐文件快照（相对路径、大小、inode、mtime），**结束后**再核对一遍；有差异就写进 `Task.result.source_integrity = {"ok": false, "changed": [...]}`，并在 `warnings` 里给**中文告警、列出被动过的路径**（硬链接本身会让源文件链接数 +1、ctime 变化，这两项**不算**差异，所以不会误报）。

> 结论：现在能**发现**源被动过并告警，但**不能阻止**它。这是单挂载形态的已知代价，文档不粉饰。

**唯一的理论例外**（不是本应用造成的，是硬链接的固有性质）：

> 下载目录那份和媒体库那份是**同一份数据**。如果你**原地编辑媒体库里的文件内容**（不是改名，是改内容），下载目录里那份的内容也会变。
> 这是硬链接的定义决定的，不是应用的行为。所以：**只改名、只删除是安全的；不要去原地编辑内容。**

### 5. 能不能删掉原始下载？

**一句话答案**：可以，删掉下载那份**不会**让媒体库那份失效（数据还在）。但**有一个大坑**：如果 `orphan_cleanup` 开着，下一次跑任务时应用会认为"源已经不在了"→ **把媒体库那份也递归删掉**。

先说好消息：硬链接的两份是同一个 inode，**删掉其中一个名字，数据不会消失**（inode 的链接计数从 2 变 1）。所以：

**【NAS 宿主】**

```bash
rm -rf /vol1/1000/Download/qbittorrent/Bangumi/"Show A"
# 媒体库里的 /vol1/1000/Library/Bangumi/Show A/... 依然能正常播放
```

**但是**：建链阶段有一个"孤儿清理"行为（现行执行体：原生实现 `app/processors/hardlink.py`）：它会检查日志里记录过的每个一级文件夹，**如果 `source_dir/文件夹` 不存在了，就递归删除目标里对应的文件夹**。

所以删掉原始下载后，只要跑一次任务（手动、qBittorrent 回调、或定时扫描），媒体库那份就会被删掉。

**如果你要"删源保库"，必须关掉孤儿清理：**

- 单库级别：编辑该媒体库，把 **`orphan_cleanup` 设为关闭**；
- 全局级别：**设置页**把 **`orphan_cleanup_enabled` 设为 `false`**（这是总开关，与单库设置是"与"的关系：两个都为真才真的删）。

**【NAS 宿主】**也可以用接口改全局开关：

```bash
curl -s -b cookies.txt -X PUT http://192.168.1.100:18081/api/settings \
  -H 'Content-Type: application/json' \
  -d '{"orphan_cleanup_enabled":"false"}'
```

> ⚠️ **这是本项目里最容易造成"我的媒体库文件不见了"的设置组合。** 如果你打算清理下载盘，**先关孤儿清理**，再做删除。关掉之后，源文件被删的旧记录会一直留在日志里、每次跑任务都会去 `stat` 一次（无实际写操作），不会有别的副作用。

**还有一件事**：删掉原始下载**不会**立刻释放空间 —— 因为媒体库那份还指着同一个 inode。要等**最后一个名字**也被删掉，空间才真的回收。

### 6. qBittorrent 不开着还能工作吗？

**一句话答案**：能。网页操作、手动跑任务、目录扫描补偿都不需要 qBittorrent 活着；只有"下载完成自动触发"和"qBittorrent API 补偿"需要它在跑。

| 功能 | 需要 qBittorrent 在跑吗 |
|---|---|
| 网页新建/编辑媒体库 | ❌ 不需要 |
| 网页手动跑任务（全量 / 指定文件夹） | ❌ 不需要 |
| 目录扫描补偿（`scan_enabled=true`） | ❌ 不需要（它只读源目录里的文件夹） |
| 「下载完成自动触发」回调 | ✅ 需要（qBittorrent 才会去执行那条 curl） |
| `qbittorrent_url` / 用户名密码 的 API 补偿 | ✅ 需要 |

也就是说：**qBittorrent 停了、你手动跑一下，照样能把已下载的东西整理好。** 这也是扫描补偿存在的意义 —— 回调漏了（容器重启、curl 超时）也能补上。

## 任务与状态类

### 7. 为什么任务显示"跳过"？

**一句话答案**：通常是因为这个文件夹**已经处理过了且内容体积没变** —— 这是幂等机制在正常工作，不是错误。

建链阶段用"一级文件夹的总体积"当作处理标记（应用侧的"已处理"判据是每库作品账本，见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) B14）：如果**账本里记过这个文件夹、且现在算出来的体积和记录的一样**，就打印：

```
文件夹已记录且体积一致，跳过: <文件夹名>
```

重命名阶段同理（现行执行体：规则引擎 `app/processors/engine.py`）：

```
Skipping folder: <文件夹名> (already processed at 2026-10-09 01:20:11)
```

**什么时候会"跳过"**：

| 场景 | 是否正常 |
|---|---|
| 同一个文件夹第二次、第三次跑 | ✅ 正常，就是幂等 |
| 下载完一个种子，但 qBittorrent 连着触发了两次回调 | ✅ 正常 |
| 你手动跑了一次全量，又跑了一次 | ✅ 正常 |
| **刚下载完的新剧集却跳过** | ⚠️ 不正常 —— 见下面 |

**"新剧集却跳过"的常见原因**：

- **同一部剧追加了等体积的文件**：建链阶段只看"总体积是否相同"。你换了/追加了内容但**总体积恰好一样**，它就认为没变（这是这套记账方式的已知限制，见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 L9）。解决办法：用**强制重跑**（force）。
- **库里根本没有匹配到**：那不会产生任务，也就不会显示"跳过"。回看回调响应里的 `ignored` 列表。

**强制重跑怎么用**：任务页/库详情页的「运行」里勾选 force，或者 API 传 `"force": true`。它会把该文件夹的"已处理"记录从**本库账本**里删掉，让建链阶段重新处理一遍。

> ⚠️ force 会让建链阶段对**已存在**的目标文件再次 `os.link`，结果是一批 `创建硬链接失败: ... File exists` 的报错（建链阶段**不覆盖、不删除**已有文件）。其中"目标就是**同一个 inode 的硬链接**"的那些会被应用改判成**幂等跳过**（`already_linked`，计入 `skipped`），任务**不会**因此判失败；只有"同名但 inode 不同"才算 `link_failed`。**只在真需要重算时用。**

> ⚠️ **一个真的会踩的坑：账本是"这个文件夹已经处理过"的凭据。**
>
> 账本记的是"这个作品**已经处理过**"，而**不是**"媒体库里有这些文件"。建链阶段的跳过判据是**本库账本**（数据库表 `link_records`）里那一行，键是"本库 + 同 `source_dir` + 同 `target_dir` + 同体积"（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) B14）；`hard_links.log` **照写**（兼容与审计），但**不是判据**。满足就打印「文件夹已记录且体积一致，跳过」并**什么都不做**。所以：
>
> - 你手动删掉 `/vol1/1000/Library/...` 下的硬链接、或把库目录换成另一个空目录 ⇒ 那批作品**不会被重新建出来**（应用认为早做完了）；
> - 要重建某个作品：用「作品记录」页的**「删除记录」**（见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §6.4），下次运行该库时它会自动重新建链 + 重命名；
> - 只想重建某一部剧：用「立即运行」勾 **force** 更快，它只删该范围的记录（见第 20 问）；
> - 结论：**删 `/data/logs/hard_links.log` 达不到"重算"的目的** —— 它不参与跳过判断，删了反而丢一份审计记录。展开见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §2.8 的提示。
>
> 💡 **每个媒体库各有一本账**（自己的重命名日志，见第 33 问），所以"某个库的日志丢了"只影响那个库，不会牵连别的库。

### 8. 为什么文件没有被重命名？

**一句话答案**：绝大多数情况是**不符合识别规则** —— 季文件夹名字不对、扩展名不在白名单、或文件不在季文件夹的直接子目录里。

这是**刻意保持**的行为：识别规则由**配置**决定（处理器字段），应用不会替你去放宽或猜测。逐条对照：

**（1）番剧（Bangumi 库）**

| 检查项 | 规则 | 你的情况如果…… |
|---|---|---|
| 季文件夹名字 | 必须**恰好**是 `Season <数字>`（`SEASON_PATTERN.fullmatch`） | `Season 1 (2018)`、`Season1`、`Specials`、`SP`、`S01` → **整个季文件夹被忽略** |
| 文件位置 | 必须在**季文件夹的直接**子目录里 | 文件在 `Season 1/Sub/` 这种嵌套目录里 → **不处理** |
| 扩展名 | 只处理 `.mkv` `.mp4` `.ass`，**大小写敏感** | `.MKV`、`.srt`、`.flac` → **不重命名**（但**会**被建硬链接） |
| 剧集号 | 文件名里要能被正则认出集数 | 认不出时看 `episode_fallback`：**内置 `bangumi` 的推荐默认是 `null`** ⇒ 该文件**保留原文件名、不改名**（计入 `result.kept_unresolved_episode`，日志里一行 `Kept (no episode): …`）；`legacy` 预设或你显式写成的字符串 `"None"` 则会把 `None` 命名进文件名（`...ENone.mkv`） |
| 库的处理器 | 必须是 `bangumi` | 如果建库时选的是 `hardlink_only` → **只建链接，不重命名** |
| 文件夹体积 | 与缓存日志记录一致就跳过整个文件夹 | 见上一问 |

**能被认出的剧集号写法**（现行是 **9 条有序规则**，序号即优先级，全部忽略大小写、数字只允许 1~2 位；逐条正则见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3.2 增量 ④）：① `第N集/话/話/回` ② `EpisodeN` ③ `SxxExx`（取 `E` 后面那个数）④ `[N]` ⑤ `EPN` ⑥ `#N` ⑦ `-N`（后面不是 `bit`）⑧ `空格 + E/e + N`（后面是空白或句点，且不是 `bit`）⑨ 兜底 `空格 + N`（后面是空白或句点，且不是 `bit`）。

**认不出的写法**（默认的 9 条规则**不认**）：`Show.E07.mkv` / `Show.e06.mkv` 这种 **`E` 紧贴点号**的形式（规则 8 要求 `E` 前是空白）、`Show 12v2.mkv`（数字后面不是空白/句点）、`Show - 1920x1080.mkv` 与 `[1AE35F3A]` 里的 `E35`（都不会被当成集号）。想要宽松的旧口径就用 `legacy` 预设（第 31 问），或把那两条正则加回 `episode_patterns`。

重命名结果形如：`<一级文件夹名> S01E01.mkv`。

**（2）电影（Movie 库）**

| 检查项 | 规则 |
|---|---|
| 处理位置 | **只处理一级文件夹的直接子文件**（不递归、不看子目录） |
| 扩展名 | 只处理 `.mkv` `.mp4` `.ass`，大小写敏感 |
| 同后缀多个文件 | 每个后缀**只重命名体积最大的那一个**，其余保留原名 |
| 结果 | `<一级文件夹名>.<后缀>` |

**（3）通用排查步骤**

1. 打开**任务详情页**，看日志里有没有 `Renamed: ... -> ...` 或 `Skipping folder: ...`；
2. 确认文件夹的**结构**（季文件夹名、文件所在层级、扩展名大小写）；
3. 确认库的**处理器**是 `bangumi` / `movie` 而不是 `hardlink_only`；
4. 需要重新处理时用 **force 重跑**。

完整规则见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) §2、§3 和 [`docs/contracts/COMPATIBILITY.md`](../contracts/COMPATIBILITY.md)。

### 9. 支持哪些命名格式？

**一句话答案**：形状就两种 —— 番剧 `Season NN` + 集数 → 输出 `<文件夹名> S01E01.<后缀>`；电影输出 `<文件夹名>.<后缀>`。**集数的识别规则是 9 条带边界约束的有序规则**，严格到不会把分辨率、CRC、`12v2` 当集号；最朴素的 `legacy` 口径用的是那两条宽松老规则（第 31 问）。

**番剧（Bangumi）**

- **季文件夹**：必须恰好是 `Season <数字>`（只有直接子目录会被检查）。
- **集数识别**（**9 条有序规则**，序号小者优先；全部忽略大小写、数字只允许 1~2 位）：

  | # | 写法 | 例子 ⇒ 集号 |
  |---|---|---|
  | 1 | `第N集` / `第N话` / `第N話` / `第N回` | `第01集.mkv` ⇒ 01、`第 12 話.mkv` ⇒ 12 |
  | 2 | `EpisodeN`（前面不能紧贴字母） | `Episode 3.mkv` ⇒ 03 |
  | 3 | `SxxExx`（季号随意，取 `E` 后面那个） | `S02E07.mkv` ⇒ 07 |
  | 4 | `[N]` | `[05].mkv` ⇒ 05 |
  | 5 | `EPN`（前面不能紧贴字母） | `EP09.mkv` ⇒ 09 |
  | 6 | `#N` | `#04.mkv` ⇒ 04 |
  | 7 | `-N`（后面不是 `bit`） | `Show - 11.mkv` ⇒ 11 |
  | 8 | 空白 + `E`/`e` + `N`（后接空白或句点，且不是 `bit`） | `Show E12.mkv` ⇒ 12 |
  | 9 | 兜底：空白 + `N`（后接空白或句点，且不是 `bit`） | `Show 12.mp4` / `Show 12 1080p.mkv` ⇒ 12 |

  **一条都不命中的写法**（一律算"认不出集数"）：`Show 1920x1080.mkv`、
  `Show x264-10bit.mkv`、`Show H265-8bit.mkv`、`Show - 10 bit.mkv`、`Show [1920x1080].mkv`、
  `Show [1AE35F3A].mkv`、`Show 第123話.mkv`、`Show S123E07.mkv`、`Episode123`、`Show 12v2.mkv`、
  `Show.E07.mkv`（`E` 前不是空白）。全角空白（`　`）也算空白，所以 `Show　12　1080p.mkv` ⇒ 12。

- **输出**：`<一级文件夹名> S01E01.mkv`（集数补零到两位）。
- **字幕 `.ass`**：后缀 = 文件名里 **`.ass` 之前最后一个点**到结尾的整段 —— 所以 `Show.S01E01.chs.ass` → `<文件夹名> S01E01.chs.ass`（`.chs.ass` **整段**保留）；`.ass` 前没有别的点时后缀就是 `.ass`。
- **不支持**：`Season 1 (2018)` 这种带附加信息的季文件夹；`.MKV`（大写）；嵌套子目录里的文件；`.srt` 等不在白名单的扩展名。
- **认不出集数**（`episode_patterns` 全不命中）时分两种情况：
  - 规格里**显式配置**了 `episode_fallback`（`preset=legacy` 就是，自己写字符串 `"None"` 也一样）⇒ 集数段落到那个**字面量**：`Show.01.ass` → `<一级文件夹名> S01ENone.01.ass`（其中 `.01` 被当作后缀保留）。这与 `legacy` 预设一致。
  - `episode_fallback` **留空**（`null`，**内置 `bangumi` 的推荐默认就是它**）⇒ **不造名字**：命名里既然引用了 `episode` / `episode_raw`，这个文件就**保留原文件名、完全不改**。它会计入 `result.kept_unresolved_episode`、出现在 `result.samples.kept_unresolved_episode`、日志里一行 `Kept (no episode): <文件夹>/<原文件名>`，并在 `warnings[]` 里汇总告警（一个文件夹里多个压制版本不会再互相撞名覆盖）。

**电影（Movie）**

- 只处理一级文件夹里的**直接**文件；
- 只处理 `.mkv` / `.mp4` / `.ass`；
- 同一后缀只重命名**体积最大**的那个；
- 输出：`<一级文件夹名>.<后缀>`。

> 这两套默认规则是**逐字符冻结**的兼容性契约（由回归测试的黄金值守护），应用不会替你去改它们；想调整就把处理器**复制**一份再改（见第 16 问与第 32 问）。

### 10. 为什么同一个文件夹第二次跑什么都没做？

**一句话答案**：这是**幂等性**在起作用，是设计目标，不是 bug。

具体机制是"一级文件夹总体积"这个标记：

1. 第一次处理某个文件夹时，建链阶段把它的总体积（递归所有文件的字节数）记进**本库账本**；
2. 第二次跑时，应用先算一遍体积，和账本里记的比：
   - **一样** → 打印"文件夹已记录且体积一致，跳过"，**什么都不做**；
   - **不一样** → 删掉旧记录、重新建链接、记录新体积。

所以重复执行不会产生重复文件，也不会破坏已有硬链接。这是刻意的：

- qBittorrent 连着触发两次回调 → 第二次空跑，无害；
- 你手动点了一次全量 → 已处理过的文件夹全部空跑；
- 定时扫描每隔 15 分钟跑一次 → 绝大多数时候是空跑。

**为什么"空跑"很重要**：它让"补偿机制"变得安全。你可以放心开着定时扫描，不必担心它反复操作你的文件。

**想绕过它**：用 force 强制重跑（见第 7 问，含风险说明）。

### 11. 容器重启后任务会继续吗？

**一句话答案**：**任务的历史记录和日志都在**（存在数据卷的 SQLite 里），但**正在执行的任务不会自动接着跑** —— 重新触发一次就好，因为建链阶段是幂等的，重跑安全。

分清楚两件事：

| 东西 | 重启后 |
|---|---|
| 账号、媒体库规则、设置 | ✅ 都在（`/data/mlm.db`） |
| 任务列表与历史 | ✅ 都在 |
| 每条任务的日志 | ✅ 都在 |
| 正在执行中（`running`）的任务 | ❌ 会被打断，**不会**自动续跑 |
| 排在队列里（`queued`）的任务 | ⚠️ 重启后不会自动开始，需要重新触发 |

**怎么办**：

1. 去任务页看看有哪条任务状态不正常（卡在 `running` 或 `queued`）；
2. **直接重新跑一次**（任务页的「重试」，或库详情页的「运行」）；
3. 放心：应用按"文件夹体积是否变化"判断（第 10 问），已经处理好的部分会被跳过，只补做缺的部分。**不会重复造文件、不会破坏已有硬链接。**

**想少遇到这种情况**：`docker-compose.yml` 里已经配了 `restart: unless-stopped`，容器意外退出会自动拉起；升级时用 `docker compose stop` 而不是 `kill`。

> 💡 如果你希望"重启后自动把没做完的任务补上"，最省事的办法是打开**扫描补偿**（设置页 `scan_enabled = true`）。扫描每隔一段时间看一遍源目录，发现「没记录过或体积变了」的文件夹就会建任务 —— 等价于自动补做。

### 12. 如何只处理某一部剧（某一个文件夹）？

**一句话答案**：在库详情页点「运行」，把范围选成「指定文件夹」，填那个一级文件夹的名字即可。

**网页操作**：媒体库 → 选中该库 → 「运行」→ 范围选 **指定文件夹** → 填文件夹名（例如 `Show A`）→ 执行。

**注意**：这里填的是**一级文件夹名**（`source_dir` 下面那一层），**不是完整路径**、也不带斜杠。例如：

| 你的实际路径 | 要填的内容 |
|---|---|
| `/vol1/1000/Download/qbittorrent/Bangumi/Show A` | `Show A` |

**用接口**：

**【NAS 宿主】**

```bash
curl -s -b cookies.txt -X POST http://192.168.1.100:18081/api/libraries/1/run \
  -H 'Content-Type: application/json' \
  -d '{"scope":{"mode":"folder","folder":"Show A"},"force":false}'
```

**原理**：应用**只把作用域限制在你指定的那个一级文件夹**（`scope.mode="folder"` + `folder`），其余文件夹这一轮一眼都不看。**源目录里的东西一个字节都不动**（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 A7）。

> 如果这个文件夹已经被处理过、体积没变，它还是会**跳过**。想强制重做，勾上 force（见第 7、20 问）。

### 13. 能不能同时处理多个库？

**一句话答案**：能建任意多个库，但**一次只能跑一个任务** —— 队列是串行的。

- **库数量不限**：`番剧`、`电影`、`4K电影`、`国漫`……想建多少建多少；每个库有自己的源目录、目标目录、匹配条件、处理器。
- **一次回调可以命中多个库**：如果某个种子同时满足好几个库的匹配条件，会**全部入队**。回调响应里的 `tasks` 数组会列出新建的任务 id，`ignored` 列出没命中的库。
- **但队列是串行的**：同一时刻只有**一个**任务在执行，其余的排队等。这是刻意的设计 —— 建链阶段的原生实现会"读-改-写整份日志文件"，并发调用会互相覆盖（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 A12、L1）。

**串行会不会很慢**：不会。硬链接是元数据操作（瞬间完成），主要耗时在**算文件夹体积**（要遍历所有文件）。几百 GB 的一个文件夹通常几秒内完成。

**想更细粒度地并行**：做不到。串行是硬约束，为的是数据一致性。

### 15. 忘记密码怎么办？

**一句话答案**：口令是用安全哈希（scrypt）保存的，**没法"找回"**，只能**重置**：把数据库里的账号记录删掉，让它回到"首次使用、请创建管理员"的状态。

> ⚠️ 下面的操作不可逆（只影响账号，**不影响媒体库规则、任务历史和你的文件**）。做之前先备份 `data/`（见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §7）。

**方法 A：如果你还留着 `.env` 里的 `ADMIN_USERNAME` / `ADMIN_PASSWORD`**

先试试重启容器，看能不能用那组账号密码登录：

**【NAS 宿主】**

```bash
cd /vol1/1000/Docker/media-ingest
docker compose restart
```

> ⚠️ 如果数据库里**已经存在**管理员，仅靠 `.env` **不一定**会覆盖它（自动创建只在"一个用户都没有"时生效）。不行就用方法 B。

**方法 B：删掉账号记录（可靠）**

**【容器内】**

```bash
docker exec -it media-ingest python -c "import sqlite3; c=sqlite3.connect('/data/mlm.db'); c.execute('DELETE FROM users'); c.commit(); c.close(); print('账号已清空')"
```

然后**在浏览器里刷新页面**（或重启一下容器更稳妥）：

**【NAS 宿主】**

```bash

```

再打开 `http://<NAS_IP>:18081`，页面会引导你「创建管理员」—— 用新账号密码进去，**你的媒体库规则、任务历史全都还在**。

**进去之后建议做的事**：

1. 立刻去**设置页改密码**（并记住它）；
2. 如果 `.env` 里有明文 `ADMIN_PASSWORD`，把它删掉或注释掉；
3. 顺手确认 `hook_token` 和 qBittorrent 里填的命令还一致。

### 16. 能不能加自己的正则 / 命名规则？

**一句话答案**：**能 —— 这个项目就是为这件事做的。** 重命名规则现在是**配置**（不是代码）：你在网页的「处理器」页改，或者直接改 `/data/config/processors/<id>.yaml`。

**能改哪些**（一个处理器 = 一套规则，详见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §5）：

| 想改的东西 | 对应字段 |
|---|---|
| 新文件名怎么拼（段与顺序） | `naming.segments`（`{param}` / `{literal}` / `pad`） |
| 更复杂的计算（拼接、条件、正则提取） | `naming.expressions`（Python 表达式，见下方 ⚠️） |
| 哪些子目录算"季目录"、季号从哪来 | `traverse.accept_dirs`（`{pattern, season_group}`） |
| 哪些目录**整棵跳过**（特典、CD、扫图…） | `traverse.reject_dirs` |
| 接受哪些后缀 | `extensions`（**大小写敏感**） |
| 集数怎么从文件名里认出来 | `episode_patterns` + `episode_fallback` |
| 同后缀取哪个文件 | `selection.per`（`file` / `extension`） |
| 该库日志叫什么 | `log_file`（只能填文件名） |

**还是不能改的**：硬链接的**路径规则与目录层级**（`目标/<一级文件夹>/<相对源的完整子路径>/<同名文件>`，逐字节保留）。那是硬链接阶段的契约（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) §1 与 §4 的 B 系列），也**不提供**开关 —— 层级一变，Emby 就认不出剧集结构。

**改完怎么生效 / 怎么验证**：

1. 网页「处理器」页 → 保存（同一请求就把文件写好）；或者直接改文件，**5 秒内**自动导入（第 29 问）；
2. 用编辑器里的**实时预览**看新名字对不对；
3. 先「预检」+ **手动运行一个小文件夹**，去任务详情页看 `Renamed:` 行，确认无误再全量跑。

> ⚠️ **`naming.expressions` 里可以写 Python 表达式**（可用 `re`、`os`、`len`、`str`、`int`、`sorted`、`min`、`max` 与 `zfill`/`splitext`/`basename`/`ass_suffix`）。这是为"可拓展、不写死"付出的代价：**能改配置文件的人就能在容器里执行代码**。不需要就让它保持空（`expressions: {}`）。
>
> ⚠️ 改了处理器，**所有用它的媒体库都跟着变**。想只影响一个新库，就**复制**一份处理器再改（见第 32 问）。
>
> 想"加一套新规则"又怕影响现有的？新处理器 + 新库，老库继续用原来的处理器 —— 两套规则并存互不干扰。

### 17. 删除媒体库规则会删掉我的文件吗？

**一句话答案**：**不会。** 删规则只是删掉数据库里的一条"配置"，磁盘上的硬链接文件和下载原文件都原样保留。

接口的响应就明确写着这件事：

```json
{"deleted": true, "hardlinks_kept": true}
```

（`hardlinks_kept: true` = 硬链接已保留。）

**删一条规则会发生什么**：

| 东西 | 结果 |
|---|---|
| 该库的配置（源/目标/匹配条件/处理器） | ❌ 删除 |
| 已经建好的硬链接文件 | ✅ **原样保留**，Emby 照常能播 |
| 下载原文件 | ✅ 完全不受影响 |
| 该库的历史任务记录 | ✅ 保留（记录里会保留库名，方便你事后看懂） |
| 以后 qBittorrent 回调 | 这个库不再参与匹配，不会再触发 |

**网页上的删除需要二次确认**（会弹窗让你确认）。用接口时必须显式带参数，否则会被拒绝：

**【NAS 宿主】**

```bash
# 会被拒绝（400）
curl -s -b cookies.txt -X DELETE http://192.168.1.100:18081/api/libraries/1

# 正确
curl -s -b cookies.txt -X DELETE "http://192.168.1.100:18081/api/libraries/1?confirm=true"
```

> 💡 想真正清理磁盘上的媒体库文件，需要你自己动手删（`rm -rf /vol1/1000/Library/...`）。应用**不会**替你删 —— 因为"删库规则"和"删文件"是两件完全不同量级的事，不应该绑在一起。
> ⚠️ 删媒体库里的文件时记住：如果下载目录里那份还在，**空间不会释放**（同一个 inode 还有别的名字）。

### 18. orphan_cleanup（孤儿清理）是什么？默认开着安全吗？

**一句话答案**：它是"源文件被删后，顺手把媒体库里对应的硬链接文件夹也删掉"的行为。**默认是开着的**，但它确实是本项目里最需要你理解的一个能力。

**它做什么**：建链阶段（现行执行体：原生实现 `app/processors/hardlink.py`）会检查日志里记录过的每个一级文件夹，如果**源目录里那个文件夹已经不存在了**，就递归删除目标媒体库里对应的文件夹，并记录一行：

```
Deleted orphaned hard link folder: /vol1/1000/Library/Bangumi/Old Show
```

**为什么要保留它**：它是原生实现的一部分，本项目不改。而且它有用 —— 你在 qBittorrent 里删掉一部看过的番，媒体库里那份也会跟着清掉，不用手工维护。

**为什么相对安全**：

- 应用用的是**自己的日志副本**（`/data/logs/hard_links.log`），所以它**只会清理"本应用自己建立过链接"的文件夹**，不会去猜、不会扫描式删除你没记录过的目录；
- 每次触发删除，都会在任务日志里以 **WARN** 级显著记录被删的**完整路径**；
- ⚠️ 它删的是**硬链接**（媒体库那一份名字），**不会**影响你还在的下载原文件。

**开关（两级，与的关系）**：

| 层级 | 位置 | 默认 |
|---|---|---|
| 单库 | 编辑媒体库 → `orphan_cleanup` | `true`（开） |
| 全局 | 设置页 → `orphan_cleanup_enabled` | `true`（开） |

**只有两个都为真，才会真的删除。**

**什么时候必须关掉**：

- 你打算**删掉下载盘里的原始下载、但保留媒体库**（第 5 问的场景）；
- 你的下载目录会被临时清空/迁移（例如换盘、临时腾空间）；
- 你就是不喜欢任何自动删除。

**关掉的副作用**：源文件已被删的旧记录会一直留在日志里，每次跑任务都会去 `stat` 一次（纯读操作），不会有别的副作用。

**不管开还是关，它都只作用于目标媒体库。你的下载原文件永远碰不到 —— 应用代码层从不写源目录，任务前后还会逐文件核对源完整性（第 4 问）。**

### 19. permission_mode 是什么？开了会发生什么？

**一句话答案**：**默认关闭**；打开后会真的生效 —— 应用把**目标库**改成 `0777`，好让非 root 服务读得到库内文件。它是可选的开关，不是"永不实现"的预留字段。

**它做什么**：建链阶段把库根目录 + 本次处理到的每个作品文件夹的**目标侧整棵子树**（含体积一致、本来会跳过的旧作品）改成 `0777`（目录与文件都是）。默认关闭时**一个 `chmod` 都不做**；开启前 WebUI 会弹确认框，**从关到开必须确认**。

**为什么要确认**：媒体库里的文件是**硬链接**，与下载原文件**共享同一个 inode**，而权限位属于 inode —— 所以给媒体库放权会**同时改掉 `/vol1/1000/Download/qbittorrent` 下源文件的权限位**。内容、大小、inode 号、mtime 都不变（源完整性核对看不见这个变化），因此每次运行都会在任务日志里以 WARNING 记下「改了 N 个目录 / M 个文件」。这个代价无法通过实现技巧消除，所以只能由开启者**显式承担**（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) §1.6 与 B13）。

> **需要调整权限怎么办**：优先在宿主上针对**目录**做精确调整（见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §10.4），或让该服务以同属主/root 身份运行 —— 这些都不动源文件。递归 `chmod`/`chown` 整棵媒体库树会连带改到下载原文件（同一个 inode），这也解释了第 27 问的现象。

### 20. 强制重跑（force）会有什么后果？

**一句话答案**：它绕过"体积一致就跳过"的幂等机制，让建链阶段重新处理一遍这个文件夹；后果是**一批无害的"文件已存在"报错**，不会覆盖或删除任何已有文件。

**它做了什么**：在进入建链阶段之前，先把该文件夹的"已处理"记录从**应用自己的日志副本**里删掉，于是建链阶段看不到这条记录，就不会走跳过分支。

**会产生什么**：

- 对已经存在的目标文件再执行一次 `os.link(源, 目标)`；
- 目标已存在 → `FileExistsError` → 建链阶段打印 `创建硬链接失败: <路径> - [Errno 17] File exists`，**继续处理下一个文件**；
- 目标**就是源文件自己的硬链接**（同一 `(st_dev, st_ino)`）时，应用把这条改判成**幂等跳过**（结果 `already_linked`，计入 `skipped`），任务**不会**因为"全部已存在"而显示 `failed`；同名而 inode 不同（内容被换过）仍然算 `link_failed`，**绝不覆盖**；
- 建链阶段的行为是"**不覆盖、不删除**"（`except` 分支：打印后继续），所以你的已有文件**不会有任何损失**；
- 重命名阶段同理，会重新走一遍改名逻辑（已经改好的名字再改一次通常就是 no-op）。

> ⚠️ **两个要注意的地方**：
> 1. **重命名阶段不会覆盖**（含 `legacy` 预设、两种平台）：目标名被占用时按**体积**判定 —— 体积最大的拿干净名，其余加 ` (2)`、` (3)`… 后缀保留；目标盘上原有的同名文件比新来的小时改名**让位**（不删除）；找不到空位则保留原名 + 记 `error`。所以不会"丢一个硬链接"（**源下载文件始终不受影响**）。⚠️ 刻意**不**静默覆盖：`os.rename` 在目标同名时 **POSIX 静默覆盖**（真实事故里全库跑丢过 114 个文件）、**Windows 报 `[WinError 183]`**（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 L4）。仍然**不要把 force 当日常操作反复点**。
> 2. `force` 是**单次任务**的参数，不会永久改变幂等行为 —— 下一条任务还是按老规矩跳过。想长期强制重算，得每次勾选。

> ⚠️ **本问的范围**：`force` **只允许配合 `scope.mode="folder"`（单个作品）**，整库强制重跑（`scope.mode="full"`，默认值）**一律返回 400**，运行弹窗里也没有这个开关。上文的"删掉该范围的已处理记录"只发生在单个作品的范围里。要重做作品请走：①「作品记录」→「立即重命名」（只重命名、不建链）②「作品记录」→ 删除记录 ⇒ 下次运行自动补做。详见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §6.4 与本篇第 38 问。

**什么时候该用 force**：

- 你确认内容变了但**总体积恰好没变**（这是体积标记法的已知盲区，见 L9）；
- 上次任务中途失败、状态不确定，想重来一遍；
- 你手工改过名字，想让引擎重新按规则命名。

⚠️ **别用 `force` 去"补目标里缺的文件"**：建链阶段用的是**源目录里的原名**，目标里已改好名的同一 inode 会被**再链一份**（同一 inode 两个目录项 + 重命名阶段多出 ` (2)`）。详见 [`docs/meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-9。要重做某个作品，用 ① 删记录后重跑（目标文件夹整体重建，干净）或 ②「立即重命名」（只改名字）。

**什么时候别用**：只是"想再跑一遍看看" —— 不用，幂等机制本来就是设计来让你放心重复跑的。

### 21. hook token 泄露了怎么办？

**一句话答案**：去设置页重新生成一个，然后把 qBittorrent 里的回调命令更新成新的。

**token 是什么**：`/api/hooks/*` 接口的"钥匙"。拿到它的人就能触发你 NAS 上的任务（但不能读你的数据、不能删文件 —— 那些接口要登录 Cookie）。

**发现泄露后的处理步骤**：

1. **网页 → 设置页 → 回调 / Hook → 重新生成 token**（旧的立即失效）；
2. 复制页面上那条**新的完整回调命令**；
3. 打开 qBittorrent WebUI → **设置 → 下载 → 运行外部程序** → 粘贴替换；
4. 验证（**【NAS 宿主】**，用新 token）：

   ```bash
   curl -s -X POST "http://192.168.1.100:18081/api/hooks/qbittorrent?token=<新TOKEN>" \
     --data-urlencode "category=ban" \
     --data-urlencode "content_path=/vol1/1000/Download/qbittorrent/Bangumi/Show A"
   ```

   返回 `{"matched":...,"tasks":[...]}` = 新 token 生效；返回 `401 回调 token 不正确。请在「设置」页复制完整的回调命令（含 token=...）…` = 没生效（检查有没有多余空格/引号）。

**日常注意**：

- 不要把 token 贴到公开论坛、issue、聊天群或截图里；
- 别把含 token 的命令写进会公开的配置仓库；
- 应用把 token 存在数据库设置里（`/data/mlm.db`），**备份 `data/` 时注意那个备份里也含 token**。

### 22. 应用会读写宿主上的哪些目录？

**一句话答案**：**只有两条** —— `MEDIA_ROOT`（单一共同父挂载，容器路径 = 宿主路径）与 `./data:/data`。这两条以外的宿主路径，应用既不挂载、也不读写。

**展开说**：

- 下载目录与媒体库都在 `MEDIA_ROOT` 这一条挂载里（第 34 问），应用在容器里看到的路径与宿主上**逐字相同**；
- `/data` 是数据卷：数据库（`/data/mlm.db`）、配置（`/data/config/`）与日志（`/data/logs/`）都只在这里；
- `HOST_PATH_MAP` 只影响网页上的**展示**（第 24 问），不参与任何判断；
- 数据卷里那本账才是"已处理"的判据（第 23 问）。

**那我想改规则怎么办**：**改处理器**（第 16 问、第 29–32 问）。执行体是应用自己的两个模块：`app/processors/hardlink.py`（硬链接原生实现）与 `app/processors/engine.py`（配置驱动的规则引擎），行为由项目自己的回归测试（**冻结的黄金值**，见第 29–32 问与 [`docs/contracts/COMPATIBILITY.md`](../contracts/COMPATIBILITY.md)）守护。

### 23. 第一次运行会不会把已经处理过的文件夹全部重做一遍？

**一句话答案**：**不会**（只要 `/data/logs/` 里那本账还在）。"已处理"记录**只由应用自己写出来**，而且**每个媒体库各有一本账**。

**判据是什么**：

| 阶段 | 记录在哪 | 判据 |
|---|---|---|
| 硬链接 | **本库账本**（数据库表 `link_records`） | 本库 + 同 `source_dir` + 同 `target_dir` + 一级文件夹体积，全部一致就打印「文件夹已记录且体积一致，跳过」（`hard_links.log` 照写，但只是兼容与审计，见第 7 问） |
| 重命名 | `/data/logs/<log_file>`（每库一条，如 `bangumicache.log`） | 标题文件夹名 + 体积（见第 33 问） |

**什么情况下才会"全部重做一遍"**：

- 你**删掉了**对应日志（或整份 `hard_links.log`）；
- 你改了媒体库的**源目录**、或者改了 `volumes` 的**容器侧路径** ⇒ 日志里的 `Source:` 字符串对不上（只影响那个库，见第 24 问）；
- 换机器 / 换数据卷、`/data` 丢了；
- **新加的媒体库本来就没有历史记录** —— 第一次跑当然是从零开始，这是正常的。

**重做一遍会怎样**：安全。对已存在的目标文件再 `os.link` 会打印一批 `创建硬链接失败: … File exists`（**不覆盖、不删除**），结果只是慢一点、日志多几行；这些"目标本来就是同一 inode 硬链接"的条目会被算成**幂等跳过**（`already_linked`），任务状态不会因此变成 `failed`。不过同一轮里**孤儿清理会失效**（它不知道哪些处理过），所以发现账本丢了时，最好先确认清楚再跑。

**怎么确认账本还在**（**【NAS 宿主】**）：

```bash
wc -l /vol1/1000/Docker/media-ingest/data/logs/hard_links.log
ls -l /vol1/1000/Docker/media-ingest/data/logs/
```

> 💡 **账本日志可以一直用**：`/data/logs/*.log` 是应用自己的账本，升级镜像、换处理器都不会让它们失效。

### 24. 我把下载目录/媒体库换到别的路径了，要注意什么？

**一句话答案**：只挪**宿主**一侧（容器内路径不变）⇒ 基本什么都不用改；改了**容器内路径**或某个库的**源目录** ⇒ 那个库的历史记录会对不上，下一轮会**全量重扫一次**（无害，只是慢 + 一批 `File exists`）。

| 改了什么 | 要跟着改什么 | 日志会失配吗 |
|---|---|---|
| 宿主把下载目录挪到别处 | `docker-compose.yml` 的 `volumes` 第一条的**宿主侧** | ❌ 不会：容器内还是 `/vol1/1000/Download/qbittorrent` |
| 宿主把媒体库挪到别处 | `volumes` 第二条的**宿主侧** | ❌ 不会 |
| 数据卷挪走 | `volumes` 第三条的**宿主侧**（`DATA_DIR` 一般不用改） | ❌ 不会；但**日志要一起搬**，否则等于账本丢了 |
| 改了 `volumes` 的**容器侧**（如 `/vol1/1000/Download/qbittorrent` → `/data/vol1/1000/Download/qbittorrent`） | 所有媒体库的 `source_dir`/`target_dir` 也要改；`HOST_PATH_MAP` 的键跟着改（纯展示用） | ✅ **会**，需处置 |
| 只把某个媒体库换了个子目录（`/vol1/1000/Download/qbittorrent/Bangumi` → `/vol1/1000/Download/qbittorrent/Bangumi2`） | 网页上改库的源/目标目录即可 | ✅ **会**（只影响那个库） |

**关键规则**：

1. **`HOST_PATH_MAP` 现在只影响显示**（纯展示用，不参与任何判断）：键是容器路径、必须带前导 `/`；宿主值填错或漏填，只是网页上显示的路径不好看，**不影响功能**；
2. 容器内路径没变 ⇒ 库记录、日志都不用动；
3. 容器内路径变了、或换了库的源目录 ⇒ 两条路：
   - **不管它**：下一轮那个库全量重扫一遍，跑完日志就重新对齐了（**推荐**，最省事）；
   - **想避免重扫**：删掉 `/data/logs/hard_links.log` 里**对应那几行**（或整份删掉）再重启容器（整份删 = 所有库全量重扫一次）；
4. 只改库的**目标目录**（`/vol1/1000/Library/A` → `/vol1/1000/Library/B`）时：硬链接日志按**源目录**记账，所以不会重扫；但新目标目录是空的，**你得把已有硬链接搬过去或重跑** —— 重跑会因为"体积一致"被跳过，需要勾 **force**（见第 20 问）；
5. 别忘了 `/vol1/1000/Download/qbittorrent` 与 `/vol1/1000/Library` 必须仍在**同一个宿主文件系统**上，否则建硬链接会跨盘失败（`EXDEV`）—— 见第 3 问。

### 25. 应用运行日志和账本日志是怎么分开的？

**一句话答案**：**分开放** —— `/data/logs/` 里只放**账本类**日志（建链记账 + 每库一条的重命名缓存），应用运行日志、访问日志、任务日志都不写进去。

| 日志 | 写在哪 |
|---|---|
| 建链记账 | `/data/logs/hard_links.log`（只写记账行 + 孤儿目录清理行） |
| 每库重命名缓存 | `/data/logs/<log_file>`（每库一条，见第 33 问） |
| 任务日志（网页上看的） | SQLite 的 `task_logs` 表 + 内存环形缓冲 |
| 应用运行日志 / 访问日志 | 控制台（`docker logs`），**不写** `/data/logs/` |

**为什么这么分**：`/data/logs/` 是**账本**目录，混进访问日志或任务日志会让"这本账里有哪些作品"难以判读；所以硬链接日志的 handler 上挂着一个**日志隔离**白名单过滤器，**只放行两类记账行**（详见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §5.2）。

**注意**：账本日志只是**兼容与审计** —— 跳过判断看的是每库账本 `link_records`，删掉日志文件不会让任何作品重做（见第 23 问）。

### 26. 回调返回 `401` / token 不对怎么办？

**一句话答案**：绝大多数情况是**「设置页里的 token」和「qBittorrent 里那条命令里的 token」不一致** —— 最常见的起因是重新生成过 token、但没把新命令粘回 qBittorrent。

401 的完整响应长这样：

```json
{"detail": "回调 token 不正确。请在「设置」页复制完整的回调命令（含 token=...），或重新生成 token 后更新 qBittorrent 的「运行外部程序」。"}
```

**按顺序检查这三件事**：

| # | 检查什么 | 怎么做 |
|---|---|---|
| 1 | 两边 token 是否一致 | 打开**设置页 → 回调 / Hook**，点「复制回调命令」，与 qBittorrent「运行外部程序」里的内容**逐字比对**。只要点过「重新生成 Token」，旧命令**立刻**开始 401 —— 必须把新命令重新粘一遍 |
| 2 | 有没有把 `HOOK_TOKEN` 写进 `.env` | **写了也没用**：`hook_token` **不是环境变量**，`.env` 里既没有这个键、应用也不会读它。它由**首次启动随机生成**，存在 `/data` 的数据库里；唯一来源是**设置页**（或 `GET /api/settings` 返回的 `hook_token` 字段） |
| 3 | 命令是否还是一行、有没有多余字符 | qBittorrent 的输入框里**必须是一行**；粘贴时最容易带上换行、首尾空格或多余引号 —— `token=xxx ` 后面多一个空格，在服务端看来就是另一个 token |

**两个不常见但真的会踩的原因**：

- 命令里混进了 shell 变量（如 `$TOKEN`、`${TOKEN}`）—— qBittorrent 不会展开它，会原样发出去；
- URL 写坏了：漏掉 `?`、把 `?token=` 写成 `&token=`，或者 `token` 拼成了 `toekn`。

**验证方法**：把设置页复制到的那条命令直接执行一次（步骤见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §9.3）。返回含 `"matched"` / `"tasks"` = 通了；仍返回 401 = 命令里的 token 与当前 token 不一致（或带了多余字符），**回设置页重新复制一次**，不要手动改 token。

> **顺带一个静默失败的坑**：回调参数**只从 URL 查询串或 urlencoded 表单体读取**。如果你把命令改成 `-H 'Content-Type: application/json' -d '{...}'`，token 是对的、HTTP 也是 200，但 `torrent.name` 会为空、`matched` 恒为 `0`，**不报任何错**。给 qBittorrent 用的命令请照设置页复制的原文（`curl --data-urlencode …`），不要改成 JSON。

### 27. 为什么媒体库里的文件权限和下载目录里的一样？

**一句话答案**：因为它们本来就是**同一个文件**（同一个 inode）—— 硬链接不复制内容，也不复制权限，**权限是 inode 的属性，天然只有一份**。

**展开说**：

- 硬链接只是给同一份数据**多加一个名字**。你在 `/vol1/1000/Library/Bangumi/Show A/Season 1/Show A S01E01.mkv` 上看到的属主、权限位，和 `/vol1/1000/Download/qbittorrent/Bangumi/Show A/…/Show A S01E01.mkv` 上的**是同一份**，改哪边都一样；
- 所以"媒体库里文件权限不对"这件事，**根因一定在源文件本身**，而不是"应用没给媒体库设权限"。想改就要在**源**上改（或在宿主上针对目录调整，见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §10.4）；
- 应用**默认不**去 `chmod` 媒体库：那会连带改掉 qBittorrent 源文件的权限位（＝修改原始下载），所以它不是默认行为；只有显式开启 `permission_mode` 才会这么做（第 19 问）；
- 想让 Emby / 其它账号能读，正确做法是保证**源目录/源文件本身**对相应账号可读（本项目的参考部署里 `/vol1/1000/Download/qbittorrent` 对 `other` 已有 `r-x`），而不是去递归 `chmod` 媒体库整棵树 —— 那个动作会**真的改到下载原文件**。

**怎么自查是不是同一个 inode**（**【NAS 宿主】**，同一个文件在两侧各来一次）：

```bash
stat -c 'inode=%i  links=%h  %n' "/vol1/1000/Download/qbittorrent/Bangumi/Show A/Season 1/Show A S01E01.mkv" \
                                 "/vol1/1000/Library/Bangumi/Show A/Season 1/Show A S01E01.mkv"
```

两行的 `inode` 相同、`links` ≥ 2 ⇒ 它们就是同一份数据。

### 28. 运行时要靠宿主上装 Python 或别的工具吗？

**一句话答案**：**不用。** 镜像自带运行环境，宿主只需要 Docker 与那两条挂载（第 22 问）。执行体只有两个应用自己的模块：`app/processors/hardlink.py`（硬链接原生实现）与 `app/processors/engine.py`（配置驱动的规则引擎）。

**硬链接怎么做**：扫描与编排都是应用自己的原生实现 —— 变量名、打印文案、日志行格式，连三个怪癖（体积变了不删旧目标文件、孤儿清理不删日志行、只精确删"本源目录+本 folder"那一行）都逐条保留。产物由 `tests/test_hardlink_native.py` 的 A 组五条场景对**冻结的黄金值**断言。

**重命名怎么做**：规则（季目录正则、集数正则、后缀白名单、命名模板）抽成了**配置**（第 16 问），由 `app/processors/engine.py` 执行。**判据怎么保证**：产物被冻结成**黄金值**，由 `tests/test_processor_engine.py` / `tests/test_bangumi_episode_rules.py` / `tests/test_rename_extensions.py` 直接断言；`legacy` 预设代表最朴素的旧口径（第 31 问）。

**所以**：镜像可以原样搬到别的设备，硬链接与重命名照样能跑；宿主上除了那两条挂载之外，不需要准备任何东西。

### 29. 我改了 `/data/config/processors/*.yaml`，网页会变吗？多久？

**一句话答案**：**会，大约 5 秒**（周期由数据库设置项 `config_sync_interval_seconds` 决定，默认 5 秒；**它不是环境变量**，写进 `.env` / compose 不会生效）。后台线程每隔 5 秒比对一次文件的 mtime + sha256，发现是"外部编辑"就自动导入。

**具体过程**：

1. 你改了 `processors/bangumi.yaml`；
2. 最长 5 秒后，应用解析 + 校验（`schema_version` + 全量字段校验）；
3. **校验通过** ⇒ 一个事务里替换数据库里的处理器，网页「处理器」页刷新后就是新规则（顶部状态条提示「配置文件已从磁盘重新导入」）；
4. **校验失败** ⇒ **数据库一个字节都不改**，网页顶部出现**红色横幅**（写清哪个文件、哪一行、什么错），而且**你写的那份文件不会被覆盖**；改回合法内容后横幅自动消失。

**几个注意**：

- 正则一定要用**单引号标量**（`pattern: '^Season (\d+)$'`），别用双引号 —— 反斜杠会被 YAML 的转义规则吃掉；
- 别在改完文件后**立刻**又在网页上改同一个处理器：网页保存以数据库为准并**覆盖文件**（同一把锁保证不交错，但最后写的赢）；
- 想立刻生效、不等 5 秒：用「重新从磁盘导入」（`POST /api/config/reload`）；
- 想**关掉**自动导入（只手工 reload）：把设置项 `config_sync_interval_seconds`（**DB 设置项，不是 env**）设成 `0`；
- 不知道哪里错了：把文件内容发给 `POST /api/processors/validate`，它会返回 `{ok, errors:[{field,message}]}`（中文字段级错误，对照表见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §5.8）。

### 30. 我在网页上改了规则，磁盘上的配置文件会变吗？

**一句话答案**：**会，而且是一次请求内就写完**（不用等那 5 秒）。数据库是运行时真源，每次通过 API 成功写入（网页保存走的也是 API），应用都会**原子写出**受影响的文件。

**"原子写出"是什么意思**：先写同目录的临时文件（`*.yaml.tmp`），再 `os.replace()` 改名到位 —— 所以**不会出现写了一半的半截文件**（断电/重启也一样：要么是旧的完整内容，要么是新的完整内容）；同时把新文件的 sha256 记进 `config_files` 表，这样后台同步线程知道"这是我自己写的，不是外部编辑"。

**哪些操作会写文件**：所有会改变处理器/媒体库的接口 —— `POST/PUT/DELETE /api/processors`、`POST /api/processors/{id}/reset`、`POST/PUT/DELETE /api/libraries`。**只读**的 `GET` 接口一个字节都不写。

**文件长什么样**：YAML 1.1（`yaml.safe_dump`，`allow_unicode=True`、`sort_keys=False`），UTF-8 无 BOM，**以 `schema_version: 2` 开头**，2 空格缩进。因为应用会"规范化回写"，所以**你手写的注释与排版在导入后会被重排**。

> 💡 想长期维护带注释的版本：把模板放在别处，需要时再复制进 `/data/config/`；或者改完文件后就**不要**再用网页保存同一个处理器。

**验证**（**【NAS 宿主】**）：

```bash
docker exec media-ingest head -5 /data/config/processors/bangumi.yaml
docker exec media-ingest cat /data/config/libraries.yaml
curl -s -b cookies.txt http://192.168.1.100:18081/api/config | python3 -m json.tool
```

`GET /api/config` 里 `files[].in_sync` 为 `true` = 文件与数据库一致。

### 31. 我只想要最朴素的旧口径，怎么办？

**一句话答案**：把用到的处理器**重置成 `legacy` 预设**（`{"preset":"legacy"}`）。`legacy` = **最朴素的旧口径**：大小写敏感的后缀白名单、没认出集数也照样重命名成 `ENone`、**不含**任何"拒绝目录"规则。

> **两个预设差在哪**：`legacy` 的 `episode_fallback` 是字符串 `"None"`、集数规则是两条宽松老规则（"没认出集数 ⇒ 名字里带 `ENone`"、"`1920x1080` 被当成集号"在它身上**完全不变**）；**`default` 的 `episode_fallback` 是 `null`**（认不出集数的文件**保留原文件名、不改名**，见第 9 问与第 8 问的检查表），并且 **`episode_patterns` 是 9 条带边界约束的有序规则**（见第 9 问）。**注意**：处理器规格是播种后独立存在的，升级镜像**不会**自动改已存在的那份 —— 改法见第 8 问下方与 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3.2（⚠️ 别用处理器编辑页的「集数兜底」输入框清空：它存的是空串而不是 `null`）。

**两个预设的区别**：

| | `legacy`（最朴素的旧口径） | `default`（推荐值） |
|---|---|---|
| 命名 / 正则 / 后缀 / 集数识别 | 两条宽松老规则 + 大小写敏感的后缀表 | 与 `legacy` 相同；差异集中在本表**下面三行**（合起来是**四处增量**） |
| 拒绝目录 `reject_dirs` | **空**（没有这个能力） | 有：番剧用一份固定的默认名单、电影由用户指定（见第 16 问与 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §5.2）｜增量 ① ② |
| 集数兜底 `episode_fallback` | 字符串 `"None"` | **`null`**：认不出集数 ⇒ **保留原文件名、不改名**｜增量 ③ |
| 集数规则 `episode_patterns` | 两条老规则（无边界约束） | **9 条有序规则**（带边界约束；见第 9 问）｜增量 ④ |
| 结果差异 | 最朴素的旧口径（由**冻结的黄金值**断言） | 差在**被拒绝目录的子树不处理**（特典/CD/扫图那一类）+ **认不出集数的文件不改名** + **不把分辨率/CRC/`12v2` 当集号**（如 `Show - 1920x1080.mkv` 从"第 19 集"变成"认不出 ⇒ 保留原名"） |

**怎么切**：

- 网页：「处理器」页 → 该处理器 → 「恢复默认」→ 弹窗里选 **`legacy`** → 确认；
- 接口：`POST /api/processors/{id}/reset`，body `{"preset":"legacy"}`；切回推荐值用 `{"preset":"default"}`。

**切换后要注意**：

1. 处理器是**共享**的 —— 用它的所有媒体库都跟着变；只想让一个库走 legacy，就**复制**一份处理器（第 32 问）再重置它；
2. 切到 `legacy` 后，之前被 `default` 的拒绝规则跳过的目录**会开始被处理**（这才是有拒绝目录规则之前的行为）；
3. 硬链接阶段**没有 preset 的概念**，它一直按同一套判据处理（执行体是 `app/processors/hardlink.py` 的原生实现；第 28 问），不受这里影响。

> ⚠️ "最朴素的旧口径"只保证**这两套内置规则**的结果。如果你以前用的是自己改过的规则，那 `legacy` 也对不上 —— 你需要把那套规则**改写成配置**（第 16 问）。

### 32. 新加一个媒体库要写 Python 吗？

**一句话答案**：**不用。** 全在网页上：①复制/新建一个处理器 → ②改规则 → ③新建媒体库并选它 → ④先小范围跑一次看结果。

**完整步骤**（详细版见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §5.9）：

| 步骤 | 在哪做 | 做什么 |
|---|---|---|
| 1 | 「处理器」页 → 选 `bangumi`（或 `movie`）→ **复制/新建** | 起个新 id（`^[a-z][a-z0-9_-]{1,31}$`，如 `documentary`）与名字，避免改到内置的 |
| 2 | 同一页 → 编辑 | 调命名段（`naming.segments`）、接受目录正则、拒绝目录正则、后缀白名单；用**实时预览**确认识别结果 |
| 3 | 保存 | 同一请求就把 `/data/config/processors/documentary.yaml` 写好 |
| 4 | 「媒体库」页 → 新建 | 填名称、源目录（`/vol1/1000/Download/qbittorrent/...`）、目标目录（`/vol1/1000/Library/...`）、匹配条件，**处理器选 `documentary`**；`log_file` 留空会自动生成 `documentarycache.log` |
| 5 | 先「预检」→ 再「立即运行」一个一级文件夹 | 到任务详情页看 `Renamed:` 行，确认无误再全量跑 |

**要写代码的场景只有一种**：规则本身**表达不出来**（例如需要查外部 API、需要按数据库元数据改名）。`naming.expressions` 能覆盖相当多的计算（可写 Python 表达式，安全提醒见第 16 问），但它**不能**访问网络、也不能读数据库。

> 💡 想让新库只影响自己：处理器 id 独立、媒体库选它即可。内置的三个处理器不建议改（改了就影响所有用它的库，不过随时可以「恢复默认」）。

### 33. 每个媒体库的日志在哪？为什么文件名是 `xxxcache.log`？

**一句话答案**：**全部在同一个目录** `/data/logs/` 下，**一个媒体库一条**重命名日志；默认文件名取**该处理器登记的日志名**（内置 `bangumicache.log` / `moviecache.log` / `hardlink_only.log`），被**其它库**占用时加 `-2`、`-3`…，所以常见形态是 `xxxcache.log`。

**为什么集中在同一目录**：这是明确要求 —— "所有重命名日志放同一文件夹"。好处是备份/迁移/排查只看一个目录（`/data/logs/` 在数据卷里，跟着 `data/` 一起备份）。**不允许**再按媒体库分子目录。

**文件名规则**：

| 情况 | `log_file` |
|---|---|
| 两个内置库（番剧 / 电影） | `bangumicache.log` / `moviecache.log`（**保持原名**） |
| 用内置 / 自定义处理器的库 | 默认 = **该处理器登记的日志名**（`bangumicache.log` / `moviecache.log` / `hardlink_only.log` / 自定义 `<id>cache.log`）；被**其它库或其它处理器**占用时加 `-2`、`-3`…（如 `bangumicache-2.log`）。**第一个**用某处理器的库保持登记名，磁盘上已有同名文件照样继续追加 |
| 手动指定 | 建库/编辑库时可自己填，但**只能填文件名**（不许含 `/`，不许 `..`） |

**日志内容**（`json_cache`，`ensure_ascii=False, indent=4`）：

```json
{
    "Show A": {
        "size": 6620411689,
        "timestamp": "2026-10-13 00:37:47",
        "works_dir": "/vol1/1000/Download/qbittorrent/Bangumi"
    }
}
```

标题文件夹名 + `size` 就是"已处理"的判据（第 23 问）；`works_dir` 是可选的记录字段 —— 日志里没有它时**没关系**，应用会忽略缺失/未知的键。

**另外两类日志**（别搞混）：

| 类别 | 位置 | 谁写 |
|---|---|---|
| 硬链接日志 | `/data/logs/hard_links.log` | 建链阶段的原生实现 `app/processors/hardlink.py`（纯文本，格式见第 14 问） |
| 任务日志（网页上看的） | SQLite `task_logs` + 内存缓冲 | 应用（任务详情页轮询；不是文件，不在 `/data/logs/`） |

**常用命令**（**【NAS 宿主】**）：

```bash
ls -l /vol1/1000/Docker/media-ingest/data/logs/
tail -n 20 /vol1/1000/Docker/media-ingest/data/logs/bangumicache.log
```

新建库时若日志文件还不存在，应用会建一个空的 `{}` —— **不会**去别处找现成内容（应用只认 `/data/logs/` 里的账本）。

### 34. 为什么必须"同一个挂载"？把源和目标各挂一条不行吗？

**一句话答案**：不行。内核的 `linkat(2)` 在建硬链接前会先比较源与目标的**挂载身份**，不同挂载**一律** `EXDEV` —— 哪怕它们在同一个文件系统、`st_dev` 完全相同。

**分成两条独立 bind 就会是这样**（`…/qbittorrent:/…:ro` 与 `…/Library:/…`），结果：硬链接**永远**建不出来（核心功能失效），而预检还报"可以创建硬链接"（**假绿** —— 探针在只读的源目录里 `mkstemp` 失败后，悄悄退化成 `st_dev` 比较）。所以正确做法是**单一共同父挂载** + **容器路径 = 宿主路径**：

```yaml
volumes:
  - ${MEDIA_ROOT:-/vol1/1000}:${MEDIA_ROOT:-/vol1/1000}
  - ./data:/data
```

顺带一个旁证：这正是 *arr 那一整套生态要求"下载目录与媒体库在同一个挂载点"的原因。

**那为什么在宿主上直接 `ln` 就成功？** 因为源与目标在宿主上本来就同属 `/vol1` 这一个文件系统 —— 让 `link()` 返回 `EXDEV` 的不是路径写法，而是"两条独立 bind 造出两个挂载"的容器视角。

### 35. 拆成两条 bind 会怎样？会静默复制一份吗？

**一句话答案**：任务会失败（`link_failed`），运行前会有警告；**绝不会**静默复制 —— 本应用永远不做复制兜底。

- **预检**：`same_filesystem` 为 `false`，`probe.note`（同一条文案也会进 `errors[]`）给出中文修法（指名 `MEDIA_ROOT`）。预检接口会因此 `ok=false`、把库标成红色，但**不会阻止你启动任务** —— **跑任务**时同一判据只写 `Task.result.warnings[]` 并继续尝试；
- **执行**：`os.link` 抛 EXDEV ⇒ 该文件记 `link_failed`，任务结论是失败；日志与 `Task.result.warnings[]` 都写清原因与修法；
- **不会**出现"看起来成功了、其实占了两倍空间"的情况。

### 36. `same_filesystem` 是 `null` 是什么意思？

**一句话答案**：**无法实证** —— 探针在源树里找不到一个可以用来试链的普通文件（比如源根是空的、只有目录），所以软件**不给结论**，而不是猜一个。

判定用的是**实证 `link()` 探针**：从源根有界递归（深度 ≤3、最多 512 条、不跟符号链接）找一个已存在的普通文件 → `os.link` 到目标根的临时名 → 立刻删除；**源目录零写入**。三态：

| 值 | 含义 |
|---|---|
| `true` | 探针成功 —— 真能建硬链接 |
| `false` | 探针失败（EXDEV / 权限等）—— 见 `probe.note` 的中文修法 |
| `null` | 找不到样本文件，**无法实证**（任务仍可运行，真跑起来才知道） |

`st_dev` 只在**没有 `/proc`** 时作为降级参考，并且明确标注"不能预测 `link()` 成功"。

### 37. 为什么有的文件没被改名，而是停在原地？

**一句话答案**：它命中了设置页「**特典文件排除**」里的正则，软件认为它是 `NCOP` / `Preview` 这类特典，于是**把它排除在改名之外** —— 保留原名、留在原位置（**不改名、也不移动**）。

- 出厂默认 7 条判据：`NCOP`、`NCED`、`Preview`、`Creditless`、`Info`、`予告編`、`CM集`；对**含扩展名的文件名**做**大小写不敏感**的正则搜索，只作用于当前作用域目录的**直接文件**（`Season 1/特典/` 这种嵌套子目录里的文件不动）。
- **没有丢东西、也没有多出来东西**：命中文件停在原处（硬链接照旧），既不会被改名，也不会被搬进别的目录。
- ⚠️ 命中文件**不进 `<作品目录>/其他/`，也不会创建 `其他/` 目录**。你手上要是已经有 `其他/` 目录，想还原成平铺摆放就手工移回去（同一文件系统内移动不占额外空间）。
- **怎么关**：设置页「特典文件排除」卡片**清空**（保存成空数组）⇒ 该功能整体关闭，一切都按老样子当正片处理。
- **怎么改**：一行一条正则。误判正片时把那条写精确（例如 `^NCOP$`，而不是裸 `NCOP`）；**非法正则会当场报错**（点明第几条、哪个模式编译失败），不会静默吞掉。
- 任务结果里看 `result.extras_classified`（本次排除了几个）与 `samples.extras_classified`（每条 `{dir, name, size, pattern}`，其中 `pattern` 是命中的那条判据，便于反查误判）；日志里是中文 INFO「特典保留原名（判据命中，未改名、未移动）：…」。详见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §8.7.1。
- ⚠️ 对所有库与所有处理器生效，`legacy` 预设也不例外。

### 38. 想重做某个作品怎么办？

**一句话答案**：走「**作品记录**」页 —— ① 勾选它点「**立即重命名**」（只重命名、**不建链**）；② 或**删掉它的记录** ⇒ 下次运行自动补做（重新建链 + 重命名），其余作品不受影响。

- **整库范围**的强制重跑是**刻意不提供**的：它会让已经改好名的作品**再多出一份按原名的硬链接**，重命名阶段于是多出 `xxx (2).mkv` 后缀 —— 越点越乱。运行弹窗里**没有整库强制重跑的开关**，应用固定以 `force=false` 调用；命令行直接传 `force=true` + 整库范围（`scope.mode="full"`，默认值）会得到 **400**：`整库强制重跑已停用：force 只允许配合 scope.mode='folder'（单个作品）使用。要重做作品，请到「作品记录」里删除对应作品的记录，下次运行时这些作品会自动补做，其余作品不受影响。`
- **要重做单个作品，走两条正道之一**：① 「**作品记录**」页（左侧栏入口，或媒体库卡片上的按钮）→ 勾选 →「**立即重命名**」（只重命名、**不建链**）；② 在同一页里**删掉记录** ⇒ 下次运行自动补做（重新建链 + 重命名），其余作品不受影响。
- `force=true` **仍可用于单个作品**（`scope.mode="folder"`，「立即重命名」内部就是这么调的）；只是**整库**范围不接受它。
- 详见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §6.4、[`docs/contracts/API.md`](../contracts/API.md) §3.9 与 §3.12。

### 39. 删除作品记录会删掉我的下载文件吗？

**一句话答案**：**不会。** 删除只动**目标目录**（媒体库侧），源下载目录**一个字节都不动**。

- 硬链接只是指向同一份数据的**另一条目录项**；删掉目标那条，源目录那个名字还指着同一份数据，**数据一个字节不少**。
- 删除执行的是"删三处"：① `link_records` 里这些作品的行（建链阶段的判据）；② 本库重命名缓存里的同名条目（**不清它，下次运行会打印 `Skipping folder: … (already processed at …)`，看起来像"删了没生效"**）；③ 目标目录里的**整个作品文件夹**（符号链接只删链接本身）。
- ⚠️ **但有三件事必须知道**：① 目标里那个作品文件夹**整个被删掉、无法撤销**；② 目录里"**不是本应用建立的硬链接**"的文件（`st_nlink < 2`，通常是你自己放进去的）会被**一并删掉** —— 确认框会列出"非硬链接文件数"并在大于 0 时显著警告；③ 删除走**一次弹窗确认**（不需要勾选确认框）：先 `dry_run=true` 预演（磁盘一个字节不动）把清单摆给你看，你在弹窗里点「确定删除」即执行（请求带 `confirm=true`）。
- 详见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §6.4、[`docs/contracts/API.md`](../contracts/API.md) §3.11。

### 40. 两个媒体库用同一个下载目录，会互相影响吗？

**一句话答案**：**不会互相影响。** 前提是每个库有**自己的账本** —— 判据是「**本库** + 同 `source_dir` + 同 `target_dir` + 同体积」，不是全局一份记录。

- **怎么做到的**：判据存在**每库自己的账本**里（数据库表 `link_records`，唯一键 `(library_id, folder)`）；`hard_links.log` **照写**（兼容与审计），跳过判断不看它。
- 所以：两个库指向同一源目录、各自指向不同目标目录 ⇒ **各建各的**，互不影响；同一库换目标目录 ⇒ 原来记录的目标目录对不上 ⇒ **重跑一遍**。
- ⚠️ **注意**：如果这本账是**空的**（换了数据卷、清了 `data/`）⇒ 第一次**全量**运行会把每个作品**重新建链一次**；已在目标里改过名的文件会以**原名**再链一份（同一 inode 的第二个目录项），重命名阶段于是多出 `xxx (2).mkv`。**不丢数据**，但会多出重复文件名。建议：用**新库**、或先清空目标目录、或逐作品处理。
- 顺带记住**账本的语义**：它是**作品级**的，**不保证文件级完整性**；你在目标目录里的**手动增删改一律保留**、不会被自动"修复"；「作品记录」里两本账的差集（`rename_missing` / `rename_only`）**只做提示，永不自动修复**。
- 详见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §6.4 / §6.5、[`docs/contracts/API.md`](../contracts/API.md) §3.10。

### 41. 作品太多，怎么在「作品记录」里快速找到某一个？为什么搜不到？

**一句话答案**：用页面顶部的**搜索框** —— 它拿你输的字做**子串**匹配，只跟**作品名**（源目录里的**一级文件夹名**）比，**ASCII 大小写不敏感**。搜不到多半是这四种：搜的是改名后的名字、库选错了、把 `%` / `_` 当通配符用了、或这个作品压根没有记录。

- ⚠️ **搜索比的是"源目录里的原名"，不是目标里改名后的名字。** 「作品」列显示的是一级文件夹名，改名不会让它变 —— 拿**源文件夹名**里的几个字去搜。
- **`%`、`_`、`\` 都是字面字符**，不是通配符：搜 `%` 只会找到名字里真有 `%` 的作品。所以**别写 `%作品%`**，直接敲名字里的几个字即可。
- **只在当前选中的那个库里搜。** 从媒体库卡片进来时**库选择器已经预选**成那个库；要看别的库就在**库选择器**里直接切换（切换会**清空已勾选的作品**）。
- **不搜**目标路径、作品**内部**的文件名、时间。
- 清空搜索框后看信息行的「**本库共 M 条**」：**M 是 0** 就说明这个库还没有记录（跑一次「手动执行」后已建链的作品才会出现在这里），不是搜错了。
- 找不到具体作品时的完整排查见 [`docs/guides/TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 场景 30；页面各部位说明见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §6.5。

### 42. 我删除了某一张海报 / 某个文件，为什么下次运行没有补回来？

**一句话答案**：因为账本是**作品级**的，不是文件级 —— 记录只说明"这个作品做完了"，应用**不会去数目标目录里少了哪个文件**，所以普通运行照样跳过它。

- **想让它回来，两条正道**：① 在「作品记录」里**删掉该作品的记录** ⇒ 下次运行**自动重新建链 + 重命名**（⚠️ 删记录会**连带删掉目标里整个作品文件夹**，源下载目录不动）；② 只想重新排一次名字 ⇒ 勾选它点「**立即重命名**」（只重命名、**不建链**）。
- ⚠️ **别用单作品 `force=true` 来"补文件"**（接口：`POST /api/libraries/{id}/run` + `scope.mode="folder"`）：它会让建链阶段把**已经改过名的文件按原名再链一份** —— 目标里同一个 inode 于是有**两个目录项**，重命名阶段再多出 `xxx (2).mkv`，`目标目录现有 N 个文件` 会从 2 变 4（见 [`docs/meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-9）。它只适合"目标目录已经是空的/残缺的"这种排查场景；真要重做就走 ①。
- **整库 `force` 已停用**（返回 400），原因见第 38 问。
- 这是**刻意**的：你在目标目录里的**手动增删改一律保留**，应用不会"顺手"帮你补回来或改回去。
- 详见 [`docs/guides/USER_GUIDE.md`](USER_GUIDE.md) §6.5 / §11.4。
