# 使用指南（WebUI）

> **本文解决什么问题**：教你在网页上把这件事跑起来 —— 第一次登录、看懂仪表盘、**建好媒体库**、跑任务、看日志、排查失败、改设置。
> 面向不懂代码的用户：你**不需要**会写命令，全部在浏览器里完成。
>
> 还没装好 → [`DEPLOYMENT.md`](DEPLOYMENT.md)（装、卷、端口、备份、PUID/PGID 都在那里）。
> 想问"为什么不复制文件""为什么没重命名"这类原理问题 → [`FAQ.md`](FAQ.md)；报错怎么修 → [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)。

**页面地址**：`http://<你的宿主机IP>:18081`（默认端口 `18081`）
**页面结构**：仪表盘 / 媒体库 / 作品记录 / 任务 / 设置（左侧导航）

**命令标注**：本文绝大多数操作**不需要命令**。少数可选的高级操作会标注【宿主机】（SSH 登录宿主机执行）或【容器内】。

> 📌 下文出现的 `/vol1/1000/...`、`192.168.1.100` 都是**示例值**（换路径/换环境时改成你自己的）。
> 容器内路径 = 宿主路径，所以这里填的就是宿主机上的真实路径 —— 见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §0 与 §2。

## 1. 第一次进来：创建管理员与登录

打开 `http://<你的宿主机IP>:18081`，会出现两种情况：

### 情况 A：还没创建过管理员

页面显示「创建管理员」。填：

- **用户名**：随便取（如 `admin`）；**密码**：**至少 8 位** —— 这是你以后进后台的唯一凭据，用强一点的。

点确认 → 自动登录 → 进仪表盘。

> 💡 如果你在 `.env` 里填过 `ADMIN_USERNAME` / `ADMIN_PASSWORD`，容器首次启动时已经建好账号，那就走情况 B。

### 情况 B：已经有管理员

输入用户名密码登录。

**登录后立刻做这三件事**：

1. **改密码**：设置页 →「修改密码」→ 当前密码 + 新密码（≥ 8 位）。
   保存后**当前会话会立即失效**，页面自动回到登录页，用新密码重新登录即可；旧密码填错会在「当前密码」输入框下红字提示「当前密码不正确」，不会把你踢下线。
   若你曾用 `.env` 的明文口令初始化，改完密码后把 `.env` 里 `ADMIN_PASSWORD` 那行**删掉**（那文件里存明文口令不安全）。
2. **复制 hook token 与回调命令**：设置页 →「回调 / Hook」→ 点复制，一会儿要粘进 qBittorrent（§9）。
3. **看一眼系统信息**：设置页 →「系统信息」，确认健康检查**四项**（`db` / `data_dir` / `processors` / `config`）全为 ✅，并确认「挂载判定」显示源与目标在**同一个挂载**。

> ⚠️ **不要用「源/目标 `st_dev` 相同」当判据**：内核 `linkat(2)` 比较的是**挂载身份**，两个独立 bind 的
> `st_dev`、`fsid`、btrfs 子卷号可以**完全相同**而 `link()` 照样 `EXDEV`。判据是 `findmnt -T` 的挂载点相同，
> 或预检里**实证探针**成功（§3.1）。

### 登录相关的小知识

- 登录状态存在浏览器 Cookie（`mlm_session`）里，有效期内不用反复登录；
- **换浏览器、清 Cookie、无痕窗口** → 要重新登录；
- 所有人都突然被登出：多半是 `/data/secret.key` 丢了或被换了（会话签名密钥变了）。**密码没变，重新登录即可**；
- 忘记密码 → 见 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 场景 11（有重置步骤）。

## 2. 仪表盘：每张卡片是什么意思

仪表盘（`#/dashboard`）回答一个问题：**"现在一切正常吗？"**

### 2.1 任务统计卡片

| 卡片 | 显示什么 | 看到多少算正常 |
|---|---|---|
| **排队中（queued）** | 已入队、还没轮到的任务数 | 平时 `0`；刚下载完一个种子后短暂变 `1` 正常 |
| **执行中（running）** | 正在跑的任务数 | `0` 或 `1`。**永远不会超过 1**（队列串行） |
| **近 24 小时成功** | 最近一天成功执行的任务数 | 数字变大 = 在正常工作 |
| **近 24 小时失败** | 最近一天失败的任务数 | **持续 > 0 就要去任务页查原因**（最常见是跨挂载 / 权限） |

### 2.2 队列状态卡片

| 字段 | 含义 |
|---|---|
| 正在执行 | 当前任务的 id（点它可跳详情）。空闲时显示「空闲」 |
| 排队数量 | 等待执行的任务数 |

> 队列是**串行**的：一次只有一个任务在跑。因为建链实现会"读-改-写整份日志文件"，两个任务同时跑会互相覆盖（[`../contracts/BASELINE.md`](../contracts/BASELINE.md) A12）。所以"排队 3 个"是正常的，它们会依次跑完。

### 2.3 媒体库概览卡片

| 字段 | 含义 |
|---|---|
| 媒体库总数 | 你建了多少条规则 |
| 已启用 | 其中启用了多少（**未启用的库不会被回调或扫描命中**） |

每个库还会显示**最近一次任务的状态**（成功 / 失败 / 跳过 / 从未运行）。这是最快的"这个库健康吗"指标。

### 2.4 近期任务列表

最近若干条任务：id、所属媒体库、触发来源、状态、时间。**点任意一条进任务详情**。

触发来源（`trigger`）：

| 来源 | 意思 |
|---|---|
| `hook` | qBittorrent 下载完成后自动回调触发（qBittorrent 设置里的「运行外部程序」） |
| `scan` | 定时目录扫描补偿发现的 |
| `manual` | 你在网页上手动点的「手动执行」 |
| `retry` | 你对一条失败/取消的任务点了「重试」 |

### 2.5 待办看板

**它是什么**：一块**全局**待办清单，回答"有没有什么事值得我处理一下？"。任务跑完时，若有"值得你知道、但**不该打断任务**"的情况，就在这里记一条；看完在**行首点一下圆圈**即可打钩。
**它不弹窗、不拦截、不阻断任何任务** —— 放着不管，任务照样跑完。

**六种待办**（每条都标注来源媒体库与任务号，点任务号可跳详情）：

| 种类 | 严重度 | 什么时候出现 |
|---|---|---|
| **硬链接创建失败**（`link_failed`） | 🔴 错误 | 源文件没能在媒体库里建出硬链接（跨挂载、权限、目标已是别的文件……）。**这个最要紧**：媒体库里没有这个文件 |
| **冲突文件已加后缀保留**（`rename_suffix`） | 🟡 警告 | 改名时目标名已被占用（同一次运行里更早的文件，或目标盘上本来就有的同名文件），L2「防丢」按**体积**判定后加了 ` (2)`、` (3)`… 后缀保留 —— **没有覆盖、也没有丢文件**。（"新来的自己加后缀"与"原有文件让位"是同一问题的两条路径，看板**只留一条**；让位那条的详情里「原因」是 `displaced`，并标出「让位文件（原名）」与「让位后文件名」。）想少看到后缀：清理目标目录里的重复版本或调命名模板 |
| **保留原名（未解析出集数）**（`unresolved_episode`） | 🟡 警告 | 名字引用了集数但规则全不命中 ⇒ 保留原名、没有改名 |
| **作品结构不可识别（未改名）**（`unscoped_works`） | 🟡 警告 | 子目录模式下作品目录里**没有可接受的「季目录」**、文件直接躺在作品目录里（扁平结构）—— 重命名阶段找不到作用域，**整个作品被跳过：不改名、也不报错**。处理：把文件放进「作品名/Season N/」，或把处理器的 `file_scope` 改成 `title` |
| **源目录完整性核对未通过**（`source_integrity`） | 🔴 错误 | 源目录在任务执行期间被外部改动过（`source_integrity.ok=false`，详情列出被动的路径） |
| **任务失败**（`task_failed`） | 🔴 错误 | 任务以 `failed` 结束（含"一个都没建成"这种程序化失败），详情里有错误文本 |

**怎么用**

- **四个筛选**：状态（未完成 / 已完成 / 全部）、种类、媒体库、**作品**；**默认只显示「未完成」**。作品框匹配的是**待办自己的文字**（问题摘要、详情里的目录/路径、去重键，任一处包含即列出），所以是**朴素子串**（搜 `Work 1` 也会列出 `Work 12`）—— 台账里**没有作品字段**（[`../meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-10）；它**不影响**顶部统计与「一键检测」。
- **翻页**：一页 20 条，底部「上一页 / 下一页」与「第 X / Y 页（共 N 条）」。
- **行首圆圈 = 打钩**：点一下出现**绿勾**、整行变灰（已完成），再点恢复。**这不是删除** —— 数据一行都没少。刚勾掉的那行会**留在原地变灰**直到你翻页或刷新，"刚勾掉的是哪几条"一眼可见。
- **一键检测**：核对"记录里的文件路径"与磁盘实况，把**其实已经不用管**的待办列成候选（默认全选、可取消），证据栏写清"为什么认为它不用管了"，点「标记完成（N）」才真的打钩 —— **打钩前还会再核对一遍**，实况变了就跳过。⚠️ 只有**记录里带得出单个文件路径**的种类能自动检测（`link_failed`、`rename_suffix`、`unresolved_episode`）；`task_failed`、`source_integrity` 与 `unscoped_works` 描述的是一次任务 / 整棵树，只能人工判断 —— 弹窗会如实列出，别把"没检测出来"当成"没问题"。
- **展开详情**：点某行「详情」，看原始路径与错误文本（长路径会换行）。
- **重复出现会合并**：同一问题（同种类 + 同一目标）反复出现**不会刷屏**，而是「出现次数」+1、刷新「最近」时间（「首次」不动）；**打过钩之后又发生会新开一条** —— "出现过几次、每次什么时候"永远查得到。
- **看板是全局的**：不分局域网里哪台机器、哪个库。
**不想要某类待办？** 设置项 `todo_kinds`（逗号 / 顿号分隔的 kind 列表，留空 = 全部启用），例如只留最要紧的两种：`link_failed,rename_suffix`。写错的种类名**会被忽略**（不会因此把看板清空）；关掉的种类**连记都不记**（不是"记了但隐藏"），看板底部会提示当前关掉了哪些。

## 3. 建媒体库前的 5 分钟自检

**这一步能省掉你 90% 的排查时间。**

**【宿主机】**

```bash
# 1) 源与目标必须在同一个挂载 —— 两条输出的 TARGET（挂载点）必须相同
findmnt -T /vol1/1000/Download/qbittorrent -o TARGET
findmnt -T /vol1/1000/Library -o TARGET

# 2) 看一眼源目录里的一级文件夹（这决定了你库的"范围"）
ls -1 /vol1/1000/Download/qbittorrent/Bangumi
ls -1 /vol1/1000/Download/qbittorrent/Movie

# 3) 番剧：确认每个作品下面真的有 "Season NN" 这种季文件夹
ls -1 "/vol1/1000/Download/qbittorrent/Bangumi/Show A"

# 4) 目标媒体库根目录可写
ls -ld /vol1/1000/Library
```

> 🚫 **别用 `stat -c '%d'`（`st_dev`）判断"能不能建硬链接"**：同一个 `st_dev` 的两个独立 bind 之间
> `link()` 依然 `EXDEV`（内核比较**挂载身份**）。`st_dev` 不同 ⇒ 一定不行；`st_dev` 相同 ⇒ **不能证明**可以。
> 唯一可信的是 `findmnt -T` 的挂载点相同，或一次真实的 `ln` 探针（§3.1）。

**要记住的两条结构要求**（它们直接决定"重命名会不会发生"）：

| 库类型 | 目录结构要求 | 不满足会怎样 |
|---|---|---|
| **番剧（Bangumi）** | 源侧要是 `<作品名>/Season 1/<视频文件>`。季文件夹名**必须恰好**是 `Season <数字>` | 不是的话季目录被忽略 → **只建硬链接、不重命名**。`Season 1 (2018)`、`Season1`、`SP`、`Specials`、`S01` 都不行 |
| **电影（Movie）** | `<电影名>/<视频文件>`（文件直接放在一级文件夹里） | 文件在子目录里 → **不重命名**（但会被建硬链接） |

扩展名白名单：`.mkv` `.mp4` `.ass`（**大小写敏感**，`.MKV` / `.SRT` 不在内）。**不在白名单里的文件仍会被建硬链接**，只是不重命名 —— 硬链接与重命名是两套不同的白名单。

### 3.1 点了媒体库页 / 库编辑页的「预检」之后看到什么

「预检」会做一串检查，最关键的是 `same_filesystem`（"源与目标在不在同一个挂载"）。它是**三态**：

| 值 | 含义 | 下一步 |
|---|---|---|
| `true` | 能建硬链接：**实证探针**成功（从源目录取一个已存在的普通文件、链到目标再删掉，**源目录零写入**），或只是「挂载 ID 预筛」通过（那时 `warnings[]` 注明「仅据挂载 ID；该判据必要不充分」＝**未实证**） | 放心跑 |
| `false` | **已证实**建不出（实证 `EXDEV`）⇒ 预检标红（`ok=false`，`errors[]` 里是中文原因） | 把下载根与媒体库根放进**同一条 bind**（`MEDIA_ROOT`），见 [`COMPATIBILITY.md`](../contracts/COMPATIBILITY.md) §2 与 [`DEPLOYMENT.md`](DEPLOYMENT.md) §3 |
| `null` | **判不了**（源树里找不到可试链的普通文件，又读不到挂载 ID）⇒ **不是**失败 | 任务仍可运行，真跑起来才知道；见 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 场景 21 |

> 📌 **`false` 会让预检报失败，但不会阻止你启动任务**：预检把它们记进 `errors[]` / `ok=false`（一眼看见问题），
> 而**跑任务**时同一判据只在 `Task.result.warnings[]` 里留一条并继续尝试。最终结论由执行前后的**逐文件源完整性核对**给出：真有文件没链上就是 `link_failed`、任务结论是失败，**绝不会**静默复制一份来"凑成功"。

> 📌 **预检还包含「权限」这一组**（响应里的 `permissions`）：以应用运行身份实测源目录可读可进入、目标目录（或其最近已存在的祖先）可写。`permissions.ok=false` 会并入 `ok=false` 与 `errors[]`。这一组**不需要你点按钮** —— 建库/改库保存时已经自动跑过同一套实测；过不了会弹「保存失败」明细窗（每条：原因 + 处理，`处理` 第一条是调整 PUID/PGID），必须点「确定」关闭且不会写入数据库。预检页面显示它只是让你能看到完整证据。排查步骤见 [`FAQ.md`](FAQ.md) 第 43 问。

## 4. 新建媒体库：三个完整例子

进「媒体库」页 → 点右上角「新建媒体库」。

### 4.0 先理解每个字段

| 字段 | 填什么 | 关键说明 |
|---|---|---|
| **名称** | 你自己看得懂的名字，如「番剧」 | 不能重名（会被拒绝） |
| **类型** | **自由文本**，如 `番剧`、`4K电影` | 只是**展示与统计用的标签**：不决定任何行为、没有枚举约束 |
| **处理器** | 下拉选一个（内置三个：`hardlink_only` / `bangumi` / `movie`） | **决定实际做什么**，见 §5。下拉里是 `processors/*.yaml` 里的**全部**处理器，你可以自己加 |
| **启用** | 开 / 关 | 关掉的库**不会**被回调或扫描命中（但可手动跑） |
| **源目录** | **容器路径**，如 `/vol1/1000/Download/qbittorrent/Bangumi` | 必须与目标目录在**同一个挂载**内（跨挂载建不了硬链接） |
| **目标目录** | **容器路径**，如 `/vol1/1000/Library/Bangumi` | 必须与源目录在**同一个挂载**内；**不能与源目录相同或互相包含** |
| **匹配分类 / 标签 / 路径前缀** | qBittorrent 的分类名（如 `ban`）/ 标签名 / 内容路径前缀 | 三项是**"与"**关系，**至少填一项**；详见 §4.4 |
| **孤儿清理** | 开 / 关 | ⚠️ 开着时会**删除**"源已不存在"的目标硬链接文件夹，见 §8.5 |
| **日志文件** | **只填文件名**，如 `bangumicache.log` | 留空会**按库唯一分配**（先取处理器登记的日志名，被占用时加 `-2`/`-3`…，§5.6）；都在 `/data/logs/` |
| **权限模式** | 开 / 关（**默认关**） | ⚠️ 真实开关：关闭时一个 `chmod` 都不做；开启后把**目标库**（含被跳过的旧作品）改成 `0777`。因为硬链接共享 inode，会**连带改掉下载源文件的权限位**，所以从关到开会**二次确认**。见 §8.9 |

**路径要注意**：这里填的是**容器内路径**；单挂载形态下**容器路径 = 宿主路径**，所以填的就是宿主机上的真实路径。容器里只有一条共同父挂载 `/vol1/1000`（外加 `/data`），**没有** `/downloads`、`/library` —— 填 `/downloads/...` 会被拒绝（[`DEPLOYMENT.md`](DEPLOYMENT.md) §2）。

> **媒体库文件夹不写死**：下载根下的**任何**子目录都能建库（`Anime-CN`、`Movie-4K`、`Documentary`……），只要它与目标目录在**同一个挂载**上（§3）。处理器**类型**不受限。

**校验失败长什么样**（统一是 `422` + 中文字段级错误，没有 400 的"类型与处理器搭配非法"）：

```json
{"detail":[{"loc":["body","processor_id"],
            "msg":"处理器「bangumi-x」不存在。可用处理器：bangumi、hardlink_only、movie。"}]}
```

### 4.1 例子一：番剧库（Bangumi）

**场景**：qBittorrent 分类 `ban` 的番剧，源 `/vol1/1000/Download/qbittorrent/Bangumi` → `/vol1/1000/Library/Bangumi` 给 Emby 用，按 `S01E01` 改名。

| 字段 | 值 |
|---|---|
| 名称 / 类型 | `番剧` / `番剧`（自由标签，写什么都行） |
| 处理器 / 启用 | `bangumi` / ✅ 开 |
| 源目录 → 目标目录 | `/vol1/1000/Download/qbittorrent/Bangumi` → `/vol1/1000/Library/Bangumi` |
| 匹配分类 | `ban`（qBittorrent 种子列表"分类"那列写什么就照抄，注意大小写） |
| 匹配标签 | （留空） |
| 匹配路径前缀 | `/vol1/1000/Download/qbittorrent/Bangumi`（兜底：某个种子忘了设分类也能命中） |
| 孤儿清理 / 权限模式 | 建议先 **关** / **关**（默认，见 §8.5、§8.9） |
| 日志文件 | 留空（自动变成 `bangumicache.log`） |

**建完先点「预检」**：真正跑之前检查源存在、目标父目录存在、**源与目标同挂载**、目标可写。全绿再跑。

> 📌 **权限问题在建库/改库时就已经拦了一次**：点「保存」时后端会用**应用自己的运行身份**实读源目录、在目标目录真写一个临时文件再删掉；不可读/不可写会直接报错（400，文案里带当前 uid/gid 与「常见问题」第 43 问入口），不会等到第一次任务才发现 Permission denied。所以「预检」按钮的价值主要在 `os.link` 实证与完整诊断，**不依赖用户点它**。

**第一次跑完要检查**：① 去 `/vol1/1000/Library/Bangumi/Show A/Season 1/` 看文件名是不是变成 `Show A S01E01.mkv`；② 用 `ls -i` 对比下载侧与媒体库侧的 inode 号是否**相同**（相同 = 硬链接生效，不是复制）；③ 名字**没变** → 对照 §3 的结构要求（季文件夹名 / 扩展名 / 层级）或看 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 场景 15。

### 4.2 例子二：电影库（Movie）

**场景**：qBittorrent 分类 `movie` 的电影，源 `/vol1/1000/Download/qbittorrent/Movie` → `/vol1/1000/Library/Movie`，一个电影一个文件夹，文件夹名就是电影名。

| 字段 | 值 |
|---|---|
| 名称 / 处理器 | `电影` / `movie` |
| 源目录 → 目标目录 | `/vol1/1000/Download/qbittorrent/Movie` → `/vol1/1000/Library/Movie` |
| 匹配分类 / 路径前缀 | `movie` / `/vol1/1000/Download/qbittorrent/Movie` |
| 日志文件 | 留空（自动变成 `moviecache.log`） |

**结果会是什么样**：源侧的 `流浪地球2/流浪地球2.2023.2160p.WEB-DL.mkv`（最大的那个）、`….ass`、`说明.txt`，跑完之后 `/vol1/1000/Library/Movie/流浪地球2/` 里是 `流浪地球2.mkv`（文件夹名 + 后缀）、`流浪地球2.ass`、`说明.txt`（不在 `.mkv/.mp4/.ass` 白名单，不重命名但会被建硬链接）。

**必须知道的两条电影规则**：① **每个后缀只重命名体积最大的那一个文件**（同目录两个 `.mkv` 时只有大的改名，小的保留原名）；② 只处理**一级文件夹的直接子文件**，子目录（如 `Extras/`）里的文件不重命名。

> ✅ **这里不会丢文件**：若目标里**已存在**同名文件而另一个文件也要叫这个名字，引擎先比**体积** —— 新来的更大 ⇒ 原有的改名**让位**成 `流浪地球2 (2).mkv`（**不删除**，计入 `displaced_targets`），新来的拿干净名；否则新来的自己加 ` (2)`。同一次运行里两个源文件抢同一名字同理（**最大的拿干净名**）。两种都计入 `name_collisions`（事实清单）与 `renamed_with_suffix`，明细见 `samples.*`。
> ⚠️ **刻意不静默覆盖**：`os.rename` 默认在目标同名时会 POSIX 静默覆盖（[`../contracts/BASELINE.md`](../contracts/BASELINE.md) L4 记录了这条规则是怎么被一次真实事故逼出来的）。

### 4.3 例子三：自定义库

"自定义"的含义：不必局限于三个内置处理器，**你可以自己写一个**（命名方式、接受/拒绝目录正则、后缀白名单全可配），再让媒体库用它。

**场景 A：只想建硬链接，不重命名（最常用）** —— 国漫/剧集已经命名整齐，只想在媒体库里出现一份：

| 字段 | 值 |
|---|---|
| 名称 / 处理器 | `国漫（只建链接）` / **`hardlink_only`** |
| 源目录 → 目标目录 | `/vol1/1000/Download/qbittorrent/Anime-CN` → `/vol1/1000/Library/Anime-CN` |
| 匹配分类 / 标签 / 路径前缀 | `anime-cn` / `国漫` / `/vol1/1000/Download/qbittorrent/Anime-CN` |
| 日志文件 | 留空（自动生成；中文库名会被折成一串 `-`，建议手填一个 ASCII 文件名） |

**结果**：应用**原封不动**地把源侧的目录层级与文件名做成硬链接（层级逐字节保留），**一个名字都不改**。

**场景 B：复制一个内置处理器，改成自己的规则** —— 想让 `4K电影` 用电影规则的变体（多拒绝几个目录、额外接受 `.srt`）：① 「处理器」页 → `movie` → 点「复制」；② 改 `id`（如 `movie-4k`）、把 `.srt` 加进 `extensions`、往 `reject_dirs` 加你的特典目录正则；③ 保存后回「媒体库」页新建库，**处理器选 `movie-4k`**，源 `/vol1/1000/Download/qbittorrent/Movie-4K` → 目标 `/vol1/1000/Library/Movie-4K`。完整分步见 **§5.9**。

> 只想**沿用**电影规则、不做改动？直接选内置 `movie`。想确认"新处理器与最朴素的旧口径产出是否一模一样"？用 `legacy` 预设（§5.2）。

### 4.4 匹配规则详解（为什么我的种子没被触发）

回调触发时，应用遍历**所有已启用**的库，对每个库检查三项：

| 检查 | 何时算通过 | 留空时 |
|---|---|---|
| 分类 | 种子的分类**等于**库的「匹配分类」列表里的某一项 | 不检查这一项 |
| 标签 | 种子的标签与库的「匹配标签」列表**有交集**（忽略大小写；分隔符是逗号、中文逗号、顿号、分号或空格） | 不检查这一项 |
| 路径 | 种子的内容路径**落在**库的「匹配路径前缀」中的某一项之下 | 不检查这一项 |

**三个条件是"与"（AND）**：填了几项就都得成立；任何一项不通过，这个库就被跳过。⚠️ 注意一种容易踩的：库填了标签条件、而回调**没带标签**时算"不通过"，**不是**"跳过这一项"。

**三条铁律**：① **三项全空 = 不匹配**（刻意设计，防止"什么都没配"的库把整个下载目录抓走）；② 命中多个库 → **全部入队**（依次执行）；③ `启用 = 关` 的库**完全不参与匹配**（但可手动跑）。

> 📌 **路径条件永远按「本应用容器内」的路径判断**。如果 qBittorrent 容器里的下载路径不一样（例如它是 `/downloads`，本应用是 `/vol1/1000/Download/qbittorrent`），先在设置页 §8.8 的 qBittorrent 卡片里配一条「回调路径映射」，回调会先换算再匹配；没配映射时 `/downloads/...` 在应用里不存在，会表现为"分类对了但路径对不上 / 退化为全量"。

> ⚠️ 这三项条件**只用于 qBittorrent 回调**（WebUI 建库页在「匹配条件」标题下也有同样说明）：「手动执行」与「目录扫描」**不看**这些条件，会处理源目录下符合规则的全部内容。
> 记住方向：**条件填得越多 = 命中越严**。"分类是 ban 但下到了 `Movie` 目录"的种子**不会**命中番剧库 —— 这在你想把两个番剧目录分开时有用，但也常常就是"为什么没触发"的答案。
> **回调返回里的 `ignored_details` 是排查神器**：逐个列出**没命中**的库并给中文原因。`matched: 0` 时先看它；逐条对照见 §9。

## 5. 处理器（processor）：媒体库的重命名规则

**一句话**：一个**处理器**就是一套"怎么改名"的规则；媒体库只是"用哪套规则、处理哪两个目录"。规则**全部可配置**（WebUI 或 `/data/config/processors/*.yaml`），不写死在代码里。

### 5.1 一个处理器由四部分组成

| # | 部分 | 作用 | 例子 |
|---|---|---|---|
| 1 | **命名方式**（`naming`） | 新文件名怎么拼：段序列 + 具名表达式 | `{title}` ` S` `{season,pad:2}` `E` `{episode,pad:2}` `{suffix}` ⇒ `Show A S01E01.mkv` |
| 2 | **接受目录正则**（`accept_dirs`） | 标题文件夹下哪些子目录算"季目录"（并从中取季号） | `^Season (\d+)$`，`season_group: 1` |
| 3 | **拒绝目录正则**（`reject_dirs`） | 命中就**整棵子树跳过** | `(?i)^(SP\|CM\|OP\|ED)$`、`(?i)^特典$` |
| 4 | **接受后缀**（`extensions`） | 哪些文件参与重命名（**大小写敏感**） | `[.mkv, .mp4, .ass]` |

另外两个决定行为的字段：`kind`（`rename` / `hardlink_only`）与 `selection.per`（`file` = 每个匹配文件都改名；`extension` = 同后缀只留体积最大的那个，电影用）。再加**每库一条日志**（`log_file`，见 §5.6）。

### 5.2 内置三个处理器与两个预设

| id | 名称 | kind | 说明 |
|---|---|---|---|
| `hardlink_only` | 只建硬链接 | `hardlink_only` | 不改名；由 `app/processors/hardlink.py` 执行 |
| `bangumi` | 番剧 | `rename` | 番剧规则（`Season NN` + 集数按 **9 条有序规则**识别：`第N集` / `Episode N` / `SxxExx` / `[NN]` / `EP N` / `#N` / `- N` / `E N` / 裸数字 → `S01E01`；认不出集数就保留原名） |
| `movie` | 电影 | `rename` | 电影规则（`<文件夹名>.<后缀>`，每个后缀只留最大者） |

内置处理器**不可删除**，只能重置（处理器页「恢复默认」）。两个预设：

| 预设 | 含义 |
|---|---|
| `default` | 推荐默认值：**相对 `legacy` 的四处增量** —— 番剧与电影各多一份拒绝目录规则（①②）、番剧「集数兜底」**留空**（认不出集数就**保留原文件名**，③）、番剧集数规则是 **9 条带边界约束的有序规则**（④） |
| `legacy` | **最朴素的旧口径**：`reject_dirs: []` + 「集数兜底」是字符串 `None` + **两条宽松老规则**（含大小写敏感的后缀白名单、没有集数号也照样改名成 `ENone`）。被冻结成**黄金值**，由 `tests/test_processor_engine.py` / `tests/test_bangumi_episode_rules.py` / `tests/test_rename_extensions.py` 守护 |

四处的逐项取值（拒绝名单、`episode_fallback`、9 条正则与正反例）见 [`../contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3 与 §3.2 —— 那里是唯一真源，本文不抄第二份。

> ⚠️ **升级镜像不会自动改已存在的处理器**（它们是首次播种后独立存在的）。想让已存在的番剧处理器"认不出就保留原名"、并用上新集数规则，二选一：
> ① 改 `/data/config/processors/bangumi.yaml`（`episode_fallback:` 留空；`episode_patterns` 换成 [`PROCESSORS.md`](../contracts/PROCESSORS.md) §3 那 9 条 —— 配置文件是**整份规格**，改前先照 §3 的 YAML 示例核对字段）；WebUI 与文件双向同步，默认 5 秒一轮生效；
> ② 处理器页「恢复默认」选 `default`（会一并覆盖你对它的其它自定义改动）。
> ⚠️ **「集数兜底」的"留空"**：清空输入框、配置文件写 `episode_fallback:`（YAML 空值）、或库里早先存下的空串，都按"没配兜底"处理（认不出集数就**保留原文件名**）；只有**非空字符串**才算兜底字面量。**新建**的处理器默认留空（`null`）。
> ⚠️ 两个预设都**不会**拒绝发布组/压制组前缀（`[ANi]`、`[VCB-Studio]` 不在范围内）。想拒绝什么，自己往 `reject_dirs` 里加。

### 5.3 硬链接部分由谁执行

**由应用自己的原生实现执行**（`app/processors/hardlink.py`）：打印文案、日志行格式、扫描顺序都被**冻结成黄金值**，由 `tests/test_hardlink_native.py` 用「同一棵树、A 组五条场景断言」锁死。容器自带全部执行体，不依赖宿主上的任何东西，镜像可以原样搬到别的设备。

### 5.4 在哪儿改规则（WebUI）

侧边导航 →「**处理器**」（`#/processors`）：**列表页**显示每个处理器的 id / 名称 / kind / 是否内置 / 被哪些媒体库引用；**编辑页**（`#/processors/{id}`）四大块与 §5.1 一一对应 —— ① 命名方式（可视化"段"列表 + **实时预览** + 独立的「命名表达式」区 + 顶部「命名模板」框，见 §5.4.1）；② 接受目录正则（可增删 `{pattern, season_group}` 行，会显示正则能否编译）；③ 拒绝目录正则（可增删 `{pattern}`，命中即整棵子树跳过）；④ 接受的后缀名（chips，必须以 `.` 开头）。顶部两个按钮：**「保存」**（全量替换）与**「恢复默认」**（二次确认，可选 `default` / `legacy`）。

> ⚠️ **改了处理器，所有用它的媒体库都跟着变**（下次运行生效），改之前先看列表页的引用清单；只想让**某一个库**换命名方式 → 用库编辑页的「本库规则覆盖」（§5.4.2），别动处理器。

#### 5.4.1 命名模板：像 calibre 那样挑字段

「命名模板」是一个文本框，你写什么就按什么拼：

```
[{season}-{episode}] {title}{suffix}      →  [01-01] 作品名.mkv
{title}/{title} - {episode}{ext}          →  作品名/作品名 - 01.mkv（含 / 会把结果落进子目录）
```

- `{名字}` = 该变量当前的值，`{episode:02}` = 补零到 2 位（`{season:02}` 同理）；`{{` / `}}` 是转义的花括号；
- 可用变量就是 §5.5 表里的 12 个，再加你在「命名表达式」里定义的名字（按钮会直接插进光标处）；
- 写错的变量名**会立刻在输入框下面变红**并说明，不用等保存；保存后落库的是**编译结果**（段序列），运行时引擎不依赖模板这个概念。

> 模板与段序列是**同一个东西的两种写法**：处理器编辑器两者都给（同时填时**模板优先**），库级覆盖里只给模板（更简单）。

#### 5.4.2 本库规则覆盖：只给某一个库改规则

库编辑页（`#/libraries/{id}`）的「**本库规则覆盖**」卡片：

- **开关关着** = 完全跟随处理器（保存时提交 `{}`，把已有覆盖清掉）；
- **开关打开**后可逐项覆盖，**没碰的字段照样继承处理器**：命名模板（+ 变量按钮 + 实时预览）、接受/拒绝目录正则（带季号捕获组的那列只对接受规则有意义）、文件作用域（`subdir` / `title`）、本库后缀白名单（优先级**最高**，压过设置页的全局白名单与处理器清单）；
- 校验在保存时做两遍：先看覆盖自己读不读得懂（正则能否编译、变量认不认识），再**合并到处理器规则上**跑一遍完整校验 —— 所以「处理器是 `title` 作用域、你却给这个库写了 `accept_dirs`」这种跨层冲突也会被拦下，并告诉你哪一层冲突。

**什么时候该用它**：「同一个番剧处理器，但某一个库想用方括号命名」「某个库想额外拒绝 `SP` 目录」「某个库只认 `.mkv`」—— 这些都不该去改处理器（那会波及所有引用它的库）。

### 5.5 命名段可用的名字（速查）

| 名字 | 取值 | 例子 |
|---|---|---|
| `title` | 标题文件夹名 | `Show A` |
| `filename` / `stem` / `ext` / `extname` | 原文件名 / 去扩展名 / 带点扩展名 / 不带点扩展名 | `Show A 01.mkv` / `Show A 01` / `.mkv` / `mkv` |
| `season_raw` / `season` | 季号原值 / 补零两位（**无季号时 `season_raw` 是空串，而 `season` 是 `"00"`**；只有 `file_scope=title` 的处理器 `season` 才是空串） | `1` / `01` |
| `episode_raw` / `episode` | 集数原值 / 按 `pad` 补零。所有 `episode_patterns` 都没命中**且没配** `episode_fallback`（空串也算"没配"）时两者都是**空串**；此时若命名引用了它们，该文件**保留原文件名、不改名**（计入 `result.kept_unresolved_episode`，日志一行 `Kept (no episode): …`）。配了兜底就是"已解析"，照旧渲染那个字面量 | `1` / `01` |
| `suffix` | `.ass` 用多段后缀（如 `.chs.ass`），其他文件等于 `ext` | `.chs.ass` |
| `works_dir` / `rel_dir` | 库的 `source_dir` / 作用域目录相对标题文件夹的路径 | `/vol1/1000/Download/qbittorrent/Bangumi` / `Season 1` |

`naming.expressions` 里可以写 Python 表达式（可用 `re`、`os`、`len`、`str`、`int`、`sorted`、`min`、`max`，以及 `zfill` / `splitext` / `basename` / `ass_suffix`）。这是"可拓展、不写死"的代价：**能在配置文件里写表达式，就等于能在容器里执行代码** —— 只有你自己能改 `/data/config/` 时才用它。

> **内部键 `episode_resolved`**（`true` / `false`）：表示"这个文件的集数解析出来了吗"（命中 `episode_patterns` 或配了 `episode_fallback` 都算 `true`）。可用在 `naming.segments[].param` 与表达式右值里；**模板写法 `{episode_resolved}` 也认**。它**不在**变量按钮表里（那是给 12 个常规变量的）。

> **写错变量名会怎样（KI-11）**：**保存期被拦住**（422「段里用了未知变量 {titlee}。可用变量：…」，编辑页下拉框带 **（未知）** 标记、模板框当场变红）；**运行期**（老配置 / 手改 YAML）照旧跑完，但那段**什么都不输出** ⇒ 文件名少一段 —— 会报出来：`unknown_params` 计数 + `samples.unknown_params` + 每文件一条 WARNING + 任务告警汇总。**任务仍算成功**。

### 5.6 每个媒体库一条日志（都在 `/data/logs/`）

| 类别 | 文件 | 作用 |
|---|---|---|
| 硬链接日志 | `hard_links.log` | 建链阶段的**兼容与审计**记录。**只写"记账行"**（体积登记与孤儿目录清理两类）；uvicorn 访问日志、任务日志等**不会**进这个文件。⚠️ **跳过判断看的是每库账本，不是这个文件**（§5.7、§11.3） |
| 每库一条重命名日志 | `<log_file>`，默认取该处理器登记的日志名（`bangumicache.log` / `moviecache.log` / `hardlink_only.log` / 自定义 `<id>cache.log`），被占用时加 `-2`/`-3` | "这个标题文件夹已经重命名过了"（含体积与时间戳） |
| 任务日志 | 数据库（任务详情页轮询） | 你在网页上看到的逐条日志 |

**三条硬规则**：日志**必须**都在 `/data/logs/`，**不允许**分子目录；表单里的「日志文件」**只能填文件名**（含 `/` 或 `..` 会被拒绝）；新建库时文件不存在会建一个空 `{}`，**不会**从任何外部目录导入。完整取名规则与自查命令见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §2.6。

> 📌 `hard_links.log` 的写入者把 `FileHandler` 挂在 **root logger** 上（必须如此，见 [`../contracts/ARCHITECTURE.md`](../contracts/ARCHITECTURE.md) §6.5），而 root 会收到**整个应用**的日志，所以它有一张白名单：只有上面两类行能落进文件。**只过滤、不清理** —— 历史行一个字节都不删；过滤也**不影响**任务详情页与 `docker compose logs`。

### 5.7 配置文件与 WebUI 双向同步（默认 5 秒一轮）

- 规则同时存在于**数据库**（运行时真源）与**文件**（`/data/config/libraries.yaml`、`/data/config/processors/<id>.yaml`）；
- **WebUI 保存** → 同一请求里就把文件原子写好；**你在宿主机上改文件** → 后台每 `config_sync_interval_seconds`（**DB 设置项**，默认 **5 秒**，区间 0–86400；**不是环境变量**）比对一次，发现被外部改动就导入数据库，页面提示「配置文件已从磁盘重新导入」；
- **导入失败**（YAML 语法错、正则编不过、后缀没以 `.` 开头…）→ **数据库不受影响**（继续用旧规则），页面顶部**红色横幅** + 错误详情，**你的文件不会被覆盖**；
- **删除语义**：文件里被删掉的**自定义**处理器 / 媒体库随导入删除；**内置处理器永不删除**；
- 想彻底关掉自动导入：把 `config_sync_interval_seconds` 设成 `0`，之后只在点按钮时导入。

> 布局、冲突仲裁、故障处置见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §2.6；备份与恢复这些文件见 [DEPLOYMENT.md](DEPLOYMENT.md) §7.1 与 §7.5。

### 5.9 新增一类媒体库：从零到跑通（完整步骤）

假设要管 `/vol1/1000/Download/qbittorrent/Documentary`（纪录片），命名用 `<文件夹名>.<后缀>`，但要多拒绝一个 `Extras` 目录、额外接受 `.srt`：

1. **先看最接近的内置处理器**：处理器页打开 `movie`，看 `naming.segments`（应为 `title` + `.` + `extname`）与 `selection.per: extension`；
2. **复制一份**：点「复制」，`id` 改 `documentary`，`name` 改 `纪录片`，`description` 写清来源（如"基于 movie，加了 srt"）；
3. **改规则**：`extensions: [.mkv, .mp4, .srt]`（带点、大小写敏感）；`traverse.reject_dirs` 加 `{pattern: '^Extras$'}`；想在名字里带年份就往 `naming.segments` 插 `{literal: '.'}` + 一个表达式，改完看**实时预览**；
4. **保存**：这一步同时把 `/data/config/processors/documentary.yaml` 写出来；
5. **建库**：媒体库页点「新建媒体库」→ 名称 `纪录片`、类型 `纪录片`、**处理器选 `documentary`**，源 `/vol1/1000/Download/qbittorrent/Documentary` → 目标 `/vol1/1000/Library/Documentary`，匹配条件按 §4.4 填（**至少一项**，别全空）；
6. **预检 + 试跑一个小文件夹**：先点「预检」确认结构 OK，再用「手动执行 → 仅指定一级文件夹」**只处理一个作品**，去任务详情页看日志里的 `Renamed:` 行；
7. **确认无误再全量跑**，然后接进回调（§9）或扫描补偿（§8.4）。

> 全程**不需要写 Python**、不需要改代码、不需要重建镜像。规则改错也不会破坏已有文件：改名只发生在媒体库一侧，源目录应用**代码层从不写**（[`FAQ.md`](FAQ.md) 第 4 问）。

### 5.10 三条别踩的线

1. **不要改媒体库里文件的内容**：硬链接与下载原文件共享同一份数据，原地编辑媒体库那份 = 改下载那份；
2. **不要让两个处理器写同一个 `log_file`**：日志是"已处理"的判据，混用会让库之间互相干扰（留空自动生成就不会撞）；
3. **`reject_dirs` 命中是"整棵子树跳过"**：它同时作用于标题层与子目录层 —— 别把正常的 `Season 1` 也匹配进去。

> 换路径、换数据卷、换机迁移时的注意事项见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §7（备份与恢复）与 [`FAQ.md`](FAQ.md) 第 23–25 问。

## 6. 跑任务：手动运行、作品记录、重做单个作品、重试

| 方式 | 谁触发 | 什么时候用 |
|---|---|---|
| **自动回调** | qBittorrent 下载完成 | 日常主力（配好后不用管） |
| **定时扫描** | 应用自己（`scan_enabled` 默认开启） | 回调漏了的补偿 |
| **手动运行** | 你在网页上点 | 补跑、试跑、只处理某一个 |
| **重试** | 你对失败任务点「重试」 | 修好问题后重来 |

### 6.1 手动运行（全量）

**媒体库页 → 选中某个库 → 「运行」 → 范围选「全部」 → 执行。**

等价于"把这个库的源目录下所有一级文件夹都过一遍"。已经处理过、体积没变的会**跳过**（这是幂等，不是失败）。结果去任务页 → 新出现的那条任务 → 点进去看日志。

### 6.2 手动运行（只处理某一部剧 / 某一个文件夹）

**媒体库页 → 该库 → 「运行」 → 范围选「指定文件夹」 → 填一级文件夹名 → 执行。** 填的是**一级文件夹名**，不是完整路径：

| 你的实际路径 | 填 |
|---|---|
| `/vol1/1000/Download/qbittorrent/Bangumi/Show A` | `Show A` |

**这就是"只处理某一部剧"的正确用法。**【宿主机】等价命令：

```bash
curl -s -b cookies.txt -X POST http://127.0.0.1:18081/api/libraries/1/run \
  -H 'Content-Type: application/json' \
  -d '{"scope":{"mode":"folder","folder":"Show A"},"force":false}'
```

### 6.3 「手动重链」和「手动重命名」到底是不是两个按钮？

**不是。** 应用的一次「运行」是按**该库的处理器**完整执行：先建硬链接、再重命名（`hardlink_only` 的库只有前者）。所以"只想重新执行重命名"时，同一个动作**效果上只有重命名阶段真的干活**：建链阶段因源侧体积与账本一致而打印"文件夹已记录且体积一致，跳过"，重命名阶段则有自己的缓存判定（体积 + 时间戳），需要时会**真的重新改名**。

> **有专门的功能做这件事**：打开**「作品记录」页** → 勾选作品 → 「立即重命名」。它**只跑重命名、不建链**。

### 6.4 重做单个作品

**整库范围的「强制重跑」不提供。** 运行弹窗里没有那个开关，应用固定以 `force=false` 调用；若你用命令行直接发 `force=true` + 整库范围（`scope.mode="full"`，默认值），服务端一律返回 **400**：

```text
{"detail": "整库强制重跑已停用：force 只允许配合 scope.mode='folder'（单个作品）使用。要重做作品，请到「作品记录」里删除对应作品的记录，下次运行时这些作品会自动补做，其余作品不受影响。"}
```

**为什么不提供**：整库 force 会让**建链阶段**把已经改过名的文件按"原名"再链一份（目标里同一个 inode 于是有两个目录项），**重命名阶段**接着多出一个 `xxx (2).mkv` 后缀 —— 越点越乱。

**要重做某个作品，走下面两条正道之一**：

| 途径 | 操作 | 效果 | 注意 |
|---|---|---|---|
| **① 只重命名** | 「作品记录」页 → 勾选作品 →「立即重命名」 | 立即对该作品跑一遍**重命名**（`kind="rename"`，202 建任务）；**不建链** | 处理器是 `hardlink_only` 的库返回 400（没有重命名规则）；库已停用返回 409 |
| **② 删记录后自动补做** | 「作品记录」页 → 勾选作品 →「删除记录」 | 删掉这些作品的记录 → **下次运行本库时自动补做**（重新建链 + 按规则重命名），其余作品不受影响 | 需**二次确认**；会**连带删除目标目录里的整个作品文件夹**，见下 |

> ⚠️ **删除的三个后果（务必看完再勾）**
> 1. **源目录一个字节都不动**：硬链接只是指向同一份数据的**另一条目录项**，删掉它**不减少**源文件的数据。
> 2. **目标是整个作品文件夹被删掉**（`shutil.rmtree`，符号链接只删链接本身），**无法撤销**。
> 3. **目录里"不是本应用建立的硬链接"的文件会被一并删掉**；弹窗会逐作品列出目标路径 / 文件数 / 总字节数 / **非硬链接文件数**，这个数大于 0 时有显著警告 —— **先看这个数字再决定**。
>
> 流程是**一次弹窗确认**：点「删除记录」→ 先摆出 `dry_run=true` 的**预演清单**（服务端只回执，**磁盘一个字节不动**）→ 点「确定删除」→ 执行（`dry_run=false, confirm=true`）→ 结果弹窗列出每个作品的成功/失败与统计。

> ⚠️ **`force=true` 配合 `scope.mode="folder"`（单个作品）仍然可用**，但它是**排查工具、不是日常操作**：「立即重命名」内部也是这么调的，它会带来两类现象 —— ① 建链阶段对**已存在**的目标文件再次 `os.link`，产生一批 `创建硬链接失败: ... File exists`；这些**无害**（建链阶段不覆盖、不删除，"目标就是同一个 inode 的硬链接"会被改判成幂等跳过 `already_linked`，只有"同名但 inode 不同"才算 `link_failed`）；② 对**已经改过名**的作品发单作品 force，目标里仍会出现**同一 inode 的第二个目录项**、重命名阶段再多出 `xxx (2).mkv`（内容还是那一份、不占额外空间），也就是整库 force 被撤掉所针对的那个现象（[`../meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-9）。**不要反复点。**

### 6.5 查看「作品记录」：一行告诉你这个作品还算不算数

**「作品记录」是一整页，不是弹窗。** 两个入口进同一页：**左侧导航栏 →「作品记录」**（路由 `#/works`），或**媒体库卡片 →「作品记录」按钮**（同一页，并把**库选择器预选**成这个库 —— `#/works/<库 id>`，筛选状态写在地址里，浏览器前进/后退可用）。

| 部位 | 内容 |
|---|---|
| 库选择器 / 搜索框 | 选看哪个库（切换会**清空已勾选**并回第 1 页）；搜索框只搜**作品名**（= 源目录里的一级文件夹名），子串匹配、**ASCII 大小写不敏感**，`%` `_` `\` 按**字面**字符处理 |
| 每页条数 / 信息行 | `25 / 50 / 100 / 200`，**默认 50**；信息行是「命中 N 条 / 本库共 M 条」+ 两本账的差集提示（`rename_missing` / `rename_only`，**按整个库算**，不受当前页影响） |
| 表格 / 底部 | 一行一个作品（列见下），每行有复选框、表头可**全选**（**勾选跨页保留**）；底部是翻页 +「已选 N 项」+「**立即重命名**」「**删除记录**」（**未勾选时禁用**） |

含义速查：

| 列 | 显示 | 说明 |
|---|---|---|
| 作品 / 体积 | 一级文件夹名 / `123 MB`（已链接 12 个文件） | 源目录里的作品名（搜索匹配的就是它）/ 记录时总体积 + 建链阶段实际写入记录的文件数 |
| 目标目录里是否还在 | 在 / **已不在** | 目标里这个作品文件夹还在不在（被手动删过 ⇒ 已不在），顺带显示**现在有多少个文件** |
| 是否已记录重命名 | 已记录 / **未记录** | 本库的**重命名缓存**里还有没有这个作品 |
| 记录时间 / 目标路径 | 时间戳 / 完整路径 | 这条记录什么时候写的 / 作品在目标里的绝对路径 |

**两个动作分别做什么：**

- **「立即重命名」**：只对**勾选的**作品跑一遍重命名（`kind="rename"`，建排队任务、返回 202）。**只碰目标库，从不碰源目录**；`hardlink_only` 的库返回 400，库已停用返回 409。**不建链。**
- **「删除记录」**：**破坏性操作**，一次弹窗确认 —— 先 `dry_run=true` **预演**（列出每个作品的目标路径、文件数、总字节数，以及**有几个不是本应用建立的硬链接**），点「确定删除」才真正执行。它删**三样东西**：① 本库账本（`link_records`）里的那一行；② 重命名缓存里的条目；③ 目标目录里**整个作品文件夹**（`shutil.rmtree`）。**源（下载）目录一个字节都不动**；删完之后下次运行会自动重新建链 + 按规则重命名，其余作品不受影响。

> 📌 **账本是"作品级"的：删掉目标里的某个文件，普通运行不会把它补回来。** 记录说的是"这个作品做完了"，应用**不会去数目标目录里少了哪个文件**。要让某个作品被重做，只有两条正道：**删掉它的记录后重跑**（会连带删掉目标里的整个作品文件夹）、**用「立即重命名」只重跑改名这一步**。信息行里的差集标记（`rename_missing` / `rename_only` / `target_exists` / `rename_recorded`）**只做提示，永远不会据此自动"修复"** —— 你在目标目录里的**手动增删改一律保留**。
>
> ⚠️ **账本为空的库必读**：判据记在**每库自己的账本**里；账本为空时（换了数据卷、清了 `/data`）第一次**全量**运行会把**每个作品重新建链一次**，已经在目标里改过名的文件会以**原名**再链一份、重命名阶段于是多出 `xxx (2).mkv`。**不丢数据**（同一 inode），但会多出重复文件名 —— 建议用**新库**、或先**清空目标目录**、或**逐作品**处理。为了不重蹈"越点越乱"的覆辙，**整库强制重跑依旧停用**（返回 400，§6.4）。

出现「已不在」「未记录」怎么办，见 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)。

### 6.6 重试（retry）

任务失败后，修好根因（权限、挂载、跨挂载…），然后：**任务页 → 找到那条失败任务 → 「重试」**。它用**完全相同的配置**新建一个任务，原任务记录保留（便于对比）。只有 `失败` / `已取消` 的任务能重试；正在跑的任务只能等它跑完。

**【宿主机】**等价命令：`curl -s -b cookies.txt -X POST http://127.0.0.1:18081/api/tasks/42/retry`

### 6.7 取消任务

**排队中（queued）** 的任务可以取消；**执行中（running）** 的任务**不能中断** —— 这是刻意的：应用正在做"读-改-写整份日志文件"的操作，硬杀会破坏一致性。请等它跑完（通常几秒到几分钟）。

## 7. 任务页：状态含义、失败原因解读、重试

### 7.1 任务页能做什么

顶部有搜索与筛选：

| 控件 | 作用 |
|---|---|
| 搜索框 | 按关键词搜（库名、文件夹名等） |
| 状态筛选 | 只看失败 / 只看成功 … |
| 媒体库筛选 | 只看某个库的任务 |

列表按时间倒序（最新在最上面）。点任意一条 → 任务详情（含 `result` 计数与完整日志）。

### 7.2 状态含义

| 状态 | 中文 | 含义 | 要做什么 |
|---|---|---|---|
| `queued` | 排队中 | 已入队，等前面的任务跑完 | 等着（队列串行） |
| `running` | 执行中 | 正在跑 | 等着 |
| `success` | 成功 | 执行完成 | 看 `result` 计数确认是否真的链了/改了。**可能有部分失败**，见下 |
| `failed` | 失败 | 执行体抛异常，或所有文件都建链失败 | 看 `error` + 日志，修好根因后**重试** |
| `skipped` | 跳过 | 无需处理（源目录里没有符合条件的一级文件夹，或体积一致全跳过） | 通常不用管。刚下载的新内容却显示跳过 → 看 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 场景 4 |
| `cancelled` | 已取消 | 在排队时被你取消了 | 需要的话重新跑 |

> ⚠️ **`success` 不等于"每个文件都成功了"。** 看详情里的计数：

| 计数 | 含义 |
|---|---|
| `linked` / `skipped` / `link_failed` | 新建的硬链接数 / 因体积一致跳过的文件夹数 / 建链接失败的文件数 |
| `renamed` / `rename_failed` | 重命名成功 / 失败数 |
| `kept_unresolved_episode` | 命名引用了集数、但一条都没解析出来的文件数（这些文件**保留原文件名、未改名**，**不是失败**；明细 `samples.kept_unresolved_episode`） |
| `name_collisions` | 改名时**目标文件名已被占用**的文件数 —— **事实清单**，**不代表**"即将被覆盖"。`within_run` = 本次运行里更早的文件占用；`existing_target` = 目标上**本来就有**同名文件。**L2 不覆盖**：靠「加后缀保留」/「原有文件让位」化解（明细 `samples.name_collisions`，日志 WARNING） |
| `renamed_with_suffix` | **实际加了后缀保留**的文件数（如 `Show A S01E01 (2).mkv`）：同一次运行里按**体积从大到小**，最大的拿干净名、其余加 ` (2)`、` (3)`…（上限 999）；目标上原有的同名文件比新来的小时改名**让位**（**不删除**）。明细 `samples.renamed_with_suffix`，日志 WARNING |
| `extras_classified` | 本次**命中特典判据、被排除在改名之外**的文件数（**不改名、也不移动** —— 保留原名留在原位置，因此**不**计入 `renamed`/`name_collisions`/`episode_unresolved`）。`0` = 没有命中或该功能已关闭（`extras_patterns: []`）。明细 `samples.extras_classified`（每条 `{dir, name, size, pattern}`），日志里是中文 INFO「特典保留原名（判据命中，未改名、未移动）：…」。见 §8.7.1 |
| `episode_unresolved` | **所有**没解析出集数的文件数，**不管最后有没有保留原名**（命名模板不引用集数时，这种文件照样改了名）。它是 `kept_unresolved_episode` 的**超集**（明细 `samples.episode_unresolved`，日志 INFO） |
| `unknown_params` | 命名段里用了**不存在的变量名**、因而那段被**留空**的文件数 ⇒ 文件名少一段，但任务仍算**成功**。老配置/手改 YAML 才可能触发。明细 `samples.unknown_params`（`{label, file, params}`），日志 WARNING + 任务告警一条汇总（带改法） |
| `orphans_removed` | 被删除的孤儿硬链接文件夹数（**注意看这个数字**） |

> **`linked: 0` 且 `skipped: 0` 且 `link_failed: 0` 且 `renamed: 0`** → 源目录里根本没有符合条件的一级文件夹，去确认源目录对不对。
> **`unknown_params > 0`** → 有文件**名字少了一段**：看 WARNING 与 `samples.unknown_params`，把那个名字改对，或在「命名表达式」里定义它（[`../meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-11）。
> **`kept_unresolved_episode > 0`** → 有文件因为"认不出集数"被跳过（详情卡片与明细里有路径）。想改名就补一条能命中文件名的 `episode_patterns`，或给 `episode_fallback` 配字面量（见 §5.2 与 [`FAQ.md`](FAQ.md) 第 9 问）。**这个计数可能比预期大**：默认是 9 条带边界约束的规则，像 `Show.E07.mkv`（`E` 紧贴点号）、`Show - 1920x1080.mkv` 都不会被当集号 —— 前者保留原名，后者归入"认不出"（不会被错认成第 19 集）。想换成最朴素的旧口径，把集数规则换回 `legacy` 那两条（或整库用 `legacy` 预设）。
> **`name_collisions > 0`** → 有多个源文件想改成**同一个目标名**（详情页「同名冲突」卡片逐条列出）。⚠️ **L2「防丢」**：体积最大的拿干净名，其余加 ` (2)`、` (3)`… 保留；目标上原有的同名文件比新来的小时改名**让位**（**不删除**）。所以它只说明"发生过争名"，**不等于丢文件**。想彻底避免，清理目标里的重复版本或调命名模板（[`../contracts/BASELINE.md`](../contracts/BASELINE.md) §5 的 L4 行）。
> **`episode_unresolved > kept_unresolved_episode`** → 有些文件认不出集数、但**没有**保留原名（命名模板没引用集数）。看 `samples.episode_unresolved` 确认。
> **`orphans_removed > 0`** → ⚠️ 媒体库里**真有文件夹被递归删除了**，去日志里找 `Deleted orphaned hard link folder:` 那几行确认。

> 📌 **另外两个字段值得看一眼**：
> - **`warnings[]`**：**不致命的告警**（中文、可执行）。常见五类：①「源与目标不在同一个挂载」—— 任务运行期只警告，真失败会体现在 `link_failed`（**建库/改库时同一条件会被 `400` 直接拒绝**，不会让你存下一个注定失败的库）；②「源目录在任务期间发生了变化」；③「本次运行有 N 个文件改到了已被占用的目标文件名上…」—— 争名汇总（明细见 `samples.renamed_with_suffix` 与 `samples.name_collisions`）；④「N 个文件因为目标名被占用而加了后缀保留（正片优先、其余不丢）：…」—— 列出前 10 条 `原名 → 新名`；⑤「N 个文件命中特典判据、已排除改名（保留原名、留在原位置）：…」—— L3 特典排除汇总（前 10 条 `文件名（判据）`；判据来自设置页，误判就把判据写精确，见 §8.7.1）。
> - **`source_integrity`**：`{"ok": true, "changed": []}`。任务**开始前**对源目录做逐文件快照（相对路径 / 大小 / inode / mtime），**结束后**再核对；`ok: false` 时列出被动过的路径。硬链接本身只让源文件的链接数 +1、`ctime` 变化，这两项**不算**变化，所以不会误报（[`FAQ.md`](FAQ.md) 第 4 问）。

### 7.3 常见失败原因："error 里这句话是什么意思"

| 报错里出现的关键词 | 意思 | 怎么办 |
|---|---|---|
| `跨挂载` / `EXDEV` / `link_failed` | 源和媒体库**不在同一个挂载**上（比"不同文件系统"更严），**建不了硬链接** | 把下载根与媒体库根放进**同一条 bind**（`MEDIA_ROOT`）；本应用**不会**复制文件。见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §3 与 [`FAQ.md`](FAQ.md) 第 3、34、35 问 |
| `无法比较文件系统` / `路径不存在或不可访问` | 源目录或目标父目录不存在；或预检**无法实证**（`same_filesystem: null`） | 检查挂载；确认你填的是**容器路径**而不是误填的旧路径；`null` 不算失败（§3.1、[`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 场景 21） |
| `Permission denied` | 容器运行身份读不了源 / 写不了目标 | 见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §10（PUID/PGID 与 chown） |
| `创建硬链接失败: ... File exists` | 目标已存在（常见于**强制重跑**）。若目标就是**同一个 inode 的硬链接**，会算成幂等跳过（`already_linked`，计入 `skipped`），任务**不会**因此失败；只有"同名但 inode 不同"才是真的 `link_failed` | 多数情况**无害，不用处理**。想彻底干净就删掉目标那一个文件再跑（或删掉该作品目录后重跑） |
| `Permission denied: '/data/config'` | 配置目录属主不对（少见） | 见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §10.3 |
| `Non-hard-link` / `非硬链接` | 应用逐文件核对后发现某个"建好的"文件不是真硬链接 | ⚠️ 严重信号（文件系统行为异常），去 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 查 |
| `Skipping folder: X (already processed at ...)` | 不是错误，是幂等跳过 | 想重做就用「作品记录」里的「删除记录」（§6.4） |

更全的对照与处置步骤见 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)。

### 7.4 看日志：怎么读

**任务详情页的日志区**按时间排好，每行有级别：

| 级别 | 含义 | 典型内容 |
|---|---|---|
| `DEBUG` | 调试细节 | 默认不显示太多 |
| `INFO` | 正常进展 | `已创建硬链接: ...`、`Renamed: ... -> ...`、`已记录文件夹体积: ...` |
| `WARN` | ⚠️ 需要注意 | **`Deleted orphaned hard link folder: <路径>`**（真的有文件夹被删了）、部分失败 |
| `ERROR` | 出错 | 执行异常、任务失败原因 |

**建链阶段原生实现打印的输出**标记为 `stdout` 来源，文案格式**冻结**（`app/processors/hardlink.py` / 规则引擎发出）：

- `已创建硬链接: <路径>`
- `创建硬链接失败: <路径> - <原因>`
- `文件夹已记录且体积一致，跳过: <文件夹>`
- `已删除旧记录: <文件夹>`
- `Deleted orphaned hard link folder: <路径>`
- `Renamed: <旧名> -> <新名>`
- `Error renaming <旧名>: <原因>`
- `Skipping folder: <文件夹> (already processed at <时间>)`

**想让日志更详细**：设置页把 `log_level` 改成 `DEBUG`（完事改回 `INFO`）。
**日志区自动刷新**（每 1.5 秒拉一次），任务跑完后停止刷新。

### 7.5 重试的正确顺序

1. 在任务详情页读 `error` 和日志，**先判断是哪一类问题**（上一节的表格）；
2. 修根因：
   - 跨挂载 → 换挂载（同一条 bind）/ 换目标目录（**不是**改库配置能绕过的）；权限 → 宿主机上调属主/权限并重建容器（[`DEPLOYMENT.md`](DEPLOYMENT.md) §10）；目录不存在 → 建目录；token/网络 → 不会产生任务，属另一类（§9）。
3. 回任务页点「重试」；
4. 还失败 → 把 `error` 里的中文原文拿到 [`FAQ.md`](FAQ.md) / [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 里对照。

## 8. 设置页：逐项说明

设置页（`#/settings`）分几块。下表是全部可改项。

### 8.1 安全 / 账号

| 项 | 说明 |
|---|---|
| **修改密码** | 填当前密码 + 新密码（≥ 8 位）。改完当前会话**立即失效**：页面直接回到登录页并提示「密码已修改，请用新密码重新登录」；旧密码输错会在输入框下红字提示，状态不变 |
| **登出** | 清除本机 Cookie |

> 💡 会话密钥存在 `/data/secret.key`。删掉它 = 所有人被登出（**账号密码不变**）。

### 8.2 回调 / Hook（**建好库之后马上来这一块**）

| 项 | 说明 |
|---|---|
| **hook token** | `http://<HOST_IP>:18081/api/hooks/*` 的通行证。**注意保密**，相当于这个应用的"触发钥匙" |
| **重新生成 token** | 旧 token **立即失效**。生成后必须**同步更新 qBittorrent 里的回调命令**，否则那边会一直报 `401` |
| **完整回调命令** | 已经把你当前的 token 和地址填好的一整行命令，点「复制」直接拿去粘进 qBittorrent。**最推荐的用法**（不用自己拼） |

> 📌 **token 只在设置页拿，不在 `.env` 里**：`hook_token` **不是环境变量**，`.env` 没有这个键、填了也不会被读取。它由应用**首次启动时随机生成**，存在 `/data` 的数据里；设置页是它**唯一的查看与轮换入口**（`GET /api/settings` 也能读到明文）。
> 📌 **qBittorrent 容器的路径和本应用容器不一样？** 例如 qBittorrent 把下载目录挂成 `/downloads`，而本应用里是 `/vol1/1000/Download/qbittorrent` —— 回调带的 `%F` 就会是 `/downloads/...`。这时要在设置页下面 **§8.8 的 qBittorrent 卡片**里加一条「回调路径映射」，否则回调会退化成整库全量（见 §9 第 4 步）。

用法见 §9。

### 8.3 源 / 目标目录的约束

v2 起**不再有**「允许的源/目标根目录」设置项（`allowed_source_roots` / `allowed_target_roots` 已从 DB、API、
WebUI 与健康检查中整体删除，启动迁移会自动清掉老库里的遗留配置）。

现在只校验两件事，都在**新建 / 编辑媒体库**时进行：

1. 源目录与目标目录**在同一个挂载**上（否则硬链接会 `EXDEV`，直接报错，不会降级成复制）；
2. 两者**不得相同、不得互相包含**。

填的仍是**容器路径**（单挂载形态下 = 宿主真实路径）。跨挂载的处置见 §7.3 与 [`DEPLOYMENT.md`](DEPLOYMENT.md) §3。

### 8.4 扫描补偿

| 项 | 默认 | 说明 |
|---|---|---|
| `scan_enabled` | `true`（开） | 定时扫描源目录，发现"没记录过或体积变化"的一级文件夹就**建任务**。用于补上漏掉的回调 |
| `scan_interval_seconds` | `900`（15 分钟） | 扫描周期。想更及时就调小（例如 `300` = 5 分钟）；合法区间 30–86400 |

**默认开启**：从零建库的新实例出厂就开着，让系统有"自愈"能力 —— 回调漏了、容器重启过，下次扫描会补上。代价是每 15 分钟做一次目录体积统计（对宿主机是轻负载）。不需要的话在设置页关掉即可；已有部署升级上来时保留原来的开关值，不会被强制打开。

> 扫描**只创建任务，不做任何文件操作**。真正的文件操作由建链执行，且依旧幂等。

### 8.5 孤儿清理（⚠️ 破坏性能力，先读完）

| 项 | 默认 | 说明 |
|---|---|---|
| `orphan_cleanup_enabled` | `true`（开） | **全局总开关**。开启时，若源目录里某个一级文件夹**已被删除**，下次跑任务会**递归删除**媒体库里对应的硬链接文件夹 |

它和每个库自己的「孤儿清理」设置是**"与"**的关系：**两个都为真**才真的删除。

**它删的是硬链接（媒体库那一份名字），不会碰你的下载原文件**（应用代码层从不写源目录，任务前后还会逐文件核对 —— [`FAQ.md`](FAQ.md) 第 4 问）。每次删除都在任务日志里以 **WARN** 级记录完整路径。

**什么时候必须关掉**：

- 你打算**删掉下载盘里的原始下载、但保留媒体库**（否则下次跑任务媒体库那份就没了），或下载目录会被临时清空 / 迁移（换盘、腾空间）。

**关掉的副作用**：源文件已删的旧记录会一直留在账本里，每次跑任务去 `stat` 一次（纯读），没别的影响。

**【宿主机】**也可以用命令关：

```bash
curl -s -b cookies.txt -X PUT http://127.0.0.1:18081/api/settings \
  -H 'Content-Type: application/json' \
  -d '{"orphan_cleanup_enabled": false}'
```

> 详见 [`FAQ.md`](FAQ.md) 第 5 问；`orphan_cleanup` 的默认安全性见 §8.5。

### 8.6 日志与历史

| 项 | 默认 | 说明 |
|---|---|---|
| `log_level` | `INFO` | 应用日志等级。排查时可临时改 `DEBUG`，**完事改回 `INFO`**（否则日志涨得快）；合法值 `DEBUG` / `INFO` / `WARNING` / `ERROR` |
| `max_history` | `2000` | 任务历史保留条数。超出后自动裁剪最旧的记录。**只删记录，不动磁盘文件**（区间 10–100000） |
| `max_task_log_lines` | `5000` | 单个任务保留的日志行数上限（超出会插入一条截断提示；区间 100–1000000） |
| `config_sync_interval_seconds` | `5` | 文件 → 数据库的自动导入间隔；设 `0` 表示**关闭自动导入**，只在你点按钮时导入（区间 0–86400） |

> 📌 **配置目录（`/data/config`）不是设置项**：它由 env `CONFIG_DIR` 指定（默认 `/data/config`，在 `/data` 卷内，无需额外挂载）；往 `PUT /api/settings` 里塞 `config_dir` 会被当成"未知的设置项"直接 **400**。
> 📌 设置页里**没有** `seed_logs_on_first_run` 这一项 —— 它是历史遗留键，不需要它。

### 8.7 允许重命名的文件后缀

设置页的「**允许重命名的文件后缀**」卡片：每行一个后缀（`.mkv` / `.mp4` / `.ass`…），**留空 = 未设置**（此时按各处理器自己的清单走）。

- 它**对所有媒体库生效** —— 这是"我不想让 `.mp4` 被改名"这类需求的一处总开关；
- 大小写不敏感（`.MKV` 会归一化成 `.mkv`）且保序去重；必须以点开头，否则保存时提示；
- **优先级**：库级覆盖（§5.4.2）→ 本设置 → 处理器清单。也就是说想只放行某一个库，去库编辑页写覆盖；想全局生效，就在这里改；
- 它只决定**重命名阶段**认哪些文件；硬链接阶段永远整棵树链过去，不看后缀。

#### 8.7.1 特典文件排除（L3）

设置页的「**特典文件排除**」卡片：**一行一条正则**（不是一行一个后缀，也**不按空格切**）。出厂默认 7 条 —— `NCOP`、`NCED`、`Preview`、`Creditless`、`Info`、`予告編`、`CM集`；**清空成 `[]` = 关闭这个功能**。

- **它解决什么**：与正片平级的散装特典文件（`NCOP.mkv`、`Preview 01.mkv`…）会被当成正片套上集号（比如被改叫 `Show A S01E01.mkv`）。开了它，命中判据的文件**退出改名流程** —— **不改名、也不移动**：保留原名留在原位置（硬链接阶段建好的那一份照旧在媒体库里）。
- ✅ **命中文件原地躺着**：应用**不会创建 `<作品目录>/其他/` 目录**，也**不会移动**任何文件（这个功能早年曾规划"移入 `其他/`"，已明确取消）。
- **判据怎么用**：对**含扩展名的文件名**做**大小写不敏感**的正则搜索（`NCOP` 能命中 `[NCOP].mkv`）。一行一条，写 `^NCOP$` 这类锚定更精确；空行会被忽略；**非法正则保存时直接报错**（会告诉你第几条、哪个模式编译失败），不会静默吞掉。**只作用于当前作用域目录的直接文件** —— `Season 1/特典/` 这种**嵌套子目录里的文件一律不动**。
- **不会丢文件、也不会多出目录**：命中文件停在原处 —— 文件名、位置、内容一个字节都没变。
- **任务结果里怎么看**：`result.extras_classified` 是**本次被排除的文件个数**（0 = 没有命中或功能已关闭），样本在 `samples.extras_classified`（每条 `{dir, name, size, pattern}`；`pattern` 是命中的那条判据，便于反查误判）；日志里是中文 INFO「特典保留原名（判据命中，未改名、未移动）：…」。
- ⚠️ **误判了正片怎么办**：把那条判据改精确（例如 `^NCOP$`）或删掉它 —— 下次改名就照旧处理了。
- **这是一项独立能力**：对所有库与所有处理器生效，`legacy` 预设也**不例外**；只影响重命名，不影响硬链接的建立。

### 8.8 qBittorrent API 连接（可选）

| 项 | 说明 |
|---|---|
| `qbittorrent_url` | 如 `http://<HOST_IP>:18080`（qBittorrent 的 **WebUI** 端口，不是本应用的 18081） |
| `qbittorrent_username` / `qbittorrent_password` | qBittorrent 的登录凭据 |
| **回调路径映射** | 可选，**参与回调的功能判定**（不是补偿项）：把 qBittorrent 容器里的路径换成本应用容器里的路径。一行一条，两个输入框分别是「容器内路径（qBittorrent 容器里的路径）」和「绝对路径（本应用容器里的绝对路径）」，可以点「添加一条映射」加多条 |

**这些是可选补偿项**。应用**不靠它工作**：自动触发靠回调，补偿靠目录扫描。填了可以做更强的 API 补偿（向 qBittorrent 查询种子列表）。不填完全不影响主流程。

> 💡 密码框显示 `***` 表示"已设置"。保持 `***` 不变就是不改它；要改就输新密码。

**「回调路径映射」什么时候要填**：只有「qBittorrent 容器的路径 ≠ 本应用容器的路径」时才需要。两边一致（单挂载形态的常见情况）就**留空**。示例：

| 容器内路径（qBittorrent 容器里的路径） | 绝对路径（本应用容器里的绝对路径） |
|---|---|
| `/downloads` | `/vol1/1000/Download/qbittorrent` |

意思是：回调带来的 `/downloads/Bangumi/Show A` 会被当成 `/vol1/1000/Download/qbittorrent/Bangumi/Show A` 来用。规则：

- 一行一条，保存即生效（不用重启）；留空 = 不换算，行为与以前完全一样。
- 左侧是 **qBittorrent 容器里**的路径前缀，右侧是**本应用容器里**的路径前缀；库的源目录/目标目录/匹配路径前缀**仍然填本应用容器里的路径**，不要填 qB 的。
- 多个前缀都能命中时用**最长**的那条；换算后的路径**必须真实存在**，否则这一次不换算（通常退化为全量）并在回调响应的 `warnings` 里说明 —— 所以映射写错不会把任务指到错误目录。
- qBittorrent 改了下载目录的挂载方式时，回来改这一行即可。
- 填错格式（只填了一边、不是 `/` 开头的绝对路径）保存会报错，提示第几条有问题。

> 📌 它和「系统信息」里的「路径映射表」（`HOST_PATH_MAP`）**不是一个东西**：那个只影响页面上显示的路径好不好看，填错不影响功能；这个**真的参与回调路径换算**。

### 8.9 权限模式（在媒体库的编辑页，不是设置页）

**一句话**：**默认关闭**。打开它、并在弹出的确认框里点「我了解风险，开启」之后，应用会在建链阶段把**目标库**的权限改成 `0777`，好让**非 root 的服务**（例如以非 root 身份运行的 Emby）也能读到库内文件。它是「要你亲手担责」的开关，不是推荐默认项。

**它到底改什么**：库根目录本身 + **本次处理到的每个作品文件夹的目标侧整棵子树**（包括体积一致、本来会被跳过的旧作品 —— 否则开关对已经入库的内容等于没开），目录与文件都改 `0777`。**不改**你的下载目录、**不跟进**符号链接；关闭时（默认）**一个 `chmod` 都不做**。

> ⚠️ **必须知道的副作用**：媒体库里的文件是**硬链接**，与下载原文件**共享同一个 inode**，而权限位是 inode 的属性 —— 所以给媒体库放权会**同时改掉下载根下源文件的权限位**。文件内容、大小、inode 号、修改时间都不变（源完整性核对因此不会报警），但**权限确实一起放宽了**。这正是：默认关闭、开启前必须二次确认、每次运行都会在任务日志里以 WARNING 记录「改了 N 个目录 / M 个文件」的原因。契约见 [`../contracts/BASELINE.md`](../contracts/BASELINE.md) §1.6 与 B13。

**什么时候该开**：只有当某个以非 root 身份访问媒体库的服务确实读不到文件（`EACCES`）时才开。**更干净的替代做法**：在宿主上针对**目录**做精确的属主/权限调整（[`DEPLOYMENT.md`](DEPLOYMENT.md) §10.3），或把该服务改成以同属主/root 身份运行 —— 这些都不动源文件。"为什么媒体库里的文件权限和下载目录里的一样"见 [`FAQ.md`](FAQ.md) 第 27 问。

### 8.10 系统信息（只读，但很有用）

| 区块 | 看什么 |
|---|---|
| **健康检查** | 四项 `checks` 全为 ✅ 才算健康（`db` / `data_dir` / `processors` / `config`）；任一项 false 的处置见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §4.4.1 |
| **路径映射表** | 容器路径 ↔ 宿主路径的对应关系（来自 `HOST_PATH_MAP`）。**它只用于显示**：填错、漏填都**不影响功能**（见 [`DEPLOYMENT.md`](DEPLOYMENT.md) §4.2）。⚠️ 别和设置页 qBittorrent 卡片里的「回调路径映射」混淆：那个是**功能项**（回调路径换算，§8.8） |
| **挂载判定** | 源与目标是否在**同一个挂载**里。预检的 `same_filesystem` 是**三态**：`true`（实证 link 探针证过；若只是挂载 ID 预筛通过会在 `warnings[]` 注明「未实证」）/ `false`（**已证实**建不出 ⇒ `ok=false`、原因进 `errors[]`）/ `null`（判不了，例如源树下找不到可试链的普通文件）。⚠️ **`st_dev` 两个数字相同 ≠ 能建硬链接** —— `linkat(2)` 比较的是挂载身份，`st_dev` 相同但分属两条 bind 时 `link()` 依然 `EXDEV`（"假绿"的根因） |

> 硬链接与重命名由 `app/processors/hardlink.py` 与规则引擎 `app/processors/engine.py` 执行，行为由项目自己的回归测试（冻结的黄金值）守护。

**建议**：建库前后各看一次这一页。跨挂载这个最坑的问题，在这里一眼就能看出来。

## 9. qBittorrent 回调：拿命令、粘进去、验证

把"下载完成 → 自动整理"打通，全程复制粘贴。

1. **拿命令**：设置页 →「回调 / Hook」→ 点「复制回调命令」。复制到的是一整行、已含你 token 的命令；
2. **粘进去**：qBittorrent WebUI（默认 `http://<HOST_IP>:18080`）→ 右上角**齿轮 → 下载 → 「运行外部程序」**→ 整行粘贴 → 确认**已启用** → 保存；
3. **三条不能改的**：命令**必须是一行**；7 个占位符 `%N` `%I` `%L` `%G` `%F` `%D` `%R` **照抄**；**不要**加 `kind=%K`（`%K` 是 Torrent ID，不是任务类型，任务类型由媒体库的处理器推导）；
4. **验证**：在【宿主机】手动打一次回调，看返回是不是 `"matched":1`（命令形状见 [`../examples/qbittorrent-autorun.md`](../../examples/qbittorrent-autorun.md)）；`matched:0` 说明通了但没命中任何库 —— 看 `ignored_details[].reason`，对照本节末指针里那张「`matched: 0` 原因对照表」与 §4.4；
5. **漏了怎么办**：扫描补偿默认已开启（`scan_enabled=true`，§8.4），每 15 分钟补一次；关掉过就回设置页重新打开。

> 📌 **qBittorrent 容器里的下载路径和本应用不一样时**：先到设置页 qBittorrent 卡片（§8.8）加一条「回调路径映射」（例如 `/downloads` → `/vol1/1000/Download/qbittorrent`），再做第 4 步验证。`%F` 是**qBittorrent 容器视角**的路径，映射就是给这条路径做前缀替换；不配的话回调通常仍能按分类命中，但切不出一级文件夹、每次退化为整库全量。

> **完整命令（7 个 `--data-urlencode` 逐字版）+ qBittorrent 各版本菜单路径 + `matched: 0` 的逐条原因对照表**：
> 见 [`../examples/qbittorrent-autorun.md`](../../examples/qbittorrent-autorun.md)（**唯一权威完整副本**）与 [`DEPLOYMENT.md`](DEPLOYMENT.md) §5。
> 回调的接口契约见 [`../contracts/API.md`](../contracts/API.md) §6、[`../contracts/ARCHITECTURE.md`](../contracts/ARCHITECTURE.md) §8。

## 10. 删除媒体库规则会发生什么

**结论：只删规则，绝不删你的文件。**

**媒体库页 → 选中某个库 → 「删除」**，会出现**二次确认弹窗**（刻意的，防手滑）。

### 10.1 删了之后

| 东西 | 结果 |
|---|---|
| 这条库的配置（源/目标目录、匹配条件、处理器…） | ❌ 删除 |
| 该库的账本记录与重命名缓存条目 | ❌ 删除（所以重建同名库后作品会被重新处理） |
| **已经建好的硬链接文件** | ✅ **原样保留**，Emby 照常能播 |
| **qBittorrent 下载的原始文件** | ✅ 完全不受影响（应用代码层从不写源目录；源完整性核对兜底） |
| 该库的历史任务记录 | ✅ 保留（记录里会留着库名，方便你事后看懂） |
| 以后的 qBittorrent 回调 | 这个库不再参与匹配，不会再触发 |

接口的响应也把这件事写在明面上（`hardlinks_kept` 恒为 `true`）：

```json
{"deleted": true, "hardlinks_kept": true, "library_id": 3, "link_records_removed": 12}
```

### 10.2 想连磁盘上的文件一起清理，要自己动手

应用**不会**因为你删了一条规则就去删媒体库里的文件 —— "删配置"和"删文件"是两件完全不同量级的事，不该绑在一起。

**【宿主机】**（⚠️ 不可逆，执行前先 `ls` 确认路径！）：

```bash
ls -la /vol1/1000/Library/Anime-CN    # 先看，确认是这个目录；确认无误再手工删
```

> ⚠️ **删媒体库里的文件时记住**：如果下载目录里那份还在，**空间不会释放** —— 同一个 inode 还有另一个名字指向它（这就是硬链接）。见 [`FAQ.md`](FAQ.md) 第 2、5 问。

### 10.3 只是想暂时停用？别删，直接关「启用」

**编辑该库 → 把「启用」关掉 → 保存。**

效果：回调与扫描都不会再命中它，但配置和历史都留着。以后想恢复，打开开关就行。

## 11. 幂等性：为什么重复执行是安全的

**一句话**：建链阶段用「一级文件夹的总体积」当处理标记（记账在**每库自己的账本**里），**体积没变就跳过**。所以同一件事跑一百遍，结果和跑一遍一样。

### 11.1 机制

建链阶段处理一个一级文件夹前，先算它的**总体积**（递归所有文件的字节数），拿去**本库账本**里查：**已有记录且体积相同** → 打印 `文件夹已记录且体积一致，跳过: Show A`，然后**什么都不做**；体积不同 → 删掉旧记录、重新建链、记录新体积。

重命名阶段（规则引擎 `app/processors/engine.py`）用**同一套机制**（缓存日志 `bangumicache.log` / `moviecache.log`，同样按体积判断）。

> 📌 **判据是账本，不是 `hard_links.log`**：后者现在只是审计台账（记"处理过、当时多大"），删掉它**不会**让建链重算。

### 11.2 所以这些事都是安全的

| 担心的场景 | 实际结果 |
|---|---|
| qBittorrent 连着触发两次回调 | 第二次空跑 |
| 定时扫描每 15 分钟跑一次 | 绝大多数时候空跑 |
| 你手动点了「手动执行」很多次 | 已处理的全部空跑 |
| 任务中途失败了，你再跑一次 | 已成功的部分空跑，只补做没做完的 |
| 容器重启后 / 升级应用后重新跑一次 | 同上，安全 |

**不会出现**：重复的硬链接、被覆盖的文件、被破坏的已有链接。这也是为什么可以「拿不准就再跑一次」。

### 11.3 唯一会打破幂等的两个操作（都知道风险再用）

| 操作 | 效果 | 风险 |
|---|---|---|
| **强制重跑（force）**——**只对 `scope.mode="folder"`（单个作品）有效** | 让该作品**不跳过**、重新处理一遍（「立即重命名」内部就是这么调的） | 一批无害的 `File exists` 报错；"目标就是同一 inode 的硬链接"算成幂等跳过（`already_linked`，任务不会失败），只有同名而 inode 不同才是真的 `link_failed`；重命名阶段**不覆盖**：争名按体积判定 —— 最大的拿干净名、其余加 ` (2)`、` (3)`… 保留，原有文件比新来的小时改名让位（不删除），找不到空位则保留原名。源文件不受影响。**整库 force 已停用**（返回 400），见 §6.4 |
| **删除 `data/logs/hard_links.log`** | 它只当审计日志，**不参与"跳过"判断** → 删掉它对建链阶段**没有任何影响**（真正管用的是每库账本） | 删这个文件已经达不到"重算"的目的，反而丢了一份审计记录。**想重做就删作品记录**（见 §6.4） |

### 11.4 幂等性的"盲区"（已知限制，本项目不修正）

| 盲区 | 表现 | 绕过办法 |
|---|---|---|
| 只看**总体积** | 同一作品被追加了**等体积**的文件 → 判定为"没变" → 跳过 | 在「作品记录」里删掉该作品的记录，下次运行自动补做（见 §6.4；只想重命名就用「立即重命名」） |
| 目录名含 `" - "` | 记账行会被静默忽略，每次都当"未记录" → 重复尝试建链（产生一批无害的 `File exists`）。这类条目现在会被正确记成"目标已是同一 inode 的硬链接"（`already_linked`、计入 `skipped`），任务不因此显示失败 | 避免目录名里出现 `" - "` |

这些都属于**既有行为**，本项目刻意不修正（见 [`../contracts/BASELINE.md`](../contracts/BASELINE.md) 的 L2、L8、L9）。
