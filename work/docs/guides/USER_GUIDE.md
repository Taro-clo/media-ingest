# 使用指南（WebUI）

> **本文解决什么问题**：教你在网页上把这件事跑起来 —— 第一次登录、看懂仪表盘、**建好三种媒体库**、跑任务、看日志、排查失败、改设置。
> 面向不懂代码的 NAS 用户：你**不需要**会写命令，全部在浏览器里完成。
>
> 还没装好？先看 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md)。
> 想问"为什么不复制文件""为什么没重命名"这类原理问题？看 [`docs/guides/FAQ.md`](FAQ.md)。

**页面地址**：`http://<你的NAS_IP>:18081`（默认端口 `18081`）
**页面结构**：仪表盘 / 媒体库 / 作品记录 / 任务 / 设置（左侧导航）

**命令标注约定**：本文绝大多数操作**不需要命令**。少数可选的高级操作会标注：【NAS 宿主】（SSH 登录 NAS 执行）或【容器内】。

## 1. 第一次进来：创建管理员与登录

打开 `http://<你的NAS_IP>:18081`，会出现两种情况：

### 情况 A：还没创建过管理员

页面会显示「创建管理员」（或跳转到 `#/login` 并提示初始化）。填：

- **用户名**：随便取，例如 `admin`；
- **密码**：**至少 8 位**。这是你以后进后台的唯一凭据，请用强一点的。

点确认 → 自动登录 → 进仪表盘。

> 💡 如果你在 `.env` 里填过 `ADMIN_USERNAME` / `ADMIN_PASSWORD`，容器首次启动时已经自动建好了账号，那就走情况 B。

### 情况 B：已经有管理员

输入用户名密码登录。

**登录后立刻做这三件事**（顺序无所谓，但别跳）：

1. **改密码**：设置页 → 「修改密码」→ 填当前密码 + 新密码（≥ 8 位）。
   如果你是用 `.env` 里的明文密码初始化的，改完密码后请把 `.env` 里 `ADMIN_PASSWORD` 那行**删掉或注释掉**（那个文件里存明文密码不安全）。
2. **复制 hook token 和回调命令**：设置页 → 「回调 / Hook」→ 点复制。这个一会儿要粘进 qBittorrent（见 §9）。
3. **看一眼系统信息**：设置页 → 「系统信息」，确认健康检查六项（`db` / `data_dir` / `downloads_readable` / `library_writable` / `processors` / `config`）全为 ✅，以及源/目标目录的设备号（`st_dev`）**相同**。

### 登录相关的小知识

- 登录状态存在浏览器的 **Cookie**（名为 `mlm_session`）里，有效期内不用反复登录；
- **换浏览器、清 Cookie、用无痕窗口** → 需要重新登录；
- 如果所有人都突然被登出：多半是数据卷里的 `data/secret.key` 丢了或被换了（会话签名密钥变了）。**密码没变，重新登录即可**；
- 忘记密码了 → 见 [`docs/guides/FAQ.md`](FAQ.md) 第 15 问（有重置步骤）。

## 2. 仪表盘：每张卡片是什么意思

仪表盘（`#/dashboard`）回答一个问题：**"现在一切正常吗？"**

### 2.1 任务统计卡片

| 卡片 | 显示什么 | 看到多少算正常 |
|---|---|---|
| **排队中（queued）** | 已入队、还没轮到的任务数 | 平时 `0`；刚下载完一个种子后短暂变成 `1` 是正常的 |
| **执行中（running）** | 正在跑的任务数 | `0` 或 `1`。**永远不会超过 1**（队列是串行的） |
| **近 24 小时成功** | 最近一天成功执行的任务数 | 数字变大 = 在正常工作 |
| **近 24 小时失败** | 最近一天失败的任务数 | **持续 > 0 就要去任务页查原因**（最常见的是跨挂载 / 权限） |

### 2.2 队列状态卡片

| 字段 | 含义 |
|---|---|
| 正在执行 | 当前任务的 id（点它可跳详情）。空闲时显示「空闲」 |
| 排队数量 | 等待执行的任务数 |

> 队列是**串行**的：一次只有一个任务在跑。为什么？因为建链阶段的原生实现会"读-改-写整份日志文件"，两个任务同时跑会互相覆盖（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 A12）。所以看到"排队 3 个"是正常的，它们会依次跑完。

### 2.3 媒体库概览卡片

| 字段 | 含义 |
|---|---|
| 媒体库总数 | 你建了多少条规则 |
| 已启用 | 其中启用了多少（**未启用的库不会被 qBittorrent 回调或扫描命中**） |

每个库还会显示**最近一次任务的状态**（成功 / 失败 / 跳过 / 从未运行）。这是最快的"这个库健康吗"指标。

### 2.4 近期任务列表

最近若干条任务，显示：任务 id、所属媒体库、触发来源、状态、时间。**点任意一条进入任务详情**（看完整日志）。

触发来源（`trigger`）含义：

| 来源 | 意思 |
|---|---|
| `hook` | qBittorrent 下载完成后自动回调触发的（在 qBittorrent 的设置里就是「运行外部程序」） |
| `scan` | 定时目录扫描补偿发现的 |
| `manual` | 你在网页上手动点的「运行」 |
| `retry` | 你对一条失败/取消的任务点了「重试」 |

### 2.5 待办看板

**它是什么**：一块**全局**的待办清单，回答"有没有什么事值得我处理一下？"。任务跑完时，如果有
"值得你知道、但**不该打断任务**"的情况，系统就在这里记一条；你看完在**行首点一下圆圈**即可。
**它不弹窗、不拦截、不阻断任何任务**——放着不管，任务照样跑完。

**五种待办**（每条都标注来源媒体库与任务号，点任务号可跳到详情）：

| 种类 | 严重度 | 什么时候出现 |
|---|---|---|
| **硬链接创建失败**（`link_failed`） | 🔴 错误 | 源文件没能在媒体库里建出硬链接（跨挂载、权限、目标已是别的文件……）。**这个最要紧**：媒体库里没有这个文件 |
| **冲突文件已加后缀保留**（`rename_suffix`） | 🟡 警告 | 重命名时这个目标文件名已经被占用（同一次运行里更早的另一个文件，或目标盘上本来就有的同名文件），L2「防丢」按**体积**判定后给它加了 ` (2)`、` (3)`… 后缀保留 —— **没有覆盖任何文件**，也**没有丢文件**。（**新来的自己加后缀**与**原有文件让位**是同一个问题的两条路径，看板上**只留一条**；让位那条的详情里「原因」写作 `displaced`，并标出「让位文件（原名）」与「让位后文件名」。）想少看到这些后缀，请清理目标目录里的重复版本或调整命名模板 |
| **保留原名（未解析出集数）**（`unresolved_episode`） | 🟡 警告 | 文件名引用了集数但规则全不命中，于是保留原名、没有改名 |
| **作品结构不可识别（未改名）**（`unscoped_works`） | 🟡 警告 | 子目录模式下，作品目录里**没有可接受的「季目录」**、文件直接躺在作品目录里（扁平结构）—— 重命名阶段找不到作用域，**整个作品被跳过：不改名、也不报错**。处理办法：把文件放进「作品名/Season N/」，或把该处理器的 `file_scope` 改成 `title` |
| **源目录完整性核对未通过**（`source_integrity`） | 🔴 错误 | 源目录在任务执行期间被外部改动过（核对不通过） |
| **任务失败**（`task_failed`） | 🔴 错误 | 任务以 `failed` 结束（含"一个都没建成"这种程序化失败），详情里带错误文本 |

**怎么用**

- **四个筛选**：状态（未完成 / 已完成 / 全部）、种类、媒体库、**作品**。
  **默认只显示「未完成」**；
  > 🔎 **作品筛选怎么用**：在「作品」输入框里敲作品名（或路径/错误文本里的任何一段），
  > 输入停 0.4 秒就自动筛选，旁边的「清空」一键取消。它匹配的是**待办自己的文字** ——
  > 问题摘要、详情里的目录/路径（例如 `Work 03/Season 1`）、以及去重键，**三处任意一处**包含这段文字就列出。
  > 所以它是**朴素子串**：搜 `Work 1` 会同时列出 `Work 12`；它**不是**"这条待办属于哪个作品"的精确归属
  > —— 待办台账里**没有作品字段**（详见 [`KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-10）。
  > 筛空了会明确说「没有匹配「…」的待办」，不会让你误以为看板坏了。作品筛选**不影响**顶部统计与
  > 「一键检测」（它们始终是整库/整表口径）；
- **翻页**：看板一页 20 条，底部有「上一页 / 下一页」与「第 X / Y 页（共 N 条）」。
  **没有"每类最多 50 条"的截断**；
  > 📌 换作品筛选会回到第 1 页并收起已展开的详情、放下刚打的钩（和换其它筛选一样）。
- **行首圆圈 = 打钩**：每行**最左边**有一个圆圈按钮，点一下圆圈里出现**绿勾**、整行变灰（已完成）；
  再点一下恢复成未完成。**这不是删除** —— 数据一行都没少，随时可以恢复；
  > 📌 **刚打钩的行不会立刻消失**：即使筛选是「未完成」，被勾掉的那一行也会**留在原地变灰**，
  > 直到你**翻页**或**刷新页面**（或换筛选）。这样"我刚刚勾掉的是哪几条"一眼可见。
- **一键检测**：点筛选栏右边的「一键检测」，软件会核对"记录里的文件路径"与磁盘实况，把
  **其实已经不用管**的待办列成候选（例如"那个目标文件早已被改名/挪走/清掉了"、"说缺的那个链接其实已经补上了"）。
  弹窗里**逐条带复选框**（默认全选，可以取消勾选），证据一栏写清楚"为什么认为它不用管了"，
  确认后点「标记完成（N）」才会真的打钩 —— **打钩前还会再核对一遍**，实况变了就跳过、绝不误标。
  > ⚠️ 只有**记录里带得出单个文件路径**的种类能自动检测（`link_failed`、`rename_suffix`、
  > `unresolved_episode`）；**任务失败**、**源目录完整性**与**作品结构不可识别**（`unscoped_works`，描述的是目录结构）描述的是一次任务 / 整棵树，
  > **没有单个文件**可核对，只能人工判断 —— 弹窗里会如实列出这些种类，别把"没检测出来"当成"没问题"。
- **展开详情**：点某行的「详情」，看原始路径与错误文本（长路径会换行显示）；
- **重复出现会合并**：同一个问题（同种类 + 同一个目标）反复出现时，**不会刷屏**，而是把这一条的
  「出现次数」加一、刷新「最近」时间（「首次」时间不动）。**但你打过钩之后它又发生了，会新开一条**
  ——这样"出现过几次、每次什么时候"永远查得到；
- **看板是全局的**：不分局域网里哪台机器、哪个库，所有待办都在这一张卡里。

**不想要某类待办？** 设置项 `todo_kinds`（逗号 / 顿号分隔的 kind 列表，留空 = 全部启用）。
例如只留最要紧的两种：`link_failed,rename_suffix`。写错的种类名**会被忽略**（不会因此把看板清空）。
关掉的种类**连记都不记**（不是"记了但隐藏"），看板底部会提示当前关掉了哪些。

## 3. 建媒体库前的 5 分钟自检

**这一步能省掉你 90% 的排查时间。** 建库之前，先在 NAS 上确认下面这些（【NAS 宿主】= SSH 登录 NAS 执行）：

```bash
# 1) 源与目标必须在同一个挂载 —— 两条输出的 TARGET（挂载点）必须相同
#    （比"同一个文件系统"更严：内核 linkat(2) 比较的是挂载身份，st_dev 相同不算数）
findmnt -T /vol1/1000/Download/qbittorrent -o TARGET
findmnt -T /vol1/1000/Library -o TARGET

# 2) 看一眼源目录里的一级文件夹长什么样（这决定了你库的"范围"）
ls -1 /vol1/1000/Download/qbittorrent/Bangumi
ls -1 /vol1/1000/Download/qbittorrent/Movie

# 3) 番剧：确认每个作品下面真的有 "Season NN" 这种季文件夹
ls -1 "/vol1/1000/Download/qbittorrent/Bangumi/Show A"

# 4) 目标媒体库根目录可写
ls -ld /vol1/1000/Library
```

**要记住的两条结构要求**（它们直接决定"重命名会不会发生"）：

| 库类型 | 目录结构要求 | 不满足会怎样 |
|---|---|---|
| **番剧（Bangumi）** | 源侧要是 `<作品名>/Season 1/<视频文件>`。季文件夹的名字**必须恰好**是 `Season <数字>` | 不是的话，季文件夹被忽略 → **只建硬链接、不重命名**。`Season 1 (2018)`、`Season1`、`SP`、`Specials`、`S01` 都不行 |
| **电影（Movie）** | `<电影名>/<视频文件>`（文件直接放在一级文件夹里） | 文件在子目录里 → **不重命名**（但会被建硬链接） |

扩展名白名单：`.mkv` `.mp4` `.ass`（**大小写敏感**，`.MKV`/`.SRT` 不在内）。注意：**不在白名单里的文件仍会被建立硬链接**，只是不重命名 —— 这是有意设计：硬链接与重命名是两套不同的白名单。

### 3.1 点了库编辑页的「验证」之后看到什么

「验证」会做一串检查，其中最关键的一行是 `same_filesystem`（"源与目标在不在同一个挂载"）：

| 值 | 含义 | 下一步 |
|---|---|---|
| `true` | 能建硬链接：要么**实证探针**成功（真的从源目录取一个已存在的文件、链到目标再删掉，**源目录零写入**），要么只是「挂载 ID 预筛」通过（**未实证**，那时 `warnings[]` 会写「仅据挂载 ID；该判据必要不充分」） | 放心跑 |
| `false` | **已证实**建不出硬链接（实证 `EXDEV`，或挂载 ID / `st_dev` 明确跨挂载）⇒ 预检页会**标红**（`ok=false`、`errors[]` 里是中文原因） | 看 `probe.note` / `errors[]` 的中文提示：把下载根与媒体库根放进**同一条 bind**（`MEDIA_ROOT`），见 [`docs/guides/FAQ.md`](FAQ.md) 第 34 问 |
| `null` | **判不了**（探针给不出结论 —— 例如源树里找不到可试链的普通文件 —— 又读不到挂载 ID）⇒ **不是**失败 | 任务仍可运行，真跑起来才知道；见 FAQ 第 36 问 |

> 📌 **`false` 会让预检本身报失败，但不会阻止你启动任务** —— 预检（`POST /api/libraries/{id}/validate`）把
> `false` 记进 `errors[]`、`ok=false`（让人一眼看见问题），而**跑任务**时同一判据只在
> `Task.result.warnings[]` 里留一条并继续尝试（免得一次误判让你连试都试不了）。
> 最终结论由任务执行前后的**逐文件源完整性核对**给出：真有文件没链上就是 `link_failed`、任务结论是失败，
> 而**绝不会**静默复制一份来"凑成功"。

## 4. 新建媒体库：三个完整例子

进「媒体库」页 → 点「新建」/「添加媒体库」。

### 4.0 先理解每个字段

| 字段 | 填什么 | 关键说明 |
|---|---|---|
| **名称** | 你自己看得懂的名字，如「番剧」「电影」 | 不能重名（重名会被拒绝） |
| **类型** | **自由文本**，如 `番剧`、`电影`、`4K电影` | 它只是**展示与统计用的标签**：不决定任何行为、没有枚举约束 |
| **处理器** | 下拉选一个（内置三个：`hardlink_only` / `bangumi` / `movie`） | **决定实际做什么**，见 §5。下拉里是 `/data/config/processors/*.yaml` 里的**全部**处理器，你可以自己加 |
| **启用** | 开 / 关 | 关掉的库**不会**被 qBittorrent 回调或扫描命中（但可以手动跑） |
| **源目录** | **容器路径**，如 `/vol1/1000/Download/qbittorrent/Bangumi` | 必须在允许的源根（默认是 `/vol1/1000/Download`，即整个下载树）之内 |
| **目标目录** | **容器路径**，如 `/vol1/1000/Library/Bangumi` | 必须在允许的目标根（默认只有 `/vol1/1000/Library`）之内；**不能和源目录相同或互相包含** |
| **匹配分类** | qBittorrent 的分类名，如 `ban` | 见 §4.4 匹配规则 |
| **匹配标签** | qBittorrent 的标签名 | 同上 |
| **匹配路径前缀** | 内容路径前缀，如 `/vol1/1000/Download/qbittorrent/Bangumi` | 同上 |
| **孤儿清理** | 开 / 关 | ⚠️ 开着时会**删除**"源已不存在"的目标硬链接文件夹，见 §8.5 |
| **日志文件** | **只填文件名**，如 `bangumicache.log` | 留空会**按库唯一分配**：先取该处理器登记的日志名，被其它库占用时加 `-2`/`-3`…（见 §5.6）。所有媒体库的日志都在 `/data/logs/` |
| **权限模式** | 开 / 关（**默认关**） | ⚠️ **是真实开关**：默认关闭时一个 `chmod` 都不做；开启后把**目标库**（含体积一致而被跳过的旧作品）改成 `0777`，好让非 root 服务读得到。因为媒体库文件与下载原文件共享同一个 inode，开启会**连带改掉 qBittorrent 源文件的权限位**（内容/大小/inode/mtime 不变），所以界面从关到开会**二次确认**。见 §8.9 |

**路径要注意**：这里填的是**容器内路径**；单挂载形态之后**容器路径 = 宿主路径**，所以填的就是 NAS 上的真实路径（`/vol1/1000/Download/qbittorrent/...`、`/vol1/1000/Library/...`）。容器里只有一条共同父挂载 `/vol1/1000`（外加 `/data`），**没有** `/downloads`、`/library` 这两个挂载点 —— 填 `/downloads/...` 这类路径会被拒绝。参考 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §2。

> **媒体库文件夹不写死**：`/vol1/1000/Download/qbittorrent` 下的**任何**子目录都能建库（`Anime-CN`、`Movie-4K`、
> `Documentary`……），只要它与目标目录在**同一个挂载**上（比"同一个文件系统"更强：内核 `linkat(2)` 比较的是挂载身份；见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §3）。
> 处理器**类型**不受限（可以直接选任意处理器，不存在"类型决定能用哪个处理器"的限制）。

**校验失败长什么样**（统一是 `422` + 中文字段级错误，没有 400 的"类型与处理器搭配非法"）：

```json
{"detail":[{"loc":["body","processor_id"],
            "msg":"处理器「bangumi-x」不存在。可用处理器：bangumi、hardlink_only、movie。"}]}
```

### 4.1 例子一：番剧库（Bangumi）

**场景**：qBittorrent 里分类 `ban` 的番剧下载，源目录 `/vol1/1000/Download/qbittorrent/Bangumi`，想链到 `/vol1/1000/Library/Bangumi` 给 Emby 用，并按 `S01E01` 规则改名。

**填写**：

| 字段 | 值 |
|---|---|
| 名称 | `番剧` |
| 类型 | `番剧`（自由标签，写什么都行） |
| 处理器 | `bangumi` |
| 启用 | ✅ 开 |
| 源目录 | `/vol1/1000/Download/qbittorrent/Bangumi` |
| 目标目录 | `/vol1/1000/Library/Bangumi` |
| 匹配分类 | `ban` |
| 匹配标签 | （留空） |
| 匹配路径前缀 | `/vol1/1000/Download/qbittorrent/Bangumi` |
| 孤儿清理 | 建议先设 **关**（见 §8.5 的风险说明） |
| 日志文件 | 留空（自动变成 `bangumicache.log`） |
| 权限模式 | **关**（默认；只有当非 root 服务读不到库内文件时才开，见 §8.9） |

**建议的匹配条件怎么想**：

- **匹配分类 = `ban`**：这是 qBittorrent 里你给番剧设的分类名。去 qBittorrent 的种子列表看一眼，那个"分类"列里写的是什么（注意区分大小写），照抄。
- **匹配路径前缀 = `/vol1/1000/Download/qbittorrent/Bangumi`**：兜底。即使某个种子的分类忘了设，只要它下载到 `Bangumi` 这个子目录里，也能被命中。
- 三个条件是**"与"（AND）**关系：**你填了几项，这几项就都必须成立**。上面例子同时填了「分类 `ban`」与「路径前缀 `/vol1/1000/Download/qbittorrent/Bangumi`」，那么种子必须**既**带分类 `ban`、**又**下载到 `/vol1/1000/Download/qbittorrent/Bangumi` 之下，才会命中这个库；只满足一条**不会**命中。
- 所以**填得越多，命中越严**。想让某个库"宽进"，就少填几项（例如只留路径前缀）。
- **千万不要三项都留空** —— 三项全空会被当作"不匹配"（防止误抓整个下载目录）。

**建完先点「预检」**：它会在真正跑任务之前检查源存在、目标父目录存在、**源与目标在同一个挂载**、目标可写。看到全绿再跑。

**第一次跑完要检查的事**：

1. 去 `/vol1/1000/Library/Bangumi/Show A/Season 1/` 看文件名是不是变成了 `Show A S01E01.mkv`；
2. 用 `ls -i` 对比下载侧和媒体库侧的 inode 号是否**相同**（相同 = 硬链接生效，不是复制）；
3. 如果名字**没变** → 对照 §3 的结构要求（季文件夹名 / 扩展名 / 层级），或看 [`docs/guides/FAQ.md`](FAQ.md) 第 8 问。

### 4.2 例子二：电影库（Movie）

**场景**：qBittorrent 分类 `movie` 的电影，源目录 `/vol1/1000/Download/qbittorrent/Movie` → `/vol1/1000/Library/Movie`，每个电影一个文件夹，文件夹名就是电影名。

**填写**：

| 字段 | 值 |
|---|---|
| 名称 | `电影` |
| 类型 | `电影`（自由标签） |
| 处理器 | `movie` |
| 启用 | ✅ 开 |
| 源目录 | `/vol1/1000/Download/qbittorrent/Movie` |
| 目标目录 | `/vol1/1000/Library/Movie` |
| 匹配分类 | `movie` |
| 匹配标签 | （留空） |
| 匹配路径前缀 | `/vol1/1000/Download/qbittorrent/Movie` |
| 孤儿清理 | 建议先设 **关** |
| 日志文件 | 留空（自动变成 `moviecache.log`） |
| 权限模式 | **关**（默认，见 §8.9） |

**结果会是什么样**：假设源是

```
/vol1/1000/Download/qbittorrent/Movie/流浪地球2/
    流浪地球2.2023.2160p.WEB-DL.mkv     ← 最大的那个
    流浪地球2.2023.2160p.WEB-DL.ass
    说明.txt
```

跑完之后 `/vol1/1000/Library/Movie/流浪地球2/` 里会变成：

```
流浪地球2.mkv      ← 改成了"文件夹名.后缀"
流浪地球2.ass
说明.txt           ← 不在 .mkv/.mp4/.ass 白名单，不重命名（但会被建硬链接）
```

**必须知道的两条电影规则**：

1. **每个后缀只重命名体积最大的那一个文件**。同目录有两个 `.mkv` 时，只有大的那个会改名成 `流浪地球2.mkv`，小的保留原名；
2. 只处理**一级文件夹的直接子文件**。放在子目录（如 `Extras/`）里的文件不重命名。

> ✅ **这里不会丢文件**：如果目录里**已经存在** `流浪地球2.mkv`，而另一个文件也要被改名成这个名字，引擎会先比**体积** —— 新来的更大 ⇒ 原有的那个改名**让位**成 `流浪地球2 (2).mkv`（**不删除**，计入 `displaced_targets`），新来的拿干净名；否则新来的自己加 ` (2)` 后缀。同一次运行里两个源文件抢同一个名字时同理（**体积最大的拿干净名**）。这两种情况都会计入 `name_collisions`（事实清单）与 `renamed_with_suffix`，明细见 `samples.*`，日志里各有一条 WARNING / INFO。⚠️ **刻意不静默覆盖**：`os.rename` 默认在目标同名时会 POSIX 静默覆盖，真实事故里全库跑丢过 114 个文件（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 L4）。

### 4.3 例子三：自定义库

这里"自定义"的含义是：不必局限于"在三个内置处理器里挑一个"，而是**你可以自己写一个处理器**
（命名方式、接受/拒绝目录正则、后缀白名单全部可配），再让媒体库用它。

**场景 A：只想建硬链接，不重命名（最常用）**

比如你的国漫/剧集已经命名整齐了，不想改名，只想在媒体库里出现一份：

| 字段 | 值 |
|---|---|
| 名称 | `国漫（只建链接）` |
| 类型 | `国漫`（自由标签） |
| 处理器 | **`hardlink_only`** |
| 启用 | ✅ 开 |
| 源目录 | `/vol1/1000/Download/qbittorrent/Anime-CN` |
| 目标目录 | `/vol1/1000/Library/Anime-CN` |
| 匹配分类 | `anime-cn` |
| 匹配标签 | `国漫` |
| 匹配路径前缀 | `/vol1/1000/Download/qbittorrent/Anime-CN` |
| 孤儿清理 | 建议先设 **关** |
| 日志文件 | 留空（自动生成；中文库名会被折成一串 `-`，建议手填一个 ASCII 文件名） |
| 权限模式 | **关**（默认，见 §8.9） |

**结果**：应用**原封不动**地把源侧的目录层级和文件名复制成硬链接（层级逐字节保留），**一个名字都不改**。这正是 `hardlink_only` 的意义。

**场景 B：复制一个内置处理器，改成自己的规则**

比如你想让 `4K电影` 用电影规则的**变体**（多拒绝几个目录、额外接受 `.srt`）：

1. 进「处理器」页 → 找到 `movie` → 点「复制」（或新建一个自定义处理器）；
2. 改 `id`（如 `movie-4k`）、把 `.srt` 加进 `extensions`、往 `reject_dirs` 里加你的特典目录正则；
3. 保存后回「媒体库」页新建库：类型随便写 `4K电影`，**处理器选 `movie-4k`**，源目录 `/vol1/1000/Download/qbittorrent/Movie-4K` → 目标 `/vol1/1000/Library/Movie-4K`。

完整的分步操作见 **§5.9**。

> 只想**沿用**电影规则、不做任何改动？那不叫自定义 —— 直接选内置 `movie` 处理器即可。
> 想确认"新处理器与最朴素的旧口径产出是否一模一样"？用 `legacy` 预设（§5.2）。

### 4.4 匹配规则详解（为什么我的种子没被触发）

qBittorrent 回调触发时，应用会遍历**所有已启用**的库，对每个库检查三项：

| 检查 | 何时算通过 | 留空时 |
|---|---|---|
| 分类 | 种子的分类**等于**库的「匹配分类」列表里的某一项 | 不检查这一项 |
| 标签 | 种子的标签与库的「匹配标签」列表**有交集**（比较时忽略大小写；分隔符是逗号、中文逗号、顿号、分号或空格） | 不检查这一项 |
| 路径 | 种子的内容路径**落在**库的「匹配路径前缀」中的某一项之下 | 不检查这一项 |

**三个条件是"与"（AND）**：**只要库填了几项，这几项就都必须通过**；任何一项不通过，这个库就被跳过。

**举个例子**（假设番剧库填了「匹配分类 = `ban`」+「匹配标签 = `番剧`」，路径前缀留空）：

| 回调带来的种子 | 分类是 `ban`？ | 标签含 `番剧`？ | 结果 |
|---|---|---|---|
| 分类 `ban`、标签 `番剧` | ✅ | ✅ | **命中**，建任务 |
| 分类 `ban`、标签 `国漫` | ✅ | ❌ | **不命中**（原因：标签没有交集） |
| 分类 `movie`、标签 `番剧` | ❌ | ✅ | **不命中**（原因：分类 `movie` 不在该库的分类列表里） |
| 分类 `ban`、**标签为空** | ✅ | ❌ | **不命中** —— ⚠️ 注意这一行：库填了标签条件、而回调**没带标签**时，算"不通过"，**不是**"跳过这一项" |

对照一下：如果这个库**只填了分类**、标签和路径前缀都留空，那么"分类 = `ban`"的种子不管标签是什么都会命中。

**三条铁律**：

1. **三项全空 = 不匹配**（刻意设计，防止"什么都没配"的库把整个下载目录都抓走）；
2. 命中多个库 → **全部入队**（会依次执行）；
3. `启用 = 关` 的库**完全不参与匹配**（但可以手动跑）。

> 记住方向：**条件填得越多 = 命中越严**。比如同时填了分类 `ban` 和路径前缀 `/vol1/1000/Download/qbittorrent/Bangumi`，那么"分类是 ban 但下到了 `Movie` 目录"的种子**不会**命中番剧库 —— 这在你想把两个番剧目录分开时很有用，但也常常就是"为什么没触发"的答案。

**回调返回里的 `ignored_details` 是排查神器**：它逐个列出**没命中**的库，并给出中文原因（例如「分类 Movie 不在该库的分类列表里。」「回调带的标签与该库的标签条件没有交集。」）。返回 `matched: 0` 时，直接看这些原因比猜快得多。

**在哪里看回调结果**：任务页/仪表盘能看到新任务；想看详细的回调结论，用接口

**【NAS 宿主】**（`<HOOK_TOKEN>` 换成设置页里的 token）：

```bash
curl -s -X POST "http://192.168.1.100:18081/api/hooks/qbittorrent?token=<HOOK_TOKEN>" \
  --data-urlencode "category=ban" \
  --data-urlencode "content_path=/vol1/1000/Download/qbittorrent/Bangumi/Show A"
```

## 5. 处理器（processor）：媒体库的重命名规则

**一句话**：一个**处理器**就是一套"怎么建链接、怎么改名"的规则；媒体库只是"用哪套规则、处理哪两个目录"。
这些规则**全部可配置**（WebUI 或 `/data/config/processors/*.yaml`），不写死在代码里。

### 5.1 一个处理器由四部分组成

| # | 部分 | 作用 | 例子 |
|---|---|---|---|
| 1 | **命名方式**（`naming`） | 新文件名怎么拼：段序列 + 具名表达式 | `{title}` ` S` `{season,pad:2}` `E` `{episode,pad:2}` `{suffix}` ⇒ `Show A S01E01.mkv` |
| 2 | **接受目录正则**（`accept_dirs`） | 标题文件夹下哪些子目录算"季目录"（并从中取季号） | `^Season (\d+)$`，`season_group: 1` |
| 3 | **拒绝目录正则**（`reject_dirs`） | 命中就**整棵子树跳过** | `(?i)^(SP\|CM\|OP\|ED)$`、`(?i)^特典$` |
| 4 | **接受后缀**（`extensions`） | 哪些文件参与重命名（**大小写敏感**） | `[.mkv, .mp4, .ass]` |

另外两个决定行为的字段：`kind`（`rename` 或 `hardlink_only`）与 `selection.per`
（`file` = 每个匹配文件都改名；`extension` = 同后缀只留体积最大的那个，电影用）。
再加上**每个媒体库一条日志**（`log_file`，默认取该处理器登记的日志名、按库唯一化，见 §5.6）。

### 5.2 内置三个处理器与两个预设

| id | 名称 | kind | 说明 |
|---|---|---|---|
| `hardlink_only` | 只建硬链接 | `hardlink_only` | 不改名；由原生实现 `app/processors/hardlink.py` 执行 |
| `bangumi` | 番剧 | `rename` | 番剧规则（`Season NN` + 集数按 **9 条有序规则**识别：`第N集` / `Episode N` / `SxxExx` / `[NN]` / `EP N` / `#N` / `- N` / `E N` / 裸数字 → `S01E01`；认不出集数就保留原名） |
| `movie` | 电影 | `rename` | 电影规则（`<文件夹名>.<后缀>`，每个后缀只留最大者） |

内置处理器**不可删除**，只能重置（处理器页「恢复默认」）。重置时可选：

| 预设 | 含义 |
|---|---|
| `default` | 推荐默认值：**相对 `legacy` 的四处增量** —— 番剧与电影各多一份拒绝目录规则（增量 ①②）、番剧的「集数兜底」**留空**（认不出集数就**保留原文件名、不改名**，增量 ③）、番剧的**集数规则**是 **9 条带边界约束的有序规则**（增量 ④，见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3.2） |
| `legacy` | **最朴素的旧口径**：`reject_dirs: []` + 「集数兜底」是字符串 `None` + **集数规则就是两条宽松老规则**（含大小写敏感的后缀白名单、没有集数号也照样改名成 `ENone`）。这套口径被冻结成**黄金值**，由 `tests/test_processor_engine.py` / `tests/test_bangumi_episode_rules.py` / `tests/test_rename_extensions.py` 守护 |

> **想要最朴素的旧口径就选 `legacy`。** 两个预设的差异只允许出现在**已登记的有意增量**上
> （见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3.2，共四处）：番剧与电影的 `reject_dirs`、番剧的
> `episode_fallback`、番剧的 `episode_patterns`（9 条规则 vs 两条宽松老规则）。
>
> ⚠️ **注意**：升级镜像**不会**自动改**已经存在**的处理器 —— 它们是首次播种后独立存在
> （DB / `processors/*.yaml`）的。想让现有的番剧处理器也"认不出集数就保留原名"、并用上新的
> 集数规则，二选一：
> ① 改 `/data/config/processors/bangumi.yaml`（`episode_fallback: null`；`episode_patterns` 换成
> [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3 里那 9 条 —— 配置文件是**整份规格**，改之前先照 §3 的
> YAML 示例核对自己的字段）；WebUI 与配置文件双向同步，默认 5 秒一轮自动生效；
> ② 处理器页「恢复默认」选 `default`（会一并覆盖你对它的其它自定义改动）。
> ⚠️ **「集数兜底」的"留空"**：清空输入框、配置文件里写 `episode_fallback:`（YAML 空值）、或库里早先存下的
> 空串，都按"没配兜底"处理（认不出集数就**保留原文件名**）。只有**非空字符串**才算兜底字面量。
> **新建**的处理器默认就是留空（`null`）。

**两个内置处理器的默认值里哪些是"有意的行为增量"**（`legacy` 都不带这几项）：

| 处理器 | 字段 | 默认值 |
|---|---|---|
| `bangumi` | `reject_dirs` | 一份固定的默认名单（`legacy` **不带**这一项）：SP/CM/OP/ED 系列、Scan/Scans、CD/CDs、映像特典/特典CD、Preview/Previews、`Scan (Vol.N)`、`Vol.N`、EXTRA/Bonus/Menus/Music、Subtitle/Subtitles、ScreenShot/ScreenShots、NCOP/NCED —— 全部 `(?i)^…$`（大小写不敏感、整名匹配） |
| `movie` | `reject_dirs` | **用户指定**（`legacy` **不带**这一项）：必选 `特典`/`CD`/`扫图`/`scans`，另加 SP、Menu、Preview、EXTRA、Bonus、NCOP/NCED、Sample |
| `bangumi` | `episode_fallback` | **留空（`null`）**：认不出集数就**保留原文件名**（不把 `None` 这类字面量命名进文件名，同一作品的多个压制版本因而不会撞名互相覆盖） |
| `bangumi` | `episode_patterns` | **9 条带边界约束的有序规则**（`legacy` 那两条没有"这里不可能是集号"的判断 ⇒ 会把 `Show - 1920x1080.mkv` 认成第 19 集、把 `[1AE35F3A]` 里的 `E35` 认成第 35 集；示例语料 8534 个文件名里前者这类误判 21 个 ⇒ 现行规则 0 个）。逐条正则与正/反例见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3 与 §3.2 增量 ④ |

> ⚠️ 两条都**不会**拒绝发布组/压制组前缀（`[ANi]`、`[VCB-Studio]` 这类**不在**拒绝范围内）。想拒绝什么，自己往 `reject_dirs` 里加。

### 5.3 硬链接部分由谁执行

**硬链接由应用自己的原生实现执行**：`app/processors/hardlink.py` —— 打印文案、日志行格式、扫描顺序都被**冻结成黄金值**，
由 `tests/test_hardlink_native.py` 用「同一棵树、A 组五条场景断言」锁死。
所以容器自带全部执行体，不依赖宿主上的任何东西，镜像可以原样搬到别的设备。见 [FAQ.md](FAQ.md) 第 28 问。

### 5.4 在哪儿改规则（WebUI）

侧边导航 →「**处理器**」（`#/processors`）：

- **列表页**：每个处理器的 id / 名称 / kind / 是否内置 / 被哪些媒体库引用；
- **编辑页**（`#/processors/{id}`）四大块，与 §5.1 的四部分一一对应：
  1. **命名方式**：可视化"段"列表（上下移、增删、选参数、`pad`、`literal` 文本输入）+ **实时预览**；另有一个独立的「命名表达式」区域（键值对增删）。这块顶部还有一个**「命名模板」**输入框（见 §5.4.1），以及 12 个变量按钮与「按模板生成段序列」；
  2. **接受目录正则**：可增删的 `{pattern, season_group}` 行，会显示正则能否编译；
  3. **拒绝目录正则**：可增删的 `{pattern}` 行（**命中即整棵子树跳过**）；
  4. **接受的后缀名**：可增删的 chips，必须以 `.` 开头；
- 顶部两个按钮：**「保存」**（全量替换）与**「恢复默认」**（二次确认，可选 `default` / `legacy`，弹窗里会说明两者差异）。

> ⚠️ **改了处理器，所有用它的媒体库都跟着变**（立即生效于下次运行）。改之前先看列表页的引用清单。
> 只想让**某一个库**换个命名方式？别动处理器 —— 用库编辑页的「本库规则覆盖」（§5.4.2）。

#### 5.4.1 命名模板：像 calibre 那样挑字段

「命名模板」是一个文本框，你写什么就按什么拼：

```
[{season}-{episode}] {title}{suffix}      →  [01-01] 作品名.mkv
{title}/{title} - {episode}{ext}          →  作品名/作品名 - 01.mkv（含 / 会把结果落进子目录）
```

- `{名字}` = 该变量当前的值，`{episode:02}` = 补零到 2 位（`{season:02}` 同理）；`{{` / `}}` 是转义的花括号；
- 可用变量就是 §5.5 表里的 12 个，再加你在「命名表达式」里定义的名字（按钮会直接插进光标处）；
- 写错的变量名**会立刻在输入框下面变红**并说明，不用等保存；保存后落库的是**编译结果**（段序列），
  所以运行时引擎不依赖模板这个概念。

> 模板与段序列是**同一个东西的两种写法**：处理器编辑器里两者都给你（同时填时**模板优先**），
> 库级覆盖里只给模板（更简单）。

#### 5.4.2 本库规则覆盖：只给某一个库改规则

库编辑页（`#/libraries/{id}`）的「**本库规则覆盖**」卡片：

- **开关关着** = 完全跟随处理器（保存时提交 `{}`，把已有覆盖清掉）；
- **开关打开** 后可逐项覆盖，改成你想改的那几项即可，**没碰的字段照样继承处理器**：
  - 命名模板（+ 变量按钮 + 实时预览）；
  - 接受 / 拒绝目录正则（带季号捕获组的那一列只对接受规则有意义）；
  - 文件作用域（`subdir` / `title`）；
  - 本库的后缀白名单（优先级**最高**，压过设置页的全局白名单与处理器清单）。
- 校验在保存时做两遍：先看覆盖自己读不读得懂（正则能不能编译、变量认不认识），
  再把它**合并到处理器规则上**跑一遍完整校验 —— 所以「处理器是 `title` 作用域、你却给这个库写了
  `accept_dirs`」这种跨层冲突也会被拦下来，并告诉你哪一层冲突。

**什么时候该用它**：「同一个番剧处理器，但某一个库想用方括号命名」「某个库想额外拒绝 `SP` 目录」
「某个库只认 `.mkv`」——这些都不该去改处理器（那会波及所有引用它的库）。

### 5.5 命名段可用的名字（速查）

| 名字 | 取值 | 例子 |
|---|---|---|
| `title` | 标题文件夹名 | `Show A` |
| `filename` / `stem` / `ext` / `extname` | 原文件名 / 去扩展名 / 带点扩展名 / 不带点扩展名 | `Show A 01.mkv` / `Show A 01` / `.mkv` / `mkv` |
| `season_raw` / `season` | 季号原值 / 补零两位（**无季号时 `season_raw` 是空串，而 `season` 是 `"00"`**；只有 `file_scope=title` 的处理器 `season` 才是空串） | `1` / `01` |
| `episode_raw` / `episode` | 集数原值 / 按 `pad` 补零。所有 `episode_patterns` 都没命中**且没配** `episode_fallback`（空串也算"没配"）时，两者都是**空串**；此时若命名引用了它们，该文件**保留原文件名、不改名**（计入 `result.kept_unresolved_episode`，日志一行 `Kept (no episode): …`）。配了 `episode_fallback`（例如 `legacy` 预设的字符串 `"None"`）则属于"已解析"，照旧渲染那个字面量 | `1` / `01` |
| `suffix` | `.ass` 用多段后缀（如 `.chs.ass`），其他文件等于 `ext` | `.chs.ass` |
| `works_dir` / `rel_dir` | 库的 `source_dir` / 作用域目录相对标题文件夹的路径 | `/vol1/1000/Download/qbittorrent/Bangumi` / `Season 1` |

`naming.expressions` 里可以写 Python 表达式（可用 `re`、`os`、`len`、`str`、`int`、`sorted`、`min`、
`max`，以及 `zfill` / `splitext` / `basename` / `ass_suffix`）。这是为"可拓展、不写死"付出的代价：
**能在配置文件里写表达式，就等于能在容器里执行代码** —— 只有你自己能改 `/data/config/` 时才用它。

> **内部键 `episode_resolved`**（`true` / `false`）：表示"这个文件的集数解析出来了吗"
> （命中 `episode_patterns` 或配了 `episode_fallback` 都算 `true`）。可以用在 `naming.segments[].param`
> 与表达式右值里（例如 `{param: episode_resolved}` 做条件拼接、或 `episode_resolved and ... ` 之类的表达式）；
> **模板写法 `{episode_resolved}` 也认**（模板的校验名单 = 12 个变量 + `episode_resolved` + 你自己在
> 「命名表达式」里定义的名字）。它仍然**不在**变量按钮表里（那是给 12 个常规变量的）。

> **写错变量名会怎样（KI-11）**：命名段里写了一个"不存在"的名字（例如手改 YAML/API 提交
> `{"param": "titlee"}`）——
> * **保存期**：**被拦住**（422，提示「段里用了未知变量 {titlee}。可用变量：…；自定义名字要先在
>   naming.expressions 里定义。」）。编辑页的下拉框里，不在可用名单里的名字会带一个 **（未知）** 标记，
>   模板框里写错会当场变红（与保存期同一套名单）。
> * **运行期**（库里早先存下的老配置、手改过的 YAML 不走保存期校验）：**照旧跑完**，但那一段**什么都不输出**
>   ⇒ 文件名少一段。**这件事会报出来**：任务结果 `unknown_params` 计数 +
>   `samples.unknown_params` 明细 + 每个文件一条 **WARNING** 日志（「命名里的未知变量被留空（文件名少了一段）：…」）
>   + 任务告警里一条汇总（带改法）。**任务仍算成功** —— 想查就跑一次任务，看任务详情里的告警与 `unknown_params`。

### 5.6 每个媒体库一条日志（都在 `/data/logs/`）

| 类别 | 文件 | 作用 |
|---|---|---|
| 硬链接日志 | `hard_links.log` | 建链阶段的**兼容与审计**记录。**它只写"记账行"** —— 体积登记与孤儿目录清理两类；uvicorn 访问日志、任务日志等**不会**进这个文件（见下方 📌）。⚠️ **跳过判断看的是每库账本，不是这个文件**（见 §5.7 与 §11.4） |
| 每库一条重命名日志 | `<log_file>`，默认取该处理器登记的日志名（`bangumicache.log` / `moviecache.log` / `hardlink_only.log` / 自定义 `<id>cache.log`），被其它库占用时加 `-2`/`-3` | "这个标题文件夹已经重命名过了"（含体积与时间戳） |
| 任务日志 | 数据库（任务详情页轮询） | 你在网页上看到的逐条日志 |

**三条硬规则**：日志**必须**都放在 `/data/logs/`，**不允许**分子目录；表单里的「日志文件」**只能填文件名**
（含 `/` 或 `..` 会被拒绝）；新建库时文件不存在会建一个空 `{}`，**不会**从任何外部目录导入。
细节与自查命令见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §2.8。

> 📌 **库日志文件只记"记账行"**：`hard_links.log` 是**数据型**文件 —— 登记"哪个一级文件夹
> 处理过、当时多大"与"哪个孤儿目录被清理过"。因为写它的处理器把 `FileHandler` 挂在 **root logger** 上
> （这是必须的，见 [`docs/contracts/ARCHITECTURE.md`](../contracts/ARCHITECTURE.md) §6.5），而 root 会收到**整个应用**的日志，
> 所以它有一张白名单：只有这两类行能落进文件，其余（uvicorn 访问日志、任务执行日志、异常回溯…）
> 一律挡在文件外。**只过滤、不清理** —— 已经写进去的历史行一个字节都不删，
> 可以放心长期保留；过滤也**不影响**任务详情页与 `docker compose logs`（它们照旧收到全部记录）。

### 5.7 配置文件与 WebUI 双向同步（默认 5 秒一轮）

- 规则同时存在于**数据库**（运行时真源）与**文件**（`/data/config/libraries.yaml`、`/data/config/processors/<id>.yaml`）；
- **在 WebUI 保存** → 同一个请求里就把文件写好（原子替换），文件几乎立刻就是新的；
- **你在宿主机上改文件** → 后台线程每 `config_sync_interval_seconds`（**DB 设置项**，默认 **5 秒**、区间 0–86400；**不是环境变量**）比对一次，
  发现被外部改动就导入数据库，页面提示「配置文件已从磁盘重新导入」；
- **导入失败**（YAML 语法错、正则编不过、后缀没以 `.` 开头…）→ **数据库不受影响**（继续用旧规则），
  页面顶部出现**红色横幅**与错误详情，**你的文件不会被覆盖**；改好后会自动再导入，也可点「重新从磁盘导入」；
- **删除语义**：文件里被删掉的**自定义**处理器 / 媒体库会随导入一并删除；**内置处理器永不删除**；
- 想彻底关掉自动导入：把设置项 `config_sync_interval_seconds`（**DB 设置项，不是 env**）设成 `0`，之后只在点按钮时导入。

> 备份与恢复这些文件、以及"两边同时改了怎么办"，见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §2.6.3 与 §7.5。

### 5.8 配置校验错误对照表（导入失败时看这里）

| 报错里的关键词 | 意思 | 怎么修 |
|---|---|---|
| `schema_version` | 第一行不是 `schema_version: 2` | 补上（必须在第一行） |
| `id` | id 不合规，或与文件名不一致 | 匹配 `^[a-z][a-z0-9_-]{1,31}$`，且文件名 = `<id>.yaml` |
| `kind` | 不是 `rename` / `hardlink_only` | 二选一 |
| `extensions` | 有后缀没以 `.` 开头 | 一律写 `.mkv` 这种带点形式（大小写敏感） |
| `pattern` / `正则` | 正则编译不过 | 用**单引号标量**写正则，先在电脑上试一下 |
| `season_group` | 指向了不存在的捕获组（缺省 1，合法 0 或 ≥1） | 数一下正则里的 `(...)` 序号（从 1 开始）；**不打算取季号就显式写 `season_group: 0`**（等价于"只用这条正则判断接受"，此时 `season_raw` 是空串、`season` 会补零成 `"00"`） |
| `segments` | 段里出现了 `param` / `literal` / `pad` 之外的键 | 只保留这三个键 |
| `param` / 未知名字 | 段或表达式引用了不存在的名字 | 对照 §5.5 的名字表 |
| `expressions` | 表达式语法错，或用了不允许的名字 | 只用 §5.5 列出的函数 |
| `episode_patterns` | 命名用到 `episode`，但没配集数正则 | 补 `episode_patterns`，或改掉命名段。**反过来**：如果你**故意**想让"认不出集数"的文件**保留原文件名**，就把 `episode_fallback` 留空（`null`）—— 这不是错误，而是会**可见地跳过**（`result.kept_unresolved_episode` + 日志 `Kept (no episode): …`） |
| `log_file` | 含 `/` 或 `..`，或不是文件名 | 只填文件名（如 `moviecache.log`） |
| `processor_id` | 媒体库引用了不存在的处理器 | 先建处理器，或改媒体库的处理器 |
| `引用` / `被引用` | 要删的处理器还有媒体库在用 | 先改那些库的处理器（列表页能看到引用清单） |

（同样的表在 [`docs/contracts/API.md`](../contracts/API.md) §5.7.8，带字段名与完整示例。）

### 5.9 新增一类媒体库：从零到跑通（完整步骤）

假设你要管一个 `/vol1/1000/Download/qbittorrent/Documentary`（纪录片），命名用 `<文件夹名>.<后缀>`，
但要多拒绝一个 `Extras` 目录、额外接受 `.srt`：

1. **先看最接近的内置处理器**：处理器页打开 `movie`，看它的 `naming.segments`
   （应为 `title` + `.` + `extname`）与 `selection.per: extension`；
2. **复制一份**：点「复制」，`id` 改成 `documentary`，`name` 改成 `纪录片`，
   `description` 写清来源（例如"基于 movie，2026-10 加 srt"）；
3. **改规则**：
   - `extensions: [.mkv, .mp4, .srt]`（注意带点、大小写敏感）；
   - `traverse.reject_dirs` 加一行 `{pattern: '^Extras$'}`；
   - 想在名字里带年份，就往 `naming.segments` 里插 `{literal: '.'}` + 一个表达式；
     改完看编辑器里的**实时预览**确认结果；
4. **保存**：这一步同时把 `/data/config/processors/documentary.yaml` 写出来；
5. **建库**：媒体库页「新建」→ 名称 `纪录片`，类型随便写 `纪录片`，**处理器选 `documentary`**，
   源目录 `/vol1/1000/Download/qbittorrent/Documentary` → 目标目录 `/vol1/1000/Library/Documentary`，
   匹配分类 / 标签 / 路径前缀按 §4.4 填（**至少填一项**，别全空）；
6. **预检 + 试跑一个小文件夹**：先点「预检」确认结构与文件系统 OK，
   再用「手动运行 → 指定文件夹」**只处理一个作品**，去任务详情页看日志里的 `Renamed:` 行；
7. **确认无误再全量跑**，然后把它接进 qBittorrent 回调（§9）或扫描补偿（§8.4）。

> 全程**不需要写 Python**、不需要改代码、不需要重建镜像。规则改错也不会破坏已有文件：
> 改名只发生在 `/vol1/1000/Library` 一侧；源目录应用**代码层从不写**（容器里没有把源目录挂成只读这一层保护，靠代码层 + 任务前后源完整性核对接管 —— [`docs/guides/FAQ.md`](FAQ.md) 第 4 问）。

### 5.10 三条别踩的线

1. **不要改 `/vol1/1000/Library` 里文件的内容**：硬链接与下载原文件共享同一份数据，原地编辑媒体库那份 = 改下载那份；
2. **不要让两个处理器写同一个 `log_file`**：日志是"已处理"的判据，混用会让库之间互相干扰（留空自动生成就不会撞）；
3. **`reject_dirs` 命中是"整棵子树跳过"**：它同时作用于标题层与子目录层 —— 写正则时别把正常的 `Season 1` 也匹配进去。

> 换路径、换数据卷时的注意事项，见
> [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §6.5 与 [`docs/guides/FAQ.md`](FAQ.md) 第 23–25 问。

## 6. 跑任务：手动运行、作品记录、重做单个作品、重试

有四种方式让任务跑起来：

| 方式 | 谁触发 | 什么时候用 |
|---|---|---|
| **自动回调** | qBittorrent 下载完成 | 日常主力（配好后不用管） |
| **定时扫描** | 应用自己（需打开 `scan_enabled`） | 回调漏了的补偿 |
| **手动运行** | 你在网页上点 | 补跑、试跑、只处理某一个 |
| **重试** | 你对失败任务点「重试」 | 修好问题后重来 |

### 6.1 手动运行（全量）

**媒体库页 → 选中某个库 → 「运行」 → 范围选「全部」 → 执行。**

等价于"把这个库的源目录下所有一级文件夹都过一遍"。已经处理过、体积没变的会**跳过**（这是幂等，不是失败）。

**去哪看结果**：任务页 → 新出现的那条任务 → 点进去看日志。

### 6.2 手动运行（只处理某一部剧 / 某一个文件夹）

**媒体库页 → 该库 → 「运行」 → 范围选「指定文件夹」 → 填一级文件夹名 → 执行。**

填的是**一级文件夹名**，不是完整路径：

| 你的实际路径 | 填 |
|---|---|
| `/vol1/1000/Download/qbittorrent/Bangumi/Show A` | `Show A` |

**这就是"只处理某一部剧"的正确用法。**

**【NAS 宿主】**等价命令：

```bash
curl -s -b cookies.txt -X POST http://192.168.1.100:18081/api/libraries/1/run \
  -H 'Content-Type: application/json' \
  -d '{"scope":{"mode":"folder","folder":"Show A"},"force":false}'
```

### 6.3 「手动重链」和「手动重命名」到底是不是两个按钮？

**不是。** 应用的一次「运行」是按**该库的处理器**完整执行：先建硬链接、再重命名（`hardlink_only` 的库只有前者）。

那"只想重新执行重命名"怎么做？—— **同一个动作**，但**效果上只有重命名阶段真的干活**：

- **建链阶段**：因为源侧体积与日志记录一致 → 打印"文件夹已记录且体积一致，跳过" → 什么都不做；
- **重命名阶段**：它有自己的缓存判定（体积 + 时间戳），需要时会**真的重新改名**。

所以：**想对某个媒体库里的剧集立即重新执行一遍重命名，就对该库的那个一级文件夹点一次「运行」**。硬链接部分会因为幂等自动跳过，不会重复造文件、也不会破坏已有链接。

> **有专门的功能做这件事**：打开**「作品记录」页**（左侧栏的「作品记录」，或媒体库卡片上的「作品记录」按钮）→ 勾选作品 → 「立即重命名」。它**只跑重命名、不建链**，所以不用再靠"点一次运行、指望建链阶段自动跳过"了。

### 6.4 重做单个作品

**整库范围的「强制重跑」不提供。** 运行弹窗里没有那个开关，应用固定以 `force=false` 调用；如果你用命令行直接发 `force=true` + 整库范围（`scope.mode="full"`，默认值），服务端一律返回 **400**：

```text
{"detail": "整库强制重跑已停用：force 只允许配合 scope.mode='folder'（单个作品）使用。要重做作品，请到「作品记录」里删除对应作品的记录，下次运行时这些作品会自动补做，其余作品不受影响。"}
```

**为什么不提供**：整库 force 会让**建链阶段**把已经改过名的文件按"原名"再链一份（目标里于是同一个 inode 出现两个目录项），**重命名阶段**接着多出一个 `xxx (2).mkv` 后缀 —— 越点越乱。

**要重做某个作品，走下面两条正道之一**：

| 途径 | 操作 | 效果 | 注意 |
|---|---|---|---|
| **① 只重命名** | 「作品记录」页（左侧栏入口，或媒体库卡片上的「作品记录」按钮）→ 勾选作品 →「立即重命名」 | 立即对该作品跑一遍**重命名**（`kind="rename"`，202 建任务）；**不建链** | 处理器是 `hardlink_only` 的库会返回 400（它根本没有重命名规则）；库已停用返回 409 |
| **② 删记录后自动补做** | 「作品记录」页（同上）→ 勾选作品 →「删除记录」 | 删掉这些作品的记录 → **下次运行本库时自动补做**（重新建链 + 按规则重命名），其余作品不受影响 | 需**二次确认**；删除会**连带删除目标目录里的整个作品文件夹**，见下 |

> ⚠️ **删除的三个后果（务必看完再勾）**
> 1. **源目录一个字节都不动。** 硬链接只是指向同一份数据的**另一条目录项**，删掉它**不减少**源文件的数据 —— 你下载的文件完好无损。
> 2. **目标是整个作品文件夹被删掉**（按名字走 `shutil.rmtree`，符号链接只删链接本身），**无法撤销**。所以弹窗里的红色警告要读完再点「确定删除」（不需要勾选确认框）。
> 3. **目录里"不是本应用建立的硬链接"的文件会被一并删掉。** 确认框会逐作品列出目标路径 / 文件数 / 总字节数 / **非硬链接文件数**；只要这个数大于 0，就会显著警告"该目录里有 N 个不是本应用建立的硬链接（可能是你自己放进去的文件），删除会一并删掉它们"。**先看一眼这个数字再决定。**
>
> **删除流程是一次弹窗确认**（不需要勾选确认框），误点不会直接执行：点「删除记录」→ 弹窗先摆出 `dry_run=true` 的**预演清单**（服务端只回执，**磁盘一个字节不动**）→ 你在弹窗里点「确定删除」→ 执行（`dry_run=false, confirm=true`）→ 结果弹窗列出每个作品的成功/失败与统计。

> ⚠️ **force 还留下的唯一用法（以及它照样带着的老风险）**
> 整库 force 没了，但 `force=true` 配合 `scope.mode="folder"`（单个作品）仍然可用 —— 「立即重命名」内部也是这么调的（`payload.force=true`）。它照样会带来这两类现象，**知道就好、不必惊慌**：
> 1. 建链阶段会对**已存在**的目标文件再次执行 `os.link`，产生一批 `创建硬链接失败: ... File exists` 的报错。**这些报错无害**：建链阶段不覆盖、不删除已有文件（`except` 分支：打印后继续）。应用会把"目标就是**同一个 inode 的硬链接**"的那些改判成**幂等跳过**（结果里记在 `already_linked`，计入 `skipped`），所以任务**不会**因此显示失败；只有"同名但**不是**硬链接"（inode 不同）才算 `link_failed`。
> 2. 重命名阶段**不覆盖**：目标名被占用时，L2「防丢」按体积判定 —— 体积最大的拿干净名，其余加 ` (2)`、` (3)`… 后缀保留；目标盘上原有的同名文件比新来的小时会改名**让位**（**不删除**）。找不到空位（` (2)`…` (999)` 全占满）时**保留原文件名**并记一条 `error`，**绝不覆盖**。⚠️ **刻意不静默覆盖**：`os.rename` 默认在目标同名时会 POSIX 静默覆盖（Windows 上则报 `[WinError 183]`）。**源下载文件不受影响。**
> 3. ⚠️ **"无害"要说清楚**：上面第 1 条那批"幂等跳过"只覆盖**同名同 inode**；建链阶段用的是**源目录里的原名**，所以对**已经改过名**的作品发单作品 `force`，目标里仍会出现**同一 inode 的第二个目录项**，重命名阶段再多出 `xxx (2).mkv` —— 也就是整库 force 被撤掉所针对的那个现象（目标从 2 个文件变 4 个，`nlink=3`，**内容还是那一份、不占额外空间**）。详见 [`docs/meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-9。**因此单作品 force 只适合"目标已经空了/残缺"的排查场景，不要拿它当"补文件"的工具。**
> 4. `force` 只作用于**这一次任务**，不会永久改变幂等行为。
>
> **结论**：force 是排查工具，不是日常操作。**不要反复点。**

> 📌 **账本是"作品级"的，两本账的差集只做提示。** 「作品记录」页的**信息行**里会标出两本账对不上的名字（`rename_missing`：在作品账本里、但重命名缓存里没有；`rename_only`：只在重命名缓存里、账本里没有），以及表格里的"目标里还在不在"（`target_exists`）和"重命名记了没有"（`rename_recorded`）。**这些标记只做提示，应用永远不会据此自动"修复"** —— 你在目标目录里的**手动增删改一律保留**，不会被自动改回去（差集**按整个库算**，不受当前页影响）。想彻底重做，就只有上表的途径 ②（删记录后重跑）。

> ⚠️ **账本为空的库必读**：应用把"哪些作品处理过了"的判据记在**每库自己的账本**里；账本为空时（换了数据卷、清了 `data/`）第一次**全量**运行会把**每个作品重新建链一次**；你已经在目标里改过名的文件会以**原名**再链一份（同一 inode 的第二个目录项），重命名阶段于是多出 `xxx (2).mkv` 后缀。**不丢数据**（同一 inode，内容还是那一份），但会多出重复文件名。建议：用**新库**、或先**清空目标目录**、或**逐作品**处理。
>
> 判据按库分开的理由：如果它**全局共用**（键 = 源目录 + 作品名 + 体积），那么①两个库指向同一个下载目录时，A 库跑完后 B 库会被"体积一致，跳过" ⇒ **B 库一个链接都不建**；②同一个库换目标目录也会照样跳过。**按库分开就避免了这两点。**

### 6.5 查看「作品记录」：一行告诉你这个作品还算不算数

**「作品记录」是一整页，不是弹窗。** 两个入口进的是同一个页面：

- **左侧导航栏 →「作品记录」**（路由 `#/works`）；
- **媒体库卡片 →「作品记录」按钮** → 同一页，并把**库选择器预选**成这个库（`#/works/<库 id>`；筛选状态写在地址里，浏览器前进/后退可用）。

页面从上到下是：

| 部位 | 内容 |
|---|---|
| 库选择器 | 选看哪个库的记录；从媒体库卡片进来时**已预选**成那个库（照常可以在这里切换：切换会**清空已勾选的作品**并回到第 1 页） |
| 搜索框 | 只搜**作品名**（= 源目录里的**一级文件夹名**），子串匹配，**ASCII 大小写不敏感** |
| 每页条数 | `25 / 50 / 100 / 200`，**默认 50**，配合底部翻页控件 |
| 信息行 | 「命中 N 条 / 本库共 M 条」+ 两本账的差集提示（`rename_missing` / `rename_only`，**按整个库算**，不受当前页影响） |
| 表格 | 一行一个作品（列见下）；每行有复选框，表头可**全选** |
| 底部 | 翻页控件 +「已选 N 项」+「**立即重命名**」「**删除记录**」两个按钮（**未勾选时禁用**） |

> 💡 **搜索的三条规矩**：① **只**匹配作品名 —— **不搜**目标路径、作品内部的文件名、时间；② `%`、`_`、`\` 按**字面**字符找，**不是**通配符；③ 只搜**当前选中的这个库**的记录，搜别的库请先切库。

> 💡 **勾选是跨页保留的。** 第 1 页勾几行、翻到第 2 页再勾几行，「已选 N 项」会累加，两个按钮作用于你勾的**全部**作品 —— 可以先把要处理的作品凑齐，再一次性点。

含义速查：

| 列 | 显示 | 说明 |
|---|---|---|
| 作品 | 一级文件夹名 | 源目录里的那个作品文件夹名（搜索匹配的就是它） |
| 体积 | `123 MB`（已链接 12 个文件） | 记录时的总体积 / 建链阶段实际写入记录的文件数 |
| 目标目录里是否还在 | 在 / **已不在** | 目标目录里这个作品文件夹还在不在（被手动删过 ⇒ 已不在）；顺带显示它**现在有多少个文件** |
| 是否已记录重命名 | 已记录 / **未记录** | 本库的**重命名缓存**里还有没有这个作品 |
| 记录时间 | 时间戳 | 这条记录是什么时候写下的 |
| 目标路径 | 完整路径 | 这个作品在目标目录里的绝对路径 |

**两个动作分别做什么：**

- **「立即重命名」**：只对**你勾选的那些作品**跑一遍重命名（`kind="rename"`，建一个排队任务、返回 202）。它**只碰目标库，从不碰源目录**；处理器是 `hardlink_only` 的库返回 400，库已停用返回 409。**不建链。**
- **「删除记录」**：**破坏性操作**，一次弹窗确认（不需要勾选确认框）—— 点「删除记录」后弹窗先做 `dry_run=true` **预演**（列出每个作品的目标路径、文件数、总字节数，以及**有几个不是本应用建立的硬链接**），你点「确定删除」才真正执行。它删**三样东西**：
  1. 这个作品在**本库账本**（`link_records`）里的那一行；
  2. 这个作品在**重命名缓存**里的条目；
  3. 目标目录里**整个作品文件夹**（`shutil.rmtree`；符号链接只删链接本身）。

  **源（下载）目录一个字节都不动。** 删完之后，下次运行这个库时它会**自动重新建链 + 按规则重命名**，其余作品完全不受影响。⚠️ 目标文件夹里**不是本应用建立的硬链接**的文件会被一并删掉 —— 预演里的那个数字大于 0 时，先看一眼再决定。

> 📌 **账本是"作品级"的：删掉目标里的某个文件，普通运行不会把它补回来。** 记录说的是"这个作品做完了"，应用**不会去数目标目录里少了哪个文件**。要让某个作品被重做，只有两条正道：**删掉它的记录后重跑**（会连带删掉目标里的整个作品文件夹，见上）、**用「立即重命名」只重跑改名这一步**。
>
> ⚠️ **别把单作品 `force=true` 当成"补文件"的工具**（`POST /api/libraries/{id}/run` + `scope.mode="folder"`，仅 NAS 宿主可用）：它会让建链阶段把**已经改过名的文件按原名再链一份** —— 目标里同一个 inode 于是有**两个目录项**（`… S01E01.mkv` 与 `… S01E01 (2).mkv` 并存，`目标目录现有 N 个文件` 从 2 变 4），这正是整库 force 被撤下的同一个现象（见 §6.4）。它只适合"目标目录已经空了/残缺"的排查场景；想让作品回到干净状态，走**删记录后重跑**。证据见 [`docs/meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-9。
>
> 为了不重蹈"越点越乱"的覆辙，**整库强制重跑依旧停用**（返回 400），见 §6.4。

出现「已不在」「未记录」怎么办，见 [`docs/guides/TROUBLESHOOTING.md`](TROUBLESHOOTING.md)。

### 6.6 重试（retry）

任务失败后，修好根因（权限、挂载、跨挂载…），然后：

**任务页 → 找到那条失败任务 → 「重试」**。

它用**完全相同的配置**新建一个任务，原任务记录保留（便于对比）。只有 `失败` / `已取消` 的任务能重试；正在跑的任务只能等它跑完。

**【NAS 宿主】**等价命令：

```bash
curl -s -b cookies.txt -X POST http://192.168.1.100:18081/api/tasks/42/retry
```

### 6.6 取消任务

- **排队中（queued）** 的任务可以取消；
- **执行中（running）** 的任务**不能中断** —— 这是刻意的：应用正在做"读-改-写整份日志文件"的操作，硬杀会破坏一致性。请等它跑完（通常几秒到几分钟）。

## 7. 任务页：状态含义、失败原因解读、重试

### 7.1 任务页能做什么

顶部有搜索与筛选：

| 控件 | 作用 |
|---|---|
| 搜索框 | 按关键词搜（库名、文件夹名等） |
| 状态筛选 | 只看失败 / 只看成功 … |
| 媒体库筛选 | 只看某个库的任务 |

列表按时间倒序（最新的在最上面）。点任意一条 → 任务详情（含 `result` 计数与完整日志）。

### 7.2 状态含义

| 状态 | 中文 | 含义 | 要做什么 |
|---|---|---|---|
| `queued` | 排队中 | 已入队，等前面的任务跑完 | 等着（队列串行） |
| `running` | 执行中 | 正在跑 | 等着 |
| `success` | 成功 | 执行完成 | 看 `result` 里的计数确认是否真的链了/改了。**可能有部分失败**，见下 |
| `failed` | 失败 | 执行体抛异常，或所有文件都建链失败 | 看 `error` + 日志，修好根因后**重试** |
| `skipped` | 跳过 | 无需处理（源目录里没有符合条件的一级文件夹，或体积一致全跳过） | 通常不用管。刚下载的新内容却显示跳过 → 看 [`docs/guides/FAQ.md`](FAQ.md) 第 7 问 |
| `cancelled` | 已取消 | 在排队时被你取消了 | 需要的话重新跑 |

> ⚠️ **`success` 不等于"每个文件都成功了"。** 看详情里的计数：
>
> | 计数 | 含义 |
> |---|---|
> | `linked` | 新建的硬链接数 |
> | `skipped` | 因体积一致被跳过的文件夹数 |
> | `link_failed` | 建链接失败的文件数 |
> | `renamed` / `rename_failed` | 重命名成功 / 失败数 |
> | `kept_unresolved_episode` | 命名引用了集数、但一条都没解析出来的文件数（这些文件**保留原文件名、未改名**，**不是失败**；明细见 `samples.kept_unresolved_episode`） |
> | `name_collisions` | 改名时**目标文件名已经被占用**的文件数 —— 一条**事实清单**，**不代表**"即将被覆盖"。`within_run` = 本次运行里更早的某个文件占用了同一个目标名；`existing_target` = 目标上**本来就有**这个名字的文件。**L2 不覆盖**：由「加后缀保留」/「原有文件让位」化解（明细见 `samples.name_collisions`，日志里是 WARNING） |
> | `renamed_with_suffix` | **实际加了后缀保留**的文件数（例如 `Show A S01E01 (2).mkv`）。规则：同一次运行里按**体积从大到小**，体积最大的拿干净名、其余加 ` (2)`、` (3)`…（上限 999）；目标盘上原有的同名文件比新来的小时会改名**让位**（**不删除**）。找不到空位 ⇒ 保留原名 + 记 `error`，**绝不覆盖**（明细见 `samples.renamed_with_suffix`，日志里是 WARNING） |
> | `displaced_targets` | **原有文件让位**的次数（它比新来的小，于是改名成 ` (N)`，**不删除、不复制数据**；明细见 `samples.displaced_targets`，日志里是 INFO） |
> | `extras_classified` | 本次**命中特典判据、被排除在改名之外**的文件数（它们**不改名、也不移动** —— 保留原名留在原位置，因此**不**计入 `renamed`、`name_collisions`、`episode_unresolved`）。`0` = 没有命中或该功能已关闭（`extras_patterns: []`）。明细见 `samples.extras_classified`（每条 `{dir, name, size, pattern}`；`pattern` 是命中的那条判据），日志里是中文 INFO「特典保留原名（判据命中，未改名、未移动）：…」。判据在设置页的「特典文件排除」卡片，见 §8.7.1 |
> | `episode_unresolved` | **所有**没解析出集数的文件数，**不管它最后有没有保留原名**（命名模板不引用集数时，这种文件照样改了名）。它是 `kept_unresolved_episode` 的**超集**（明细见 `samples.episode_unresolved`，日志里是 INFO） |
> | `unknown_params` | 命名段里用了**不存在的变量名**、因而那段被**留空**的文件数 ⇒ 这些文件的**文件名少了一段**，但任务仍算**成功**。老配置/手改过的 YAML 才可能触发（新写的会被保存期拦下）。明细见 `samples.unknown_params`（`{label, file, params}`，日志里是 WARNING），任务告警里有一条汇总（含改法：把名字改对，或在「命名表达式」里定义它） |
> | `orphans_removed` | 被删除的孤儿硬链接文件夹数（**注意看这个数字**） |
> | `duration_ms` | 耗时（毫秒） |
>
> **`linked: 0` 且 `skipped: 0` 且 `link_failed: 0` 且 `renamed: 0`** → 源目录里根本没有符合条件的一级文件夹，去确认源目录对不对。
> **`unknown_params > 0`** → 有文件的**名字少了一段**，因为命名里用了一个"不存在的变量名"。去任务详情看 WARNING（「命名里的未知变量被留空（文件名少了一段）：…」）与 `samples.unknown_params`，把那个名字改对，或在「命名表达式」里定义它（新写的错名字会在保存时被拦下，所以这条多半来自老配置/手改过的 YAML）。见 [`docs/meta/KNOWN_ISSUES.md`](../meta/KNOWN_ISSUES.md) KI-11。
> **`kept_unresolved_episode > 0`** → 有文件因为"认不出集数"被跳过了（任务详情页的卡片与明细里能看到具体路径）。想要它们改名：补一条能命中文件名的 `episode_patterns`，或给 `episode_fallback` 配一个字面量（见 §5.2 的两个预设与 [`docs/guides/FAQ.md`](FAQ.md) 第 9 问）。**这个计数可能比预期的更大**：默认集数规则是 9 条带边界约束的规则（[`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3.2 增量 ④），像 `Show.E07.mkv`（`E` 紧贴点号）、`Show - 1920x1080.mkv` 这类写法不会被当集号 —— 前者保留原名，后者也归入"认不出"（而不会被错认成第 19 集）。要换成最朴素的旧口径，就把集数规则换回 `legacy` 那两条（或整体用 `legacy` 预设）。
> **`name_collisions > 0`** → 有多个源文件想改成**同一个目标文件名**（任务详情页的「同名冲突」卡片会逐条列出「目标名 ← 本次源名（先前占用者 谁；kind=…）」）。⚠️ **L2「防丢」**：体积最大的那个拿干净名，其余的加 ` (2)`、` (3)`… 后缀保留（计入 `renamed_with_suffix`）；目标盘上本来就有的同名文件比新来的小时改名**让位**（计入 `displaced_targets`，**不删除**）。所以 `name_collisions > 0` 只说明"发生过争名"，**不等于丢文件**。想彻底避免，请清理目标目录里的重复版本或调整命名模板（[`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) §5 的 L4 行）。
> **`episode_unresolved > kept_unresolved_episode`** → 有一些文件认不出集数、但**没有**保留原名（命名模板没引用集数，所以照旧改了名）。看 `samples.episode_unresolved` 确认它们是不是你想要的。
> **`orphans_removed > 0`** → ⚠️ 媒体库里**真有文件夹被递归删除了**，去日志里找 `Deleted orphaned hard link folder:` 那几行确认是不是你想要的。
>
> 📌 **另外两个字段值得看一眼**：
> - **`warnings[]`**：**不致命的告警**（中文、可执行）。常见五类：①「源与目标不在同一个挂载」——只警告，真失败会体现在 `link_failed`；②「源目录在任务期间发生了变化」；③「本次运行有 N 个文件改到了已被占用的目标文件名上（同一次运行内更早的文件占用 X 个 + 目标上本来就存在的文件 Y 个）；已按 L2 防丢策略处理…」——争名汇总，明细见 `samples.renamed_with_suffix` 与 `samples.name_collisions`；④「N 个文件因为目标名被占用而加了后缀保留（正片优先、其余不丢）：…」——列出前 10 条 `原名 → 新名`；⑤「N 个文件命中特典判据、已排除改名（保留原名、留在原位置）：…」——L3 特典排除汇总（列出前 10 条 `文件名（判据）`；判据来自设置页的「特典文件排除」，误判就把判据写精确，见 §8.7.1）。
> - **`source_integrity`**：`{"ok": true, "changed": []}`。任务**开始前**对源目录做逐文件快照（相对路径 / 大小 / inode / mtime），**结束后**再核对一遍；`ok: false` 时会列出被动过的路径。
>   硬链接本身只会让源文件的链接数 +1、`ctime` 变化，这两项**不算**变化，所以不会误报。
>   （源目录与目标同挂载、本身可写，保护靠"代码层不写源目录 + 这套核对" —— 见 [`docs/guides/FAQ.md`](FAQ.md) 第 4 问。）

### 7.3 常见失败原因："error 里这句话是什么意思"

| 报错里出现的关键词 | 意思 | 怎么办 |
|---|---|---|
| `跨挂载` / `EXDEV` / `link_failed` | 源和媒体库**不在同一个挂载**上（比"不同文件系统"更严），**建不了硬链接** | 把下载根与媒体库根放进**同一条 bind**（`docker-compose.yml` 的 `MEDIA_ROOT`）；本应用**不会**复制文件。见 [`docs/guides/FAQ.md`](FAQ.md) 第 3、34、35 问 |
| `不在允许的根路径内` | 库的源/目标目录超出了白名单（默认是 `/vol1/1000/Download` 和 `/vol1/1000/Library`） | 改库的路径，或在设置里改 `allowed_source_roots` / `allowed_target_roots` |
| `无法比较文件系统` / `路径不存在或不可访问` | 源目录或目标父目录不存在；或预检**无法实证**（`same_filesystem: null`，源树里找不到可试链的普通文件） | 检查挂载；确认你填的是**容器路径**而不是 NAS 宿主路径；`null` 不算失败，见 [`docs/guides/FAQ.md`](FAQ.md) 第 36 问 |
| `Permission denied` | 容器运行身份读不了源 / 写不了目标 | 见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §10（PUID/PGID 与 chown） |
| `创建硬链接失败: ... File exists` | 目标已存在（常见于**强制重跑**）。若目标就是**同一个 inode 的硬链接**，应用把它算成幂等跳过（`already_linked`，计入 `skipped`），任务**不会**因此失败；只有"同名但 inode 不同"才是真的 `link_failed` | 多数情况**无害，不用处理**。真想彻底干净就删掉目标那一个文件再跑（或在库里删掉该作品目录后重跑） |
| `Permission denied: '/data/config'` | 配置目录属主不对（少见） | 见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §10.3 |
| `Non-hard-link` / `非硬链接` | 应用在调用后逐文件核对，发现某个"建好的"文件不是真硬链接 | ⚠️ 这是严重信号（说明文件系统行为异常），请去 [`docs/guides/TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 查 |
| 日志里出现 `Skipping folder: X (already processed at ...)` | 不是错误，是幂等跳过 | 想重做就用「作品记录」里的「删除记录」（见 §6.4） |

### 7.4 看日志：怎么读

**任务详情页的日志区**按时间排好，每行有级别：

| 级别 | 含义 | 典型内容 |
|---|---|---|
| `DEBUG` | 调试细节 | 默认不显示太多 |
| `INFO` | 正常进展 | `已创建硬链接: ...`、`Renamed: ... -> ...`、`已记录文件夹体积: ...` |
| `WARN` | ⚠️ 需要注意 | **`Deleted orphaned hard link folder: <路径>`**（真的有文件夹被删了）、部分失败 |
| `ERROR` | 出错 | 执行异常、任务失败原因 |

**建链阶段原生实现打印的输出**会标记为 `stdout` 来源。这些**文案的格式是冻结的**（由 `app/processors/hardlink.py` / 规则引擎发出），包括：

- `已创建硬链接: <路径>`
- `创建硬链接失败: <路径> - <原因>`
- `文件夹已记录且体积一致，跳过: <文件夹>`
- `已删除旧记录: <文件夹>`
- `Deleted orphaned hard link folder: <路径>`
- `Renamed: <旧名> -> <新名>`
- `Error renaming <旧名>: <原因>`
- `Skipping folder: <文件夹> (already processed at <时间>)`

**想让日志更详细**：设置页把 `log_level` 改成 `DEBUG`。

**日志区是自动刷新的**（每 1.5 秒拉一次），不用手动刷新页面。任务跑完后停止刷新。

### 7.5 重试的正确顺序

1. 在任务详情页读 `error` 和日志，**先判断是哪一类问题**（上一节的表格）；
2. 修根因：
   - 跨挂载 → 换挂载（把源与目标放进同一条 bind）/ 换目标目录（**不是**改库配置就能绕过的）；
   - 权限 → 在 NAS 上调整属主/权限，重建容器（见 DEPLOYMENT §10）；
   - 目录不存在 → 建目录；
   - token/网络 → 那不会产生任务，属另一类问题。
3. 回任务页点「重试」；
4. 还失败 → 把 `error` 里的中文原文拿到 [`docs/guides/FAQ.md`](FAQ.md) / [`docs/guides/TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 里对照。

## 8. 设置页：逐项说明

设置页（`#/settings`）分几块。下表是全部可改项。

### 8.1 安全 / 账号

| 项 | 说明 |
|---|---|
| **修改密码** | 填当前密码 + 新密码（≥ 8 位）。改完建议重新登录一次 |
| **登出** | 清除本机 Cookie |

> 💡 会话密钥存在 `data/secret.key`。删掉它 = 所有人被登出（**账号密码不变**）。

### 8.2 回调 / Hook（**建好库之后马上来这一块**）

| 项 | 说明 |
|---|---|
| **hook token** | `http://<NAS_IP>:18081/api/hooks/*` 的通行证。**注意保密**，相当于这个应用的"触发钥匙" |
| **重新生成 token** | 旧 token **立即失效**。生成后必须**同步更新 qBittorrent 里的回调命令**，否则那边会一直报 `401` |
| **完整回调命令** | 已经把你当前的 token 和地址填好的一整行命令，点「复制」直接拿去粘进 qBittorrent。**这是最推荐的用法**（不用自己拼） |

> 📌 **token 只在设置页拿，不在 `.env` 里**：`hook_token` **不是环境变量**，`.env` 没有这个键、填了也不会被读取。它由应用**首次启动时随机生成**，存在 `/data` 的数据里；设置页就是它**唯一的查看与轮换入口**（`GET /api/settings` 也能读到明文）。

用法见 §9。

### 8.3 路径白名单

| 项 | 默认 | 说明 |
|---|---|---|
| `allowed_source_roots` | `["/vol1/1000/Download/qbittorrent"]` | 媒体库的**源目录**必须落在这个范围里 |
| `allowed_target_roots` | `["/vol1/1000/Library"]` | 媒体库的**目标目录**必须落在这个范围里 |

格式是 **JSON 数组**，例如：

```
["/vol1/1000/Download/qbittorrent", "/vol1/1000/Download/qbittorrent-2"]
```

> ⚠️ **改这一项要小心**：它是"防手滑"的安全网。放得太宽（比如写成 `["/"]`）就等于关掉了保护。改完保存，下次新建/编辑库时生效。
> 注意：这里只能是**容器路径**（容器里挂了什么才能写什么）。

### 8.4 扫描补偿

| 项 | 默认 | 说明 |
|---|---|---|
| `scan_enabled` | `false`（关） | 定时扫描源目录，发现"没记录过或体积变化"的一级文件夹就**建任务**。用于补上漏掉的 qBittorrent 回调 |
| `scan_interval_seconds` | `900`（15 分钟） | 扫描周期。想更及时就调小（例如 `300` = 5 分钟） |

**建议**：**打开**。它让系统有"自愈"能力 —— 回调漏了、容器重启过，下次扫描会补上。代价是每 15 分钟做一次目录体积统计（对 NAS 是轻负载）。

> 扫描**只创建任务，不做任何文件操作**。真正的文件操作由建链实现执行，且依旧幂等。

### 8.5 孤儿清理（⚠️ 破坏性能力，先读完）

| 项 | 默认 | 说明 |
|---|---|---|
| `orphan_cleanup_enabled` | `true`（开） | **全局总开关**。开启时，若源目录里某个一级文件夹**已被删除**，下次跑任务会**递归删除**媒体库里对应的硬链接文件夹 |

它和每个库自己的「孤儿清理」设置是**"与"**的关系：**两个都为真**才真的删除。

**它删的是硬链接（媒体库那一份名字），不会碰你的下载原文件（应用代码层从不写源目录，任务前后还会逐文件核对源完整性 —— [`docs/guides/FAQ.md`](FAQ.md) 第 4 问）。** 每次删除都在任务日志里以 **WARN** 级记录完整路径。

**什么时候必须关掉**：

- 你打算**删掉下载盘里的原始下载、但保留媒体库**（否则下次跑任务媒体库那份就没了）；
- 下载目录会被临时清空或迁移（换盘、腾空间）。

**关掉的副作用**：源文件已删的旧记录会一直留在日志里，每次跑任务去 `stat` 一次（纯读），没别的影响。

**【NAS 宿主】**也可以用命令关：

```bash
curl -s -b cookies.txt -X PUT http://192.168.1.100:18081/api/settings \
  -H 'Content-Type: application/json' \
  -d '{"orphan_cleanup_enabled":"false"}'
```

> 详见 [`docs/guides/FAQ.md`](FAQ.md) 第 5 问与第 18 问。

### 8.6 日志与历史

| 项 | 默认 | 说明 |
|---|---|---|
| `log_level` | `INFO` | 应用日志等级。排查问题时可以临时改 `DEBUG`，**完事改回 `INFO`**（否则日志涨得快） |
| `max_history` | `2000` | 任务历史保留条数。超出后自动裁剪最旧的记录。**只删记录，不动磁盘文件** |
| `max_task_log_lines` | `5000` | 单个任务保留的日志行数上限（超出会插入一条截断提示） |
| `config_dir` | `/data/config` | 处理器与媒体库配置文件所在目录（在 `/data` 卷内，无需额外挂载） |
| `config_sync_interval_seconds` | `5` | 文件 → 数据库的自动导入间隔；设 `0` 表示**关闭自动导入**，只在你点按钮时导入 |

> 这两条 `config_*` 是配置同步用的。设置页里**没有** `seed_logs_on_first_run` 这一项
> —— 不需要它（原理见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §6.5）。

### 8.7 允许重命名的文件后缀

设置页的「**允许重命名的文件后缀**」卡片：每行一个后缀（`.mkv` / `.mp4` / `.ass`…），
**留空 = 未设置**（此时按各处理器自己的清单走）。

- 它**对所有媒体库生效** —— 这是"我不想让 `.mp4` 被改名"这类需求的一处总开关；
- 大小写不敏感（`.MKV` 会归一化成 `.mkv`）且保序去重；必须以点开头，否则保存时提示；
- **优先级**：库级覆盖（§5.4.2）→ 本设置 → 处理器清单。也就是说想只放行某一个库，去库编辑页写覆盖；
  想全局生效，就在这里改；
- 它只决定**重命名阶段**认哪些文件；硬链接阶段永远整棵树链过去，不看后缀。

#### 8.7.1 特典文件排除（L3）

设置页的「**特典文件排除**」卡片：**一行一条正则**（不是一行一个后缀，也**不按空格切**）。出厂默认 7 条 ——
`NCOP`、`NCED`、`Preview`、`Creditless`、`Info`、`予告編`、`CM集`；**清空成 `[]` = 关闭这个功能**。

- **它解决什么**：与正片平级的散装特典文件（`NCOP.mkv`、`Preview 01.mkv`…）会被当成正片套上集号
  （比如被改叫 `Show A S01E01.mkv`）。开了它，命中判据的文件**退出改名流程** ——
  **不改名、也不移动**：保留原名留在原位置（硬链接阶段建好的那一份照旧在媒体库里）。
- ⚠️ **命中文件不会进 `其他/` 目录**：应用**不会创建 `<作品目录>/其他/`**，命中文件原地不动。
  （你要是手上已经有 `其他/` 目录，想还原成平铺摆放就手工移回 —— 同一文件系统内的移动不消耗额外空间。）
- **判据怎么用**：对**含扩展名的文件名**做**大小写不敏感**的正则搜索（`NCOP` 能命中 `[NCOP].mkv`）。
  一行一条，写 `^NCOP$` 这类锚定更精确；空行会被忽略；**非法正则保存时直接报错**（会告诉你第几条、
  哪个模式编译失败），不会静默吞掉。**只作用于当前作用域目录的直接文件** ——
  `Season 1/特典/` 这种**嵌套子目录里的文件一律不动**。
- **不会丢文件、也不会多出目录**：命中文件停在原处 —— 文件名、位置、内容一个字节都没变。
- **任务结果里怎么看**：任务详情页/`GET /api/tasks/{id}` 的 `result.extras_classified` 是**本次被排除的文件个数**
  （0 表示没有命中或该功能已关闭），样本在 `samples.extras_classified`（每条 `{dir, name, size, pattern}`；
  `pattern` 是命中的那条判据，便于反查误判）；任务日志里会看到中文
  INFO「特典保留原名（判据命中，未改名、未移动）：…」。
- ⚠️ **误判了正片怎么办**：把那条判据改精确（例如 `^NCOP$`）或删掉它 —— 下次改名就照旧处理了。
  **已经归入 `其他/` 的文件不会自动搬回**，需要你手工移回（同一文件系统内的移动不消耗额外空间）。
- **这是一项独立能力**。它**对所有库与所有处理器生效**，
  `legacy` 预设也**不例外**；只影响重命名，不影响硬链接的建立。

### 8.8 qBittorrent API 连接（可选）

| 项 | 说明 |
|---|---|
| `qbittorrent_url` | 如 `http://192.168.1.100:18080` |
| `qbittorrent_username` / `qbittorrent_password` | qBittorrent 的登录凭据 |

**这些是可选补偿项**。应用**不靠它工作**：自动触发靠回调，补偿靠目录扫描。填了可以做更强的 API 补偿（向 qBittorrent 查询种子列表）。不填完全不影响主流程。

> 💡 密码框若显示 `***`，表示"已设置"。保持 `***` 不变就是不改它；要改就输新密码。

### 8.9 权限模式（在媒体库的编辑页，不是设置页）

**一句话**：**默认关闭**。打开它、并在弹出的确认框里点「我了解风险，开启」之后，应用会在建链阶段把**目标库**的权限改成 `0777`，好让**非 root 的服务**（例如以非 root 身份运行的 Emby）也能读到库内文件。它是「要你亲手担责」的开关，不是推荐默认项。

**它到底改什么**：库根目录本身 + **本次处理到的每个作品文件夹的目标侧整棵子树**（包括体积一致、本来会被跳过的旧作品 —— 否则开关对已经入库的内容等于没开），目录与文件都改 `0777`。**不改**你的下载目录、**不跟进**符号链接；关闭时（默认）**一个 `chmod` 都不做**。

> ⚠️ **必须知道的副作用**：媒体库里的文件是**硬链接**，与下载原文件**共享同一个 inode**，而权限位是 inode 的属性 —— 所以给媒体库放权会**同时改掉 `/vol1/1000/Download/qbittorrent` 下源文件的权限位**。文件内容、大小、inode 号、修改时间都不变（源完整性核对因此不会报警），但**权限确实一起放宽了**。这正是：默认关闭、开启前必须二次确认、每次运行都会在任务日志里以 WARNING 记录「改了 N 个目录 / M 个文件」的原因（源完整性核对看不见权限变化，靠日志留痕）。契约见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) §1.6 与 B13。

**什么时候该开**：只有当某个以非 root 身份访问媒体库的服务确实读不到文件（`EACCES`）时才开。**更干净的替代做法**：在宿主上针对**目录**做精确的属主/权限调整（见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §10.4），或把该服务改成以同属主/root 身份运行 —— 这些都不动源文件。"为什么媒体库里的文件权限和下载目录里的一样"见 [`docs/guides/FAQ.md`](FAQ.md) 第 27 问。

### 8.10 系统信息（只读，但很有用）

| 区块 | 看什么 |
|---|---|
| **路径映射表** | 容器路径 ↔ 宿主路径的对应关系（来自 `HOST_PATH_MAP`）。**它只用于显示**：填错、漏填都**不影响功能**（见 [`docs/guides/DEPLOYMENT.md`](DEPLOYMENT.md) §6.5） |
| **挂载判定** | 源与目标是否在**同一个挂载**里。预检的 `same_filesystem` 是**三态**：`true`（实证 link 探针证过；若只是挂载 ID 预筛通过会在 `warnings[]` 注明「未实证」）/ `false`（**已证实**建不出 ⇒ `ok=false`、原因进 `errors[]`）/ `null`（判不了，例如源树下找不到可试链的普通文件，无法实证，不猜）。⚠️ **`st_dev` 两个数字相同 ≠ 能建硬链接** —— 内核 `linkat(2)` 比较的是挂载身份，`st_dev` 相同但分属两条 bind 时 `link()` 依然 `EXDEV`（这就是"假绿"的根因） |

> 硬链接与重命名由 `app/processors/hardlink.py` 与规则引擎 `app/processors/engine.py` 执行，行为由项目自己的
> 回归测试（冻结的黄金值）守护；容器只读 `/data` 与 `MEDIA_ROOT`
> （见 [`docs/guides/FAQ.md`](FAQ.md) 第 22 问）。

**建议**：建库前后各看一次这一页。跨挂载这个最坑的问题，在这里一眼就能看出来。

## 9. qBittorrent 回调：token 与命令的复制粘贴

这是把"下载完成 → 自动整理"打通的一步。**全程复制粘贴，不需要你理解命令内容。**

### 9.1 从本应用复制

1. 打开 `http://<NAS_IP>:18081` → **设置**页；
2. 找到 **回调 / Hook** 区块；
3. 点「**复制回调命令**」按钮。复制到的是一整行、已经含你 token 的命令，形如：

```
curl -s -X POST "http://192.168.1.100:18081/api/hooks/qbittorrent?token=xxxxxxxx" --data-urlencode "name=%N" --data-urlencode "hash=%I" --data-urlencode "category=%L" --data-urlencode "tags=%G" --data-urlencode "content_path=%F" --data-urlencode "save_path=%D" --data-urlencode "root_path=%R"
```

> 如果页面上的地址不对（例如要换成域名或别的 IP），按 [`docs/contracts/API.md`](../contracts/API.md) §6 的格式自己替换一下 URL 部分即可，其余**照抄**。

### 9.2 粘进 qBittorrent

1. 打开 qBittorrent WebUI（默认 `http://192.168.1.100:18080`）；
2. 右上角**齿轮图标（设置）** → **下载**；
3. 找到「**运行外部程序**」（Run external program on torrent completion）；
4. 把刚才复制的命令**整行粘贴**进去；
5. 确认这一项**已启用**，保存。

**注意**：

- **必须是一行**，不能换行；
- 命令里的 `%N` `%I` `%L` `%G` `%F` `%D` `%R` 是 qBittorrent 的占位符，**不要改**，也不要去掉；
- **不要**往命令里加 `kind=%K`：qBittorrent 的 `%K` 是**种子内部 ID（Torrent ID）**，**不是**任务类型。任务类型由媒体库的处理器推导（番剧/电影库 → 建链 + 重命名，自定义库 → 只建链）。`kind` 只是给高级用户手工传 `hardlink` / `rename` / `rename_hardlink` 时才用的**可选覆盖项**，标准命令里一律不传（[`docs/contracts/ARCHITECTURE.md`](../contracts/ARCHITECTURE.md) §8 是这条命令的唯一真源）；
- 不要改成 `-d "name=%N"` 这种写法（种子名里有空格和中文会出错，必须用 `--data-urlencode`）；
- qBittorrent 容器里自带 `curl`，不需要额外装东西。

### 9.3 验证它到底通没通

**最快的方法 —— 网页上模拟一次回调**：不用等真下载。

**【NAS 宿主】**（`<HOOK_TOKEN>` 换成你的 token）：

```bash
curl -s -X POST "http://192.168.1.100:18081/api/hooks/qbittorrent?token=<HOOK_TOKEN>" \
  --data-urlencode "category=ban" \
  --data-urlencode "content_path=/vol1/1000/Download/qbittorrent/Bangumi/Show A"
```

返回的**完整形状**是这样（字段含义见 [`docs/contracts/API.md`](../contracts/API.md) §6）：

```json
{
  "matched": 1,
  "tasks": [43],
  "ignored": ["电影", "国漫"],
  "ignored_details": [
    {"library_id": 2, "name": "电影", "reason": "分类 Movie 不在该库的分类列表里。"},
    {"library_id": 3, "name": "国漫", "reason": "回调带的标签与该库的标签条件没有交集。"}
  ],
  "warnings": [],
  "torrent": {"name": "Show A", "hash": "8f2c0a…"}
}
```

| 返回 | 意思 | 下一步 |
|---|---|---|
| `"matched":1`、`"tasks":[43]` | ✅ 通了，已新建任务 43 | 去任务页看任务 |
| `"matched":0`、`"tasks":[]` | 通了但**没命中**任何库（**这不是错误**） | 看 `ignored_details[].reason`，见 §9.3.1 |
| `401 回调 token 不正确。…` | token 错了或没带上 | 回设置页重新复制**完整回调命令**（含 `token=...`，别带多余空格或引号），或重新生成 token 后更新 qBittorrent 的「运行外部程序」 |
| `Connection refused` | 应用没跑或端口不对 | `docker compose ps` 看容器状态 |

#### 9.3.1 `matched: 0` 时怎么看原因（回调排查的主要依据）

**`matched` 为 `0` 不是失败**：它说明回调到达了、token 也对，只是**没有媒体库的规则匹配这个种子**。`ignored_details` 会逐个列出「没命中的库 + 中文原因」，照着下面这张表读就行：

| `reason` 长这样 | 意思是 | 怎么修 |
|---|---|---|
| 「该库没有配置任何匹配条件（分类/标签/路径前缀全为空），回调不会命中它。」 | 这个库**一个匹配条件都没填** | 回库编辑页填分类或路径前缀（§4.4） |
| 「分类 X 不在该库的分类列表里。」 | 分类对不上 | 要么改 qBittorrent 里这个种子的分类，要么把 `X` 加进库的分类列表 |
| 「该库配置了标签条件，但回调没有带标签。」 | 库要标签，但种子没有标签 | 给种子打上库要求的标签 |
| 「回调带的标签与该库的标签条件没有交集。」 | 有标签，但一个都对不上 | 同上，核对标签拼写（比较时会统一转小写） |
| 「`content_path …` 不在该库的任何路径前缀之下。」 | 种子不在这个库盯着的下载子目录里 | 检查库的路径前缀，或种子的分类/保存路径（§4.4） |
| 「匹配条件不是合法 JSON…」 | 库的分类/标签/前缀在数据库里是坏值 | 回库编辑页把这三项重填一遍（正常操作不会遇到） |

**记住匹配规则是「与」不是「或」**：一个库填了多个条件时，必须**全部**成立才算命中；少满足一个，这个库就进 `ignored_details`（详见 §4.4）。

**验证"qBittorrent 真的会调用"**：去看一次真实下载的完成事件。

**【NAS 宿主】**

```bash
cd /vol1/1000/Docker/media-ingest
docker compose logs --tail=100
```

应能看到回调被命中、任务入队。同时网页任务页会出现新任务。

### 9.4 如果回调漏了

回调不是 100% 可靠（qBittorrent 重启、curl 超时、应用正好在重启）。所以建议在设置页打开 **`scan_enabled`**（§8.4）作为补偿 —— 每 15 分钟扫一次，漏掉的会自动补上。

## 10. 删除媒体库规则会发生什么

**结论：只删规则，绝不删你的文件。**

**媒体库页 → 选中某个库 → 「删除」**，会出现**二次确认弹窗**（这是刻意的，防止手滑）。

### 10.1 删了之后

| 东西 | 结果 |
|---|---|
| 这条库的配置（源/目标目录、匹配条件、处理器…） | ❌ 删除 |
| **已经建好的硬链接文件** | ✅ **原样保留**，Emby 照常能播 |
| **qBittorrent 下载的原始文件** | ✅ 完全不受影响（应用代码层从不写源目录；源完整性核对兜底） |
| 该库的历史任务记录 | ✅ 保留（记录里会留着库名，方便你事后看懂） |
| 以后的 qBittorrent 回调 | 这个库不再参与匹配，不会再触发 |

接口的响应也把这件事写在明面上：

```json
{"deleted": true, "hardlinks_kept": true}
```

### 10.2 想连磁盘上的文件一起清理，要自己动手

应用**不会**因为你删了一条规则就去删媒体库里的文件 —— "删配置"和"删文件"是两件完全不同量级的事，不该绑在一起。

**【NAS 宿主】**（⚠️ 不可逆，执行前先 `ls` 确认路径！）：

```bash
ls -la /vol1/1000/Library/Anime-CN          # 先看，确认是这个目录
# 确认无误后再删：
# rm -rf /vol1/1000/Library/Anime-CN
```

> ⚠️ **删媒体库里的文件时记住**：如果下载目录里那份还在，**空间不会释放** —— 同一个 inode 还有另一个名字指向它（这就是硬链接）。见 [`docs/guides/FAQ.md`](FAQ.md) 第 2、5 问。

### 10.3 只是想暂时停用？别删，直接关「启用」

**编辑该库 → 把「启用」关掉 → 保存。**

效果：回调与扫描都不会再命中它，但配置和历史都留着。以后想恢复，打开开关就行。

## 11. 幂等性：为什么重复执行是安全的

**一句话**：建链阶段（现行执行体：原生实现 `app/processors/hardlink.py`）用「一级文件夹的总体积」当处理标记，**体积没变就跳过**。所以同一件事跑一百遍，结果和跑一遍一样。

### 11.1 机制

1. 处理一个一级文件夹前，建链阶段先算它的**总体积**（递归所有文件的字节数）；
2. 拿这个体积去日志里查：**已经有记录且体积相同** → 打印

   ```
   文件夹已记录且体积一致，跳过: Show A
   ```

   然后**什么都不做**；
3. 体积不同 → 删掉旧记录、重新建链接、记录新体积。

重命名阶段（规则引擎 `app/processors/engine.py`）用**同一套机制**（缓存日志 `bangumicache.log` / `moviecache.log`，同样按体积判断）。

### 11.2 所以这些事都是安全的

| 担心的场景 | 实际结果 |
|---|---|
| qBittorrent 连着触发两次回调 | 第二次空跑 |
| 定时扫描每 15 分钟跑一次 | 绝大多数时候空跑 |
| 你手动点了「运行」很多次 | 已处理的全部空跑 |
| 任务中途失败了，你再跑一次 | 已成功的部分空跑，只补做没做完的 |
| 容器重启后你重新跑一次 | 同上，安全 |
| 升级应用后你重新跑一次 | 同上，安全 |

**不会出现**：重复的硬链接、被覆盖的文件、被破坏的已有链接。这也是为什么可以「拿不准就再跑一次」。

### 11.3 唯一会打破幂等的两个操作（都知道风险再用）

| 操作 | 效果 | 风险 |
|---|---|---|
| **强制重跑（force）**——**只对 `scope.mode="folder"`（单个作品）有效** | 让建链阶段/规则引擎对该作品**不跳过**、重新处理一遍（"立即重命名"内部就是这么调的） | 一批无害的 `File exists` 报错；"目标就是同一 inode 的硬链接"会算成幂等跳过（`already_linked`，任务不会因此失败），只有同名而 inode 不同才是真的 `link_failed`；重命名阶段**不覆盖**：争名按体积判定 —— 最大的拿干净名、其余加 ` (2)`、` (3)`… 后缀保留，原有文件比新来的小时改名让位（不删除），找不到空位则保留原名；**幂等**，所以重复 force 不会越叠越多（候选后缀已是本文件自己的 inode ⇒ 照用）。源文件不受影响。**整库 force 已停用**（返回 400），见 §6.4 |
| **删除 `data/logs/hard_links.log`** | 它现在只当审计日志，**不参与"跳过"判断** → 删掉它对建链阶段**没有任何影响**（真正管用的是每库自己的账本） | 删这个文件已经达不到"重算"的目的了，反而丢了一份审计记录。**想重做就删作品记录**（见 §6.4） |

### 11.4 幂等性的"盲区"（已知限制，本项目不修正）

| 盲区 | 表现 | 绕过办法 |
|---|---|---|
| 只看**总体积** | 同一作品被追加了**等体积**的文件 → 判定为"没变" → 跳过 | 在「作品记录」里删掉该作品的记录，下次运行自动补做（见 §6.4；只想重命名就用「立即重命名」） |
| 下载工具**原地改写**已存在的文件且尺寸不变 | 事后检测发现不了 | 同上：删掉对应作品的记录后重跑（或先用「立即重命名」） |
| 目录名含 `" - "` | 记录行会被静默忽略，每次都当"未记录" → 重复尝试建链（产生一批无害的 `File exists`）。这类条目现在会被正确记成"目标已是同一 inode 的硬链接"（`already_linked`、计入 `skipped`），任务不因此显示失败 | 避免目录名里出现 `" - "` |

这些都属于**既有行为**，本项目刻意不修正（见 [`docs/contracts/BASELINE.md`](../contracts/BASELINE.md) 的 L2、L8、L9）。
