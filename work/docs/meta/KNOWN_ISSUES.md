## KI-1 无 `Season N` 层级时改名被静默跳过

**状态：搁置 —— 改名行为不变，只以看板待办的形式提示。**

对命中本条的每个作品，应用**仍不改名、不移动**，也**不算**「未解析出集数」；它只是多出一条
**第六种待办** `unscoped_works`（标题「作品结构不可识别（未改名）」），让"以为跑过了"与"其实没改名"
在看板上区分开。真正的「扁平目录模式」（方案 ②）**未实现**。

### 现象

对「作品目录下**没有 `Season N` 这一层**」的作品，重命名阶段**一个文件都不改**：

- 任务**不报错、不失败**（可以是 `success`），`result.renamed = 0`、`rename_failed = 0`；
- `result.warnings[]` 里**没有任何**和这件事相关的条目 —— 页面上看不出异常；
- 目标侧 `/vol1/1000/Library/Test` 下**硬链接照常建好**，但文件名**保持源侧原名**（命名模板没生效）。

一句话：**建链接这一步与这件事无关，它照做；不生效的是「改名」这一步。**

### 触发条件

三个条件同时成立时才发生：

| # | 条件 | 示例取值 |
|---|---|---|
| 1 | 媒体库的 `traverse.file_scope` 是 `subdir` | `subdir`（`bangumi` 处理器的默认值） |
| 2 | `traverse.accept_dirs` **非空**，且只接受季目录 | `["^Season (\\d+)$"]`（`season_group: 1`） |
| 3 | 某个一级作品目录 `T` 的**直接子目录里没有**名字能整名匹配 `accept_dirs` 的目录 | 示例库：54 个作品里的 **8 个**（见下） |

注意判定是**整名匹配**（`fullmatch`，见 `docs/contracts/PROCESSORS.md` §4 第 5 步），
所以 `Season 1 (2018)`、`SP`、`特典` 这类目录名同样不匹配。

### 机制（为什么是「静默」）

作用域目录的计算在 `app/processors/engine.py:489-524`（`_scope_dirs()`）：

- 命中 `reject_dirs` ⇒ 跳过，**并写 warning**（`app/processors/engine.py:501-502`）；
- `accept_dirs` 非空且**不匹配** ⇒ **直接 `continue`**（`app/processors/engine.py:513-514`）—— **不写任何 warning**。

子目录全被 `continue` 掉之后，该作品的作用域目录列表为空 ⇒ 没有候选文件 ⇒ 改名阶段无事可做 ⇒
`renamed = 0`，而执行器只按「有没有失败」判定任务状态，所以任务**看起来是成功的**。
`docs/contracts/PROCESSORS.md` §4 第 5 步记的正是这套遍历语义（`file_scope: subdir` 时候选 = `T` 的直接子目录，按 `reject_dirs` / `accept_dirs` / `skip_season_zero` 逐层筛）。

> 这不是哪一次改动的回归：处理器默认规格与真实源「偶尔缺 `Season` 这一层」的叠加结果，
> 在**一次全库运行里即可被量化**（示例库 54 个作品里有 8 个命中；比例随源库而变）。

成因：**源侧的目录层级不总是齐全**（`Season` 这一层是在配置 qBittorrent 下载目录时定下的，
某次下载漏掉它就不会有），而本应用的重命名作用域**硬依赖这一层**。

### 影响面

- **受影响**：源树里没有 `Season N` 子目录的作品（与 `renamed = 0` 的集合**完全一致**）。
  例如 `/vol1/1000/Download/qbittorrent/Bangumi/` 下的一级目录 `作品 A`、`作品 B`…，
  只要它下面没有名字整名匹配 `accept_dirs` 的子目录，就落在本条里。

- **规模**：示例库里 8 / 54 个作品（比例随源库而变）；这些作品的文件在目标侧**全部以源原名存在**（硬链接已建好，**数据不缺失**，缺的只是改名）。
  各作品下的文件数**未逐目录清点**（全库跑的 `result` 只给聚合计数），需要精确数字时按下面「复核」里的命令数一遍。
- **不受影响**：有 `Season N` 子目录的作品改名正常；`file_scope: title` 的库、以及 `accept_dirs` 为空的库都不走这条分支。
- **对用户的实际后果**：媒体库里这些作品的文件名不符合命名模板（刮削器/播放器可能认不出）；
  任务本身**不会**因此报错或失败，但看板上会出现对应的 `unscoped_works` 待办。

### 复核（只读，不改任何东西）

**【NAS 宿主】** 源侧确认某个作品的直接子目录里没有 `Season N`（把 `作品目录` 换成你的目录名）：

```bash
docker exec media-ingest-test sh -c 'ls "/vol1/1000/Download/qbittorrent/Bangumi/作品目录"'
```

**【NAS 宿主】** 目标侧确认文件仍是**源原名**（没有套上命名模板）：

```bash
docker exec media-ingest-test sh -c 'ls "/vol1/1000/Library/Test/作品目录"'
```

**【浏览器】** 「任务」→ 打开刚跑的那次任务 → 结果里这些作品的 `renamed` 为 `0`，且状态**不是失败**。

### 可选修法（**未实现**，仅备查）

| 方案 | 做法 | 风险 |
|---|---|---|
| ① 单库覆盖 `file_scope: title`（**低风险，推荐优先评估**） | 在**该库**的「重命名规则（本库）」覆盖里把 `traverse.file_scope` 改成 `title`：作用域 = 作品目录 `T` 本身，文件直接取自 `T`，`season_raw = ""`（`docs/contracts/PROCESSORS.md` 的 `traverse` 覆盖键包含 `file_scope`，`app/processors/engine.py:493-494`）。**不改代码、不影响其它库。** | ① 只对这一个库生效，其它同样缺 `Season` 的作品目录要各自处理；② `season` 变成**空串**（`app/processors/engine.py:217`），命名模板里的 `{season:02}` 经 `pad` 走 `zfill` 会渲染成 **`00`**（`app/processors/engine.py:240-243`），文件名会出现 `S00` 这种字样，需要相应调整模板；③ `title` 模式下**不过滤非文件项**（`docs/contracts/PROCESSORS.md` §4 第 6 步），恰好以后缀白名单结尾的子目录名也会进候选；④ 作用域变大 ⇒ 该作品目录下的所有匹配后缀的文件都会被改名，先确认目录里没有不该动的文件 |
| ② 让 `accept_dirs` 也接受作品目录本身 | 改引擎 `_scope_dirs()`：`accept_dirs` 都不匹配时，把 `T` 本身也作为一个作用域目录（此时 `season_raw = ""`）。 | ① **改的是所有库共用的冻结遍历语义**，触碰 `docs/contracts/BASELINE.md` / `docs/contracts/COMPATIBILITY.md` 里记录遍历判据的**契约条款**，必须先过一遍基线影响评估（现行判据是冻结的黄金值，见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §4.1）；② 同样有 `season = "00"` 的命名后果；③ 「`accept_dirs` 不匹配 ⇒ 跳过」是既有的遍历语义，改成"再兜底一层"会让「用户显式写了接受规则」的意图变得含糊（例如只想处理 `SP` 目录的库会突然开始处理整个作品目录）；④ 需要新测试钉住，否则是静默的行为扩散 |

> 两条方案的共同前提：**先确认「这些作品其实希望被改名」**。若某些作品（例如多季混合目录）
> 本就不适合按单目录模板命名，方案 ① 会把它们一起改了 —— 那是**新的**正确性问题，不要顺手做。

### 现行行为（不修，只报）

- **不修**：这是记录在案的现状，本应用不会自动改动媒体库里的任何东西。
- 配套的可观测性：`RenameOutcome.unscoped_works` / `result["unscoped_works"]` / `samples.unscoped_works`，
  `app/todos.py` 登记为第六种 kind `unscoped_works`（级别 `warning`，去重键 = 作品目录），
  任务日志同时留一条 `WARNING`。触发条件收紧：只有「作品目录里确有本规格该处理的文件、且未被特典判据命中」
  才报（空目录、或直接文件全是特典的扁平目录不报）。
- 若以后决定**真正处理**扁平结构：优先按方案 ① 用**库级覆盖**验证（可随时改回），确认命名模板与
  `{season}` 表现后再考虑是否要做方案 ②（扁平目录模式开关）。

## KI-7 升级后首次全量运行会重链并可能多出「 (2)」后缀

**状态：已知且被接受的一次性影响（不是缺陷）。** 老媒体库**刻意不回填**历史 `hard_links.log`，所以首次全量运行会重链一次；规避办法见下。

### 现象

老媒体库的 `link_records` 账本是**空的**（新表由启动时自动补建，但**没有**把历史日志里的记录搬进来）。于是**第一次全量运行会把每一个作品都重新建链**；如果此前在目标目录里把某些文件**改过名**，那次运行会以**原名**把同一批文件再链一份 —— 同一个 inode 的**第二个目录项**。到重命名阶段，这两个目录项会争同一个目标名（体积相同 ⇒ 按目录顺序），于是多出一个 `xxx (2).mkv` 后缀（冲突加后缀的完整口径见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §4：` (2)`…` (999)`）。

### 为什么这么设计

`hard_links.log` 是**全局**的、且不含库 / 目标维度，无法可靠地映射成「某库某作品已处理」，所以升级**不做历史回填**、账本从空开始。

### 影响面与规避

- **不丢数据**：多出来的是**硬链接**（同一个 inode），源目录**完全不受影响**；只是目标目录会多出重复的文件名，需要手动清理。
- **规避办法（三选一）**：① 升级后**使用新媒体库**（推荐，本项目验证时走的就是这条路径）；② 先**清空目标目录**再跑首次全量；③ 在「作品记录」里**逐作品删除记录**后重做 —— 下次运行自动补做这些作品，其余作品不受影响。
- 一次性：重链过一轮之后账本就有记录了，后续运行恢复正常的跳过行为。

## KI-8 「作品记录」页的搜索是朴素子串、目标侧计数只覆盖当前页

**状态：已知且刻意保持（不是缺陷）。** 这两条都是「**作品级账本 + 服务端分页**」这个设计的自然结果：改掉它们要么得不偿失，要么与账本语义冲突。**只影响"看一眼"的便利性，不影响任何写入行为。**

### 现象

1. **搜索只认作品名，而且是朴素子串。** 「作品记录」页的搜索框把输入**转义后**原样做子串匹配（`folder LIKE '%<输入>%' ESCAPE '\'`，见 `app/link_records.py` 的 `search_records`），匹配对象是**作品名**（源目录里的**一级文件夹名**）。因此：
   - **不支持**正则、多关键词（空格会被当成名字的一部分，不是"与"）、日期范围，也不能按体积 / 路径过滤；
   - 搜**目标里改名后的名字**、作品**内部**的文件名、目标路径片段一律**搜不到**（改名不会改变账本里的作品名）；
   - `%`、`_`、`\` 被**转义成字面字符**（不会当通配符，也不会报错）；ASCII 大小写不敏感；
   - 只在**当前选中的那个库**的记录里搜。
2. **「目标里现在有多少文件」只对当前页现算。** 列表返回的 `target_files` / `target_bytes` / `target_loose`（不是本应用建立的硬链接数，即"你自己放进去的文件"）是对**当前这一页**的每个作品**现场读磁盘**（`os.walk`）算出来的；信息行的「命中 N 条 / 本库共 M 条」和两本账差集（`rename_missing` / `rename_only`）**才是按整本账算的**，不受搜索与翻页影响。

### 为什么这么设计

- 账本 `link_records` 的键是 `(library_id, folder)`，**作品级**、不存文件清单：既然账本里没有文件级信息，页面上任何"目标里现在有几个文件"的数字就只能**现场读磁盘**得到；对整库（几百上千个作品）在翻页之外再全量扫一遍磁盘，会把一次翻页变成一次全库 IO —— 代码注释写得很直白："几千个作品时'翻一页算一页'才不会把接口拖死"。
- 搜索刻意做成**最保守的子串**：转义 `%` / `_` / `\` 后交给 SQLite `LIKE`，任何输入都只会**缩小结果、不会报错**，也不会因为随手写个 `%` 就把整本账拉出来。正则 / 多关键词 / 时间范围属于**未被需求验证过**的功能，没有实现。

### 影响面与规避

- **不影响正确性**：搜索与计数都是**只读展示**；「删除记录」「立即重命名」的作用对象始终是你**显式勾选**的作品，与当前页、当前搜索词无关（勾选还**跨页保留**）。
- **想按别的维度找**：用【NAS 宿主】直接查接口 `GET /api/libraries/{id}/works?q=&limit=&offset=`（契约见 [`docs/contracts/API.md`](../contracts/API.md) §3.10），或先按作品名搜到大概范围再翻页。
- **想要"整库健康扫描"**：**现在没有**这个功能 —— 不要把某一页的 `target_loose` 之和、或某一页的 `target_files` 当成整库结论；真要全库核对，就分页翻完或直接读接口。
- 相关：账本的作品级语义及其取舍见 [`docs/contracts/COMPATIBILITY.md`](../contracts/COMPATIBILITY.md) §3.5；页面各部位的说明见 [`docs/guides/USER_GUIDE.md`](../guides/USER_GUIDE.md) §6.5。

### 相关测试

`tests/test_works_ledger.py`（含 `test_search_records_filters_by_literal_substring_and_pages`：`%` / `_` 按字面匹配 + 分页）；页面表格与信息行的字段来自 `app/routers/libraries.py` 的 works 列表接口（`app/routers/libraries.py:599` 的 docstring 记了 `total` / `ledger_total` / `target_*` 的口径）。

## KI-9 单作品 `force=true` 仍会把已改名的文件按原名再链一份

**状态：已知、界面无法触达、是否退役待定。** **单作品** `force=true`（`scope.mode="folder"`）是刻意保留的 API 用法（「立即重命名」内部就是这么调的：`payload.force=true`），但**它照样会复现整库 `force` 被撤掉所针对的那个现象** —— 建链阶段把**已经改过名的文件按原名再链一份**，于是目标作品文件夹里**同一个 inode 有两个目录项**，重命名阶段再多出 ` (2)` 后缀。**现在只有接口能走到这条路径**：运行弹窗与「作品记录」页都不会发 `force=true`。

### 现象（`ls -lai` 实测）

对一个已经跑完、目标里只剩 2 个干净文件的合成作品发一次单作品 force：

```
POST /api/libraries/1/run  {"force": true, "scope": {"mode": "folder", "folder": "Work 03"}}
```

任务 202 + `success`（**没有任何报错**），但 `ls -lai '/vol1/1000/Library/Test227/t1/Work 03/Season 1'` 变成 **4 个目录项**：

```
17067864  -rw-r--r--  3 … Work 03 S01E01.mkv
17067864  -rw-r--r--  3 … Work 03 S01E01 (2).mkv      # 同一个 inode，第二次目录项
17067865  -rw-r--r--  3 … Work 03 S01E01.ass
17067865  -rw-r--r--  3 … Work 03 S01E01 (2).ass
```

「作品记录」页那一行的「目标目录现有 **4** 个文件」就是它的观感（正常应是 2）。`nlink=3` 说明：源文件 + 干净名 + ` (2)` 名，三个目录项、**一份数据**（**不占额外空间、不丢数据**）。

### 为什么这么设计（以及为什么不修）

- **建链阶段的跳过判据在 `force` 时被摘掉**是**有意**的（`app/processor.py`：`force` 时把被强制的作品从 `skip` 字典里摘掉，否则"强制重跑"会变成静默空操作）—— 这正是"强制"二字的含义：**不跳过、重新处理一遍**。而"重新处理"是按**源目录的原始文件名**建链的，目标里早有改好名的同一 inode，于是同 inode 出现第二个目录项。
- **判据是作品级、不是文件级**（账本语义见 [`docs/contracts/COMPATIBILITY.md`](../contracts/COMPATIBILITY.md) §3.5）：要做成"只补缺失的那几个文件"，就必须引入**逐文件核对**（已被明确否决的路线），代价与风险都不划算。
- **界面已无入口**：用户实际能点的两条重做路径是「删除记录 ⇒ 下次运行自动补做」（会连带删掉目标作品文件夹，是"从零重建"的干净语义）与「立即重命名」（只改名字、不建链）。把 `force=true` 做成"先删目标作品文件夹再重建"会**静默删掉用户手工放进去的文件**，与"删除必须显式确认"冲突，所以**没有**这么改。
- **待定项**：是否在后续版本里让 `force=true` **一律 400**（彻底退役、只留两条正道）。做这个决定前，接口用户应把本条目当成"已知坑"。

### 影响面与规避

- **正常使用完全碰不到**：两条界面路径都不发 `force`。
- **接口用户**：`force=true` + `scope.mode="folder"` 只适合"目标目录已经空了/残缺"的排查场景；**不要**用它去补目标里缺失的文件。真想让某个作品回到干净状态：在「作品记录」里**删掉该作品的记录**（勾选 → 删除记录 → 弹窗点「确定删除」）再跑一次普通执行，或在 NAS 上手工删掉那个作品文件夹后再跑。
- **已经出现了 ` (2)` 怎么办**：把目标里那一个作品文件夹整个删掉（或删掉 ` (2)` 那两份），然后**删掉该作品的账本记录**再跑一次普通执行 —— 只删 ` (2)` 文件而不删记录的话，普通运行会照旧跳过它（见 [KI-7](#ki-7-升级后首次全量运行会重链并可能多出-2后缀)）。
- 相关：整库 `force` **已停用**（返回 400，文案见 [`docs/guides/USER_GUIDE.md`](../guides/USER_GUIDE.md) §6.4 与 [`docs/guides/FAQ.md`](../guides/FAQ.md) 第 38 问）；整库升级后首跑的同现象见 [KI-7](#ki-7-升级后首次全量运行会重链并可能多出-2后缀)。

### 相关测试

`tests/test_works_ledger.py::test_works_endpoints_round_trip`（覆盖 `scope.mode="works"` / 删除 / 立即重命名；**不覆盖**单作品 `force=true` 的重复建链现象）。

## KI-10 待办看板的「作品筛选」是朴素子串、不是按作品精确归属

**状态：已知且刻意保持（不是缺陷）。** 待办看板的「作品」筛选框（`GET /api/todos?q=`）在输入停 0.4 秒后自动筛选。它匹配的是**待办自己的文字** —— `title`（问题摘要）、`detail`（详情里的目录 / 路径 / 错误文本）、`dedupe_key`（去重键，例如 `Work 03/Season 1`）**三列任意一处包含这段文字**即列出，**不是**"这条待办属于哪个作品"。

### 现象与口径

- **子串，不是精确**：搜 `Work 1` 会同时列出 `Work 12`（与「作品记录」页的搜索同一套规矩，见 [KI-8](#ki-8-作品记录页的搜索是朴素子串目标侧计数只覆盖当前页)）。
- **可能多列**：同一段文字出现在**别的**条目里（例如两个作品共用一个源目录名、或某条"任务失败"的详情里提到了同一段路径），也会被列出来。
- **ASCII 大小写不敏感**；`%` / `_` / `\` 按**字面**处理（`ESCAPE '\'`，与 `link_records.search_records` 同一套转义）—— 搜 `50%` 不会命中所有条目。
- **AND 关系**：与状态 / 种类 / 媒体库三个筛选叠加；`total` 与翻页都按**过滤后**算。
- **不影响统计**：顶部计数与「一键检测」始终是整表 / 整库口径（不是"筛完之后的数"）；筛空了看板会明确说「没有匹配「…」的待办」，不会让人误以为看板坏了。

### 为什么这么设计（以及为什么不修）

- **`todos` 是全局一份台账**（建表时就刻意不挂外键、不带库结构）：条目记的是"发生过什么"，表里**没有** `folder` / 作品列。作品名只出现在摘要、详情与去重键里 —— 能筛出"和某段文字有关的待办"已经是这份数据模型能给出的全部。
- **要做"精确归属"得改数据模型**：给每条待办加作品字段并**回填历史条目**（旧条目本来就没记过作品，只能留空或按路径猜），还要在五种样本的生成路径上逐个补字段；收益只是"少列几条"，代价是迁移 + 五种 kind 的写入路径全改，不划算。
- **"按路径猜归属"被刻意否决**：源目录一级文件夹名并不等于作品（同一作品可能跨多个一级文件夹、特典可能平级），猜错反而会**漏列**真正相关的待办 —— 筛漏比多列更危险。

### 影响面与规避

- **正常使用无感**：想精确一点就写更长的子串（`Work 03` 而不是 `Work 0`），或配合「种类」「媒体库」两个下拉框把范围收窄。
- **接口用户**：`q` 缺省 / 空串 / 纯空白 = 不过滤（与不传 `q` 完全一样）；`q` **不会**变成错误输入 —— 没有任何取值会 400。
- 相关：作品记录页的搜索口径见 [KI-8](#ki-8-作品记录页的搜索是朴素子串目标侧计数只覆盖当前页)；待办看板本身的语义见 [`docs/guides/USER_GUIDE.md`](../guides/USER_GUIDE.md) §2.5 与 [`docs/contracts/API.md`](../contracts/API.md) §5.9.2。

### 相关测试

`tests/test_todos.py`：`test_list_todos_query_filters_by_literal_substring`（三列口径 / 大小写 / 空串 / 0 命中）、`test_list_todos_query_escapes_like_wildcards`（`%` / `_` 字面）、`test_list_todos_query_combines_with_other_filters_and_paging`（AND + 翻页 + `total` 口径）、`test_api_todos_query_param_is_forwarded_and_trimmed`（路由透传 + `strip` + `summary` 不受影响）。

## KI-11 命名里出现未知变量时，段序列静默少一段

**状态：当前行为。** 保存期拦住新写的错名字（422），运行期对老配置只**留痕不拦截** —— 不再有"任务成功却什么都没说"的情况。

### 现象

命名（`naming.segments` 的 `param` 段，或 `naming.template` 里的 `{名字}`）写了**上下文里不存在的变量名**时：

- 那一段**什么都不输出**（`render_segments()` 对 `context.get(name) is None` 直接 `continue`），文件名因此**少了一段**；
- 任务照样 `success`，`result` 里没有任何字段、`warnings` 里没有任何条目，日志里也没有一行 —— 保存时也不报错（只要名字是合法标识符）；
- 极端情况：段序列**全**是未知名字 ⇒ 渲染出空文件名，走兜底"段序列渲染出空文件名（…），已跳过。"

实例（`tests/test_processor_engine.py`）：段序列 `[literal OK-, param no_such_name, literal -TAIL, param ext]` 渲染成 `OK--TAIL.mkv` —— 那一段凭空消失。

### 触发条件（谁会真的踩到）

| 入口 | 能不能写出未知名字 | 说明 |
|---|---|---|
| 处理器编辑页的**段下拉框** | **几乎不能** | 选项 = 变量表（`PROC_PARAMS`）+ 该 spec 的表达式名；只有"当前值本来就不认识"时会以 `名字（未知）` 形式出现（历史数据） |
| 处理器编辑页的**模板框** | 能，但**当场报错** | 边写边跑 `templateErrors()`，认不出就红字（与服务端同一份清单） |
| 媒体库编辑页的**规则覆盖模板** | 能，保存时被拦 | 服务端 `template_errors()` 用"合并后的变量名"校验（基本 spec 的表达式 + 覆盖自己的表达式 + 引擎内部键） |
| **手写 / 导入 YAML** | 能，且**不会被拦** | 直接改 `/data/config/processors/*.yaml`、导入 `libraries.yaml`、`PUT /api/processors/<id>` 提交 `naming.segments` |
| 直接改数据库里的 spec | 能，且不会被拦 | 老库升级/人工修数据的场景 |

### 因何产生（这份"未知"到底是怎么来的）

1. **改名了表达式、没改段序列**：先写了 `naming.expressions.ver`，段里用了 `{ver}`；后来把表达式删掉/改名，段里的 `ver` 就变成"未知"（保存期不查段里的名字，所以旧版本会原样存下）。
2. **手写 YAML 打错名字**：`{param: episdoe}`、`{param: episode-raw}`（连字符不是合法标识符，模板框会报"变量名不合法"；段序列只报"未知变量"）。
3. **把"变量表里没有、但引擎其实给得出"的名字当成合法的**：`episode_resolved` 是引擎内部键（见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3.1），模板校验**不会**再把它误判成"未知变量"（有效名字集合 = 变量表 + 引擎内部键 + 表达式名，前后端同一份口径）。
4. **跨版本搬运配置**：旧版本里合法的自定义表达式名，在新库里没带过来（覆盖与基本 spec 的表达式是两处，覆盖模板只能引用"合并后"存在的名字）。
5. **模板写法与段写法口径不同**：模板走 `template_errors()`（按变量表校验），段序列只按"形状"校验 —— 同义写法一个报错、一个静默，这本身就是 bug 的来源之一。

### 修法（两条腿：保存期拦住 + 运行期留痕）

| 层 | 改动 | 位置 |
|---|---|---|
| 保存期（新写的配置） | `validate_spec()` 检查每个 `param` 段的名字是否在"有效名字集合"里，不在就 422：`naming.segments[i].param` +「段里用了未知变量 {x}。可用变量：…；自定义名字要先在 naming.expressions 里定义。」；空串 `param` 也报错 | `app/processors/spec.py` |
| 有效名字集合（唯一口径） | `spec.known_context_names(expressions)` = `TEMPLATE_VARS` + `ENGINE_ONLY_VARS`(`episode_resolved`) + `naming.expressions` 的名字；`template_errors()` 默认用它，覆盖模板由 `overrides.resolve_override()` 传**合并后**的清单 | `app/processors/spec.py` / `app/processors/overrides.py` |
| 前端同口径 | `processors_util.js` 的 `knownContextNames()` 是同一份集合的前端镜像（编辑页模板框、媒体库覆盖模板框、段下拉的"（未知）"标记都用它） | `web/js/processors_util.js` / `web/js/pages/{processor_edit,library_edit}.js` |
| 运行期（老数据 / 手写 YAML） | `render_segments(..., dropped=…)` 收集被留空的名字 ⇒ 引擎 stdout 打 `Unknown param: <作用域标签> (名字)` + `outcome.unknown_params` ⇒ 任务结果 `result.unknown_params`（计数）+ `samples.unknown_params`（`{label, file, params}`）+ `warnings[]` 汇总一条 + executor 逐条 WARNING 日志 + 收尾摘要「命名未知变量 N」 | `app/processors/engine.py` / `app/executor.py` |

**为什么不做成"未知名字直接失败"**：段序列的渲染契约就是"查不到就留空、绝不抛异常"（改名前不能因为命名里一个错字就让整个作品停摆）。所以运行期只**留痕不拦截**，由保存期尽量把"新写的错名字"挡住；老数据则在结果与日志里变成可计数的事实。

**为什么不新加待办种类**：待办看板已经因为"一条待办只记一次、同问题聚合"而被用户嫌噪音（看板上 `unresolved_episode` 这类条目数量最多）。未知变量属于"配置写错"，改一次就不会再有，用任务结果的计数 + 日志告警足够定位，不占用待办板。

### 影响面与规避

- **在哪里看得见**：任务详情右侧的**橙色告警区**（一条汇总，列出前若干个文件名并指向 `samples.unknown_params`）+ 下方**日志**面板里的逐条 WARNING（`命名里的未知变量被留空（文件名少了一段）：作品名/Season N/文件名 · 变量名`）+ 任务结果字段 `result.unknown_params`（计数）与 `result.samples.unknown_params`（`{label, file, params}`）。**它不进统计卡片那一排**（卡片是固定的一组计数），也不进收尾摘要以外的日志级别 —— 但不再有"任务成功却什么都没说"的情况。
- **编辑器实时预览的显示差别**：预览对"前端算不出来"的段一律显示 `{名字}` 花括号原文（表达式名与未知名字看起来一样），而运行期对**表达式名**会真求值、对**未知名字**整段略过。想确认某个名字到底认不认得，看段下拉框有没有 `名字（未知）` 标记、以及模板框/保存有没有报"未知变量"。
- **看见「命名未知变量 N」怎么办**：任务详情里逐条的 WARNING 会点名 `作品名/Season N/文件名 · 变量名`，去处理器编辑页（或媒体库的规则覆盖模板）把那个名字改对；改完把该作品重跑一次即可（见 [`docs/guides/FAQ.md`](../guides/FAQ.md) 第 42 问）。
- **升级注意事项**：保存**已经存在的**、带未知名字的旧配置会被 422 拦住（校验是保存路径，不是读取路径 —— 旧配置照旧能跑）。要在编辑页改别的字段时，先把那个段删掉或改成合法名字。
- 相关：变量表与表达式见 [`docs/contracts/PROCESSORS.md`](../contracts/PROCESSORS.md) §3 / §3.1；预览与真实渲染的差别、以及逐条排查步骤见 [`docs/guides/TROUBLESHOOTING.md`](../guides/TROUBLESHOOTING.md) §31。

### 相关测试

`tests/test_processor_spec.py`（段序列未知名字 422 / 空串 param 422 / 表达式名与 `episode_resolved` 放行 / `known_context_names()` 集合）、`tests/test_processor_engine.py::test_unknown_segment_param_is_still_dropped_but_now_recorded`（留空 + `unknown_params` 明细 + 汇总告警；取代原 `test_unknown_segment_param_is_currently_dropped_without_a_warning`）、`tests/test_library_overrides.py`（覆盖模板引用基本 spec 的表达式不再误报；`test_executor_makes_unknown_naming_variables_visible` 走 `execute_task()` 端到端核对结果键、样本、告警与日志）。

## KI-12 目标目录被手工删除、但作品账本仍在 ⇒ 整库运行必然失败

**状态：已记录，暂时搁置 —— 不修。** 官方重做路径「作品记录 → 删除」不会留下这个状态，只有**手工删掉目标目录**才会踩到。

### 现象

目标根（媒体库的「目标目录」）被人在文件管理器里删掉后，再对整库点「运行」：

- 任务 `status=failed`、`result` 里 `linked 0 / skipped 54`、耗时几百毫秒、看板多一条 `task_failed`；
- 任务行错误：`无法读取媒体库目录 /vol1/1000/Library/Test2211full：[Errno 2] No such file or directory: '/vol1/1000/Library/Test2211full'`；
- 源目录一个字节都没动（符合「源树只读」契约），但**链接一个都没重建** —— 用户以为"重跑一次就能恢复"，实际整库跑不动。

### 机制（已定位到行）

`link_records`（每库作品账本）只比对「源目录 + 目标目录 + 文件夹体积」，**不看目标目录是否还在**：

1. `app/processors/hardlink.py:162-165`：`_link_folder()` 命中"账本里已有该文件夹且体积一致"就 `print(PRINT_SKIPPED + folder)`（`hardlink.py:62` 的 `文件夹已记录且体积一致，跳过: `）后**直接 `return`**；
2. 目标根只在**真正建链**时创建（`hardlink.py:169 os.makedirs(target_folder, exist_ok=True)`）⇒ 全部文件夹都被跳过时，目标根**根本不会被创建**；
3. 改名阶段 `app/executor.py:537` 用 `settings.library_log_path(...)` 去读库目录 ⇒ ENOENT ⇒ 整个任务失败。

### 触发条件（谁会真的踩到）

| 入口 | 能不能制造「账本在、目录没了」 | 说明 |
|---|---|---|
| 「作品记录 → 删除」（`POST /api/libraries/{id}/works/delete`） | **不能** | 官方重做路径：连同目标作品夹一起删、并清账本 |
| 「作品记录 → 改名」（`POST /api/libraries/{id}/works/rename`） | **不能** | `app/routers/libraries.py:804` 有目标根守卫（缺失即 400） |
| 整库运行（`run_library`，`app/routers/libraries.py:839`） | **能** | 该端点**没有**同款前置守卫 |
| 手工 `rm -rf` 目标根 / 换挂载盘 / 迁移数据时漏掉目标树 | **能** | 账本在 `/data/mlm.db`，目标树在媒体盘 —— 两者不同步时就是这个状态 |

### 候选修法（三条，择一，未实施）
